# H264 지속 worker 2단계 준비

## 1단계 채택 후보

- H264 1.2Mbps
- persistent worker
- raw, 상태파일, worker response를 `/dev/shm`에 배치
- mp4v 대비 함수 경계 p50 46.01%, p95 27.42~28.78% 단축
- 파일 크기 54.95% 감소

사용자 승인 후 후보 diff를 저장소의 `uploader.py`에 적용했다. 개발 PC 구문·오프라인
회귀와 Jetson 격리 `/tmp` smoke가 모두 통과했다. 정확한 사전 검수 diff는
`h264_test_artifacts_20260926/uploader_shm_candidate.diff`에도 보존한다.

장시간 시험은 이 검증된 후보와 테스트를 커밋한 뒤 동일 커밋으로만 수행한다.
Jetson 운영 checkout 배포와 `main.py` 재시작은 2단계 결과 승인 이후로 분리한다.

## 후보 변경 조건

1. `H264_STATE_PATH` 환경변수를 지정하면 기존처럼 우선 적용
2. 기본값만 `H264_RAW_DIR/drone_clip_encoder_state.json`으로 변경
3. persistent worker response는 고유한 `raw_path + ".response.json"` 사용
4. 기존 `finally` cleanup이 raw와 response를 모두 삭제
5. mp4v와 per-event worker 경로는 변경하지 않음

## 클럭 상태

root 없이 읽은 현재 값:

- CPU governor: `schedutil`
- CPU min/max: 1,190,400 / 1,420,800kHz
- 조회 시 CPU: 1,420,800kHz
- GPU governor: `nvhost_podgov`
- GPU min/max: 114,750,000 / 1,109,250,000Hz
- 조회 시 GPU: 1,109,250,000Hz

`jetson_clocks --show`는 root 권한이 필요해 고정 여부를 직접 확인하지 못했다.
동적 governor 상태이므로 2단계에서는 각 회차의 클럭/온도 분포를 함께 기록한다.

## 운영 반영 전 실패 조건

- `/dev/shm` 여유가 raw payload + 64MB 미만이면 인코딩 시작 전 실패
- response 또는 상태 atomic write에서 ENOSPC가 발생하면 해당 이벤트 실패
- 상태파일은 재부팅 시 소실되며 연속 실패 카운터가 초기화됨
- 저장소의 main 로그를 영속 장애 증거로 사용한다. `/tmp` worker 로그와 tmpfs
  상태파일은 재부팅 후 보존을 보장하지 않으므로 사후 증거로 간주하지 않는다.

## Jetson 격리 확인 결과

- `/tmp`는 루트 ext4에 있고 `/dev/shm`은 3.3GiB tmpfs이며 확인 시 3.3GiB가
  가용했다. 따라서 상태파일 이동은 재부팅 후 연속 실패 카운터 소실이라는 실제
  의미 변화를 만든다.
- 이 카운터는 자동 롤백이 아니라 `h264_rollback_recommended` 경보용이다. 재부팅
  간 카운터 연속성을 포기하고 영속 main 로그를 장애 증거로 쓰는 조건으로 허용한다.
- 운영 PID 5563의 stdout/stderr는 모두
  `/home/hpc/drone_2026/code/logs/main.log`을 가리키며 해당 경로는 ext4이다.
- 기본 960×540, 48장의 raw 크기는 74,649,600B(약 71.19MiB)이다. 64MiB
  최소 여유를 합친 단일 job 요구량은 약 135.19MiB로 확인 당시 가용량보다 작다.
  다만 장시간 시험의 최소 가용량과 orphan 0개를 기준으로 다시 판정한다.
- 재부팅 간 경보 연속성이 운영 요구가 되면 성공 hot path는 그대로 두고, 두 번째
  연속 실패로 rollback 권고가 처음 발생할 때만 ext4 durable marker를 기록하는
  후속 설계를 사용한다.

## 2단계 실행 조건

비행 없는 유지보수 시간에만 수행한다.

1. 서로 다른 장면 복잡도의 저장 영상 최소 2개
2. mp4v/H264 각 100회, 총 30분 이상
3. cold/warm, p50/p95/max, 파일 크기
4. RSS, fd, thread, worker PID·재시작, 손상 MP4
5. CPU/GPU 실제 클럭과 온도 분포
6. 1.2Mbps/4Mbps/mp4v PSNR·SSIM 및 서버 판정 비교
7. `/dev/shm` ENOSPC 실패주입과 재시작 후 상태 정책 확인
8. 종료 후 raw/response/lock orphan 0개 확인

실제 업로드 종단 지연은 위 반복성·품질·실패 시험 통과 후 3단계에서 수행한다.

## 통과·롤백 기준

모든 기준을 충족해야 통과한다.

- 같은 영상의 mp4v 대비 H264 p50·p95가 각각 20% 이상 단축
- 영상별로도 H264 p95가 mp4v보다 악화되지 않음
- 100회 H264 성공 100%, 손상·빈 MP4 0개
- 예기치 않은 persistent worker 재시작 0회
- uploader와 persistent worker 프로세스를 각각 측정해 종료 시 fd/thread가 각
  warm 기준 +2 이내, RSS가 각 warm 기준 +100MiB 이내
- H264 첫 25회 대비 마지막 25회의 p95 증가가 10% 이내이며, response 기록
  p50 증가가 10ms 이내
- 종료 후 `/dev/shm` raw/response/lock orphan 0개
- 1.2Mbps의 PSNR 30dB 이상, SSIM 0.95 이상을 임시 품질 gate로 사용
- 동일 원본의 mp4v 대비 서버 최종 판정 일치 100%, anomaly score 차이
  중앙값 0.02 이하·p95 0.05 이하. anomaly score 범위는 0~1을 전제로 함
- ENOSPC 주입은 timeout 전에 명시적 실패, partial MP4 0개, 공간 복구 후 다음
  정상 job 성공 및 상태 `ok`

하나라도 실패하면 H264 운영 전환을 보류하고 `CLIP_ENCODER=mp4v`를 유지한다.
PSNR/SSIM 임시 gate만 실패하고 서버 판정·score gate는 통과한 경우에도 바로
완화하지 않는다. bitrate를 1.2→2→4Mbps 순서로 올려 같은 품질·지연 시험을
반복하고, 모든 gate를 만족하는 최저 bitrate를 다시 후보로 선택한다.

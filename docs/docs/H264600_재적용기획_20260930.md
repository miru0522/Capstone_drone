- 작성일: 2026-09-30
- 문서 상태: 검수 요청 전 초안
- 대상: Jetson `~/drone_2026/code/`
- 현재 운영 브랜치: `vadclip-v4-20260831`
- 현재 HEAD: `2007b8f`
- 실제 반영, 프로세스 재시작, 서버 전송, Claude Code 검수 요청은 이 문서 작성 범위에 포함하지 않는다.

## 1. 목적

이상 트리거 후 9초 링버퍼 영상을 서버에 올릴 때 사용하는 mp4v 인코딩을 Jetson 하드웨어 H264 600 kbps 인코딩으로 다시 전환한다.

목표는 다음과 같다.

1. 승인된 H264 600 kbps 인코딩 구조를 현재 Jetson 코드에 안전하게 재적용한다.
2. mp4v 대비 인코딩 시간을 0.1초 이상 줄인다.
3. 영상 크기를 줄이면서 서버 VideoMAE 판정과 `anomaly_score` 전송을 유지한다.
4. 현재 개발 중인 주기 녹화 기능과 H264 인코더가 겹쳐도 기능 실패나 자원 고갈이 발생하지 않게 한다.
5. `CLIP_ENCODER=mp4v`만으로 즉시 비교·복귀할 수 있는 경로를 유지한다.

20% 이상 단축은 적용 조건으로 사용하지 않는다. 기존 시험에서 H264 600 kbps의 인코딩 구간 단축은 전체 p50 0.426초, p95 0.739초였으며, 이 프로젝트가 요구하는 최소 개선량 0.1초를 충족했다.

## 3. 적용 결정

### 3.1 채택 구조

- `uploader.py` 프로세스 내부 persistent worker 1개
- worker: `h264_encoder_worker.py`
- GStreamer: `nvv4l2h264enc`
- 비트레이트: 600,000 bps
- 업로드 클립: 960×540, 9초, 81프레임
- 업로드 모드: `UPLOAD_MODE=B`
- 활성 설정: `CLIP_ENCODER=h264`
- `maxperf-enable=true`: 제외

### 3.2 이번 적용에서 제외하는 구조

유닉스 소켓 기반 독립 H264 데몬은 채택하지 않는다. 현재 프로토타입에는 연결된 클라이언트의 무기한 대기, 데몬 내부 GStreamer 정지 복구, stale socket 판정, 단일 장애점 문제가 남아 있다.

프로세스별 부팅 웜업은 기본 H264 600 재적용이 통과한 뒤 별도 커밋으로 진행한다. 웜업과 코덱 재적용을 한 커밋에 섞으면 기존 승인 후보와 새 동작의 원인을 구분하기 어렵다.

## 4. 후보 코드 구성 방법

### 4.1 기준점

현재 Jetson HEAD `2007b8f`를 기준으로 격리 디렉터리 또는 별도 worktree에서 후보를 만든다. 실제 checkout 파일은 검수와 승인 전까지 수정하지 않는다.

### 4.2 파일별 구성

| 파일 | 구성 방법 |
|---|---|
| `uploader.py` | 승인된 `7f273bb`의 H264 persistent worker 구현을 복원하고 현재 파일과 전체 diff 검토 |
| `h264_encoder_worker.py` | 승인된 `7f273bb` 파일을 바이트 단위로 복원 |
| `start_all.sh` | `CLIP_ENCODER=${CLIP_ENCODER:-h264}`, `H264_BITRATE=${H264_BITRATE:-600000}` 추가 |
| `restart_component.sh` | 위 두 환경변수 기본값 추가 |
| `main.py` | 현재 미커밋 주기 녹화 코드를 기준으로 H264 설정 로그 9줄만 수동 병합 |

`main.py`의 변경은 다음 범위로 제한한다.

1. `uploader` import에 `CLIP_ENCODER` 추가
2. `log_upload_configuration()` 인자에 `clip_encoder` 추가
3. 시작 로그에 실제 encoder 값 추가

링버퍼, VadCLIP, 업로드 worker, 호버 요청, 스트리밍, 주기 녹화 로직은 이 단계에서 수정하지 않는다.

승인 후보의 기준 SHA-256은 기존 manifest를 사용한다.

### P0-1. 정적 검사

### P0-2. mp4v 회귀 시험

후보 파일을 격리 환경에서 `CLIP_ENCODER=mp4v`로 실행한다.

- 81프레임 MP4 생성
- 프레임 수와 재생 가능 여부 확인
- `anomaly_score=None`일 때 점수 필드가 생기지 않는지 확인
- 기존 업로드 인터페이스가 유지되는지 확인

운영 `main.py` 재시작은 검수와 사용자 승인 이후에만 수행한다.

### P0-3. H264 600 단독 시험

- 저장 영상 또는 동일 raw frame 입력 사용
- 첫 호출과 두 번째 호출의 worker PID가 같은지 확인
- 두 결과가 각각 81프레임인지 확인
- 비트레이트 설정 600,000 확인
- `.partial`, raw frame, state 파일 정리 확인
- timeout 후 worker 종료·재생성 경로 확인

성능 판정은 mp4v 대비 0.1초 이상 단축 여부로 한다. 20% 비율 기준은 사용하지 않는다.

### P0-4. 주기 녹화와 동시 인코딩 시험

현재 주기 녹화는 별도 `nvv4l2h264enc` 프로세스를 4 Mbps로 실행하므로, 이상 클립 H264 600 kbps worker와 겹칠 수 있다. 이전 H264 승인 시험에는 이 구조가 없었으므로 새 P0이다.

격리 시험에서 다음 상황을 만든다.

1. 주기 녹화 인코딩 시작
2. 같은 시간에 이상 클립 H264 600 kbps 인코딩 요청
3. 두 출력 파일 디코딩과 프레임 수 확인
4. 각 프로세스 종료 코드와 소요시간 기록
5. `tegrastats`, RAM, swap, `/dev/shm`, GPU/encoder 오류 로그 기록
6. 10회 이상 반복해 교착, timeout, 손상 파일, 메모리 누수가 없는지 확인

동시 실행이 불안정하면 두 인코더를 한 번에 실행하지 않도록 전역 파일락 또는 공용 직렬 큐를 추가하는 별도 설계로 전환한다. 이 경우 H264 적용 후보를 바로 운영에 넣지 않는다.

### P0-5. 부모 통합 시험

카메라를 열지 않는 저장 영상 주입 방식으로 확인한다.

- 링버퍼 snapshot → `upload_clip_sync()`
- H264 worker 재사용
- 인코딩 결과 검증
- 업로드 직전 폼 데이터에 `drone_id`, 유효한 `anomaly_score` 포함
- `None` 점수일 때 `anomaly_score` 키 없음

실제 서버 전송 없이 로컬 요청 캡처로 먼저 검사한다.

### P0-6. 최소 서버 통합 시험

앞 단계 통과 후 대상 영상, 횟수, 엔드포인트를 제시하고 사용자 승인을 받은 경우에만 실제 서버로 전송한다.

- 저장 영상 1개
- mp4v 1회, H264 600 kbps 1회
- 서버 수신 완료, VideoMAE 시작·완료, 결과 응답 확인
- Jetson 인코딩 시간, 업로드 시간, 전체 시간 분리 기록
- 점수와 영상이 관제 화면에 정상 표시되는지 확인

서버 판정 재검증을 위해 30영상 전체를 다시 보내지 않는다.

검수와 사용자 승인 이후 다음 순서로 진행한다.

## 8. 중단 조건과 복귀

다음 조건이면 적용을 중단하고 원인을 분석한다.

- 현재 미커밋 `main.py` 변경이 사라지거나 예상 밖으로 변함
- 승인된 `uploader.py` 또는 worker 해시 불일치
- 문법·의존성·mp4v 회귀 시험 실패
- H264 출력 파일 없음, 0 byte, 디코딩 실패, 81프레임 불일치
- worker 응답 정지 또는 timeout 후 복구 실패
- 주기 녹화와 동시 실행 시 반복 오류, 교착, 손상 파일, 자원 고갈
- 실제 환경변수가 목표값과 다름
- 업로드 실패 또는 서버가 영상을 처리하지 못함
- 상태 파일 `status="rollback_recommended"`

개발 환경에서 인코딩 시간이 3초를 넘었다는 이유만으로 자동 롤백하지 않는다. 소요시간과 자원 사용량을 기록하고 기능 실패 여부와 함께 판단한다.

복귀는 `CLIP_ENCODER=mp4v ./restart_component.sh main`을 우선 사용한다. 코드 자체에 문제가 있으면 시간 표시 백업을 복원하고 `main.py`만 재시작한다.

## 9. 후속 단계: 프로세스별 웜업

기본 H264 600 적용이 안정화된 뒤 별도 커밋으로 다음을 구현한다.

1. `uploader.py`에 공개 함수 `warmup_clip_encoder()` 추가
2. H264 모드에서만 960×540 dummy frame 2장으로 worker 시작
3. 카메라 첫 프레임과 VadCLIP 초기화 후, 추론 루프 시작 전에 웜업
4. 웜업 PID와 첫 실제 인코딩 worker PID가 같은지 로그로 확인
5. 웜업 실패는 main 종료로 연결하지 않고 실제 첫 요청에서 재시도
6. 웜업 실패 횟수를 이벤트 인코딩 연속 실패 카운터와 분리
7. mp4v에서는 no-op

독립 데몬은 이 후속 단계에도 포함하지 않는다.

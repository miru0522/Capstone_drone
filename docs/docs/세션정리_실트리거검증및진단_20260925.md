## 2. 1차 시도 — 실패, nginx 408 발견

기존 wifi 우회 라우팅(`203.249.90.3 via wlan0 metric 50`, 이전 세션에서 임시로 걸어둔 것) 상태에서 `kakao_20260914.mp4`를 주입했다.

- 젯슨: VadCLIP 트리거 정상 발생(score=0.999), 영상 전송 시작
- 78초 후 실패: `[동기전송] 요청 오류: Remote end closed connection without response`
- 서버(`dae_ai_server`) 로그: **완전히 비어있음** — 요청이 애플리케이션까지 도달하지 못함
- nginx(`dae_frontend`) 로그에서 원인 확인: `POST /analyze-video HTTP/1.1" 408 0` — nginx가 클라이언트(젯슨)의 업로드를 기다리다 타임아웃
- 원인: `/analyze-video` 위치 블록에 `client_body_timeout`이 설정돼 있지 않아 nginx 기본값 60초가 적용됨. 이 시각 직전의 실제(비테스트) 트리거도 동일하게 408로 실패한 것을 로그에서 확인 — **이번 배포와 무관한 기존 문제**였다.
- 부수 발견: 이 시점 nginx 접근 로그에 외부 IP(`223.62.149.182`, `add-project.kro.kr:8031` 경유)가 실시간으로 관제 화면·사고 영상을 조회 중인 것을 확인 — 체험용 웹사이트 트래픽이 실제로 발생하고 있었다.

## 3. 원인 재진단 — 네트워크 경로가 근본 원인

nginx `client_body_timeout` 수정을 적용하기 전에, 젯슨의 동글(`eth1`) 경로가 여전히 서버에 도달 불가능한지 먼저 재확인했다.

```
dongle(eth1) -> HPC-server: HTTP=200 time=0.077501s   (동글, curl --interface eth1)
wifi(wlan0)  -> HPC-server: HTTP=200 time=1.112328s   (기존 우회 경로)
```

**동글이 이전 세션 기록("동글로는 도달 불가")과 달리 지금은 정상 도달하며, wifi보다 약 14배 빠르다.** 임시 wifi 우회 정책 라우팅을 제거했다:

```
sudo ip route del 203.249.90.3/32 via 192.168.0.1 dev wlan0 metric 50
```

제거 후 `ip route get 203.249.90.3`이 기본 라우팅(`dev eth1`, 동글)으로 정상 전환된 것을 확인했다.

## 4. 2차 시도 — 성공, 전체 파이프라인 실측

동일 영상(`kakao_20260914.mp4`)을 동글 경로로 재주입했다.

- 젯슨: score=0.936(첫 트리거), 이후 score=1.000(중복 트리거는 업로드 진행 중이라 자동 생략)
- 호버 요청: `command_receiver.py`에 제출됐으나 드론 상태가 `IDLE`이라 `unsafe_status:IDLE`로 안전하게 거부됨(J02 안전 로직 정상 동작, 실비행 영향 없음)
- 업로드 성공: `[동기전송] 성공`, 서버 응답 수신, 이벤트 ID **323** 생성
- 총 소요(젯슨 기준, "영상 전송 시작"→"서버 응답 수신"): **약 19.3초**

### 4-2. AI서버 파이프라인 세부 (analysis_id=`4893e06c-a56e-4133-a5dc-795faae7ef11`, event_id=323, 총 13,106.7ms)

|---|---:|---:|---|
| request_body | 32.2 | 0.2% | nginx가 받아둔 본문을 ai서버로 전달(7.1MB) |

### 4-3. 배포 검증 관점의 확인 사항 (승인 문서 요구사항과 대조)

- `metadata_merge`: `before`/`after`가 동일, `changed_fields: []` → 값이 조용히 덮어써지지 않음(승인 문서 §요구사항 2 충족)
- `input`에서 `vadScore_present: true, vadScore_invalid: false` 등 1차 점수가 `None`/`0.0`/실제값을 명확히 구분해 기록됨
- `request_terminal.backend_outcome: "completed"`, `response_status: 200` — 정상 종료 상태가 정확히 기록됨
- 민감정보(예외 메시지, locals, 소스 텍스트) 없이 `stage`/`event`/`duration_ms`/필드 존재여부만 기록되는 것을 실제 로그로 재확인
- 결론: **지난 배포 검수(`claude-deployment-verification-20260925.md`)에서 "실제 트래픽 미검증"으로 남겼던 한계가 이번 건으로 해소됨**

## 5. 별개로 발견한 문제 — DR-01 오프라인 판정 (이번 건과 무관)

사용자 질문("DR-01 오프라인 판정과 관계있나")에 대해 조사한 결과, **완전히 별개의 원인**임을 확인했다.

- 프론트엔드 오프라인 판정 로직(`useDroneStore.js`)은 순수하게 STOMP 텔레메트리 수신 여부(`lastSeen` 기준 10초 초과 시 OFFLINE)로만 결정되며, `/analyze-video` 업로드 경로와 구조적으로 무관하다.
- 젯슨 `telemetry_sender.log`에서 원인 확인: `[파라미터 대기] 연결되었으나 데이터 없음 (SR0_EXT_STAT, SR0_POSITION 확인 필요)`가 반복됨 — MAVSDK는 Pixhawk에 연결됐지만 위치/상태 MAVLink 스트림이 오지 않아 텔레메트리 자체가 완성되지 못하는 상태.
- 같은 로그에 배터리 `-1.0`(무효)도 계속 찍히는 것으로 보아, **배터리 무효값 문제와 동일한 근본 원인(Pixhawk 연결/스트림 상태)**일 가능성이 있다.
- **미해결** — 별도로 Pixhawk SR0_* 스트림 레이트 설정을 점검해야 한다.

## 6. 별개로 재확인한 것 — 서버/젯슨 시계 오프셋 (해결됨)

기존 메모리에 "HPC-server가 Jetson보다 5분22초 느림(NTP 미동기화)"로 기록돼 있었으나, 이번에 재측정한 결과 **더 이상 사실이 아님**을 확인했다.

- 측정(SSH 왕복시간 보정 포함 3회 반복): 젯슨이 서버보다 약 **0.38~0.39초** 느림(사실상 무시 가능)
- `timedatectl status`(서버): `NTP enabled: yes`, `NTP synchronized: yes` — 2026-09-13 당시엔 "no"였던 것이 그 사이 고쳐짐
- 서버 타임존 라벨은 `Asia/Tokyo(JST)`이나 UTC 오프셋은 KST와 동일(+9)이라 시각 계산에는 영향 없음
- **조치**: 기존 "+5분22초 보정" 메모를 폐기하고 최신 상태로 갱신함 — 이 보정을 더 이상 로그 대조에 쓰지 말 것

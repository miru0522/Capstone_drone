# mp4v와 H264 shm/shm 실제 함수 경계 비교

## 조건

- 동일 저장 영상에서 만든 동일한 81개 BGR 프레임 객체
- 960x540, 9fps, 조건별 20회, seed 20260927 무작위 교차
- mp4v: 실제 `_encode_frames_mp4v()` 진입부터 반환까지
- H264: 실제 `_encode_frames_h264()` 진입부터 반환까지
- H264 bitrate 1.2Mbps, persistent worker, state와 response는 `/dev/shm`
- mp4v에 존재하지 않는 H264 전용 상태/response 오버헤드는 추가하지 않음
- 실제 카메라·업로드·전력 설정 변경 없음

## 결과

| 조건 | p50 | p95 | max | 파일 중앙값 |
|---|---:|---:|---:|---:|
| mp4v | 1.985초 | 2.053초 | 2.124초 | 3,104,481 bytes |
| H264 shm/shm | 1.072초 | 1.462초 | 2.071초 | 1,398,522 bytes |

H264는 mp4v 대비 p50 46.01%, p95 28.78%, 파일 크기 54.95%를 줄였다.
max 개선은 2.48%뿐이다. H264 max는 persistent worker 최초 cold 회차 2.071초이며,
p95는 두 번째 H264 회차 1.462초다. 이후에도 worker encode 0.96~0.98초대
변동이 있어 n=20 tail을 운영 수치로 확정하지 않는다.

p50은 짝수 표본 두 중앙값의 평균이고, 기본 p95는 올림 순위법의 20개 중 19번째
표본이다. 같은 원시값을 선형보간하면 mp4v p95 2.057초, H264 p95 1.493초로
27.42% 단축된다. 두 정의 모두 20% 선별 기준을 통과한다.

H264 worker encode p50은 0.830초, p95는 0.981초였다. 20/20회 상태가 `ok`였고
실제 state/response 경로가 모두 `/dev/shm`임을 확인했다.

## 안전·운영 이상 이벤트 중첩 확인

- 총 40/40회 완료, 운영 main.py 전 회차 생존
- 시험 회차와 겹친 운영 이상 트리거, mp4v 인코딩, 업로드 시작: 모두 0회
- MemAvailable: 1,629,472~1,972,756KiB
- swap 사용: 1,101,312KiB로 일정
- 출력 파일은 매 회차 크기 확인 후 삭제

시험 시작부터 종료까지 swap 사용량이 같아 시험 중 추가 swap-in/out의 부재를
뜻하지는 않지만, 적어도 사용량 증가는 없었다. `tegrastats`는 1초 간격 88개
표본으로 약 81초 시험 구간을 덮었다.

`nvpmodel -q`는 `MODE_20W_6CORE`를 기록했다. `jetson_clocks --show`도 사후
캡처를 시도했지만 root 권한이 필요하다는 출력만 남았으므로 고정 클럭 여부는
확인하지 못했다. 설정은 변경하지 않았으며 이 시험만으로 스로틀링을 완전히
배제하지 않는다.

여기서 확인한 것은 운영 이상 트리거·인코딩·업로드가 시험 회차와 겹치지 않았다는
사실이다. main.py의 정상 추론 지연이나 프레임 드롭이 전혀 증가하지 않았다는
의미의 "운영 무교란" 주장은 하지 않는다.

## 판정 범위

동일 저장 영상의 실제 함수 반환 경계에서 H264 shm/shm 후보가 p50과 방향성 p95
모두 20%를 넘긴 1단계 선별 증거다. n=20 p95는 19번째 단일 표본이 결정하며,
max는 cold 회차에 민감하다. 품질, 100회/30분 안정성, tmpfs ENOSPC·재부팅 정책,
실제 업로드 종단 지연을 확인하기 전에는 운영 전환 승인으로 사용하지 않는다.
단일 `04_Violence` 영상 결과이므로 장면 복잡도가 다른 영상으로 일반화하지 않는다.

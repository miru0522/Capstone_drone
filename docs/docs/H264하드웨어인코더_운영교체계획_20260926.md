# H.264 하드웨어 인코더 운영 교체 계획

기준 문서: `docs/docs/H264하드웨어인코더_테스트아키텍처_20260926.md`

## 1. 결론

운영 교체의 기반은 Jetson에서 이미 시험한 **PyGObject의 GStreamer 직접 제어 방식**으로 한다. 과거 hang이 발생한 OpenCV `VideoWriter(..., CAP_GSTREAMER, ...)` 경로는 복원하지 않는다.

다만 시험 구현 `h264enctest.py`를 그대로 `uploader.py`에 복사하는 것은 보류한다. 현재 timeout은 모든 프레임을 `push-buffer`로 전달한 뒤 `runner.join(timeout)`에서만 작동한다. `appsrc block=true`의 `push-buffer` 또는 `pipeline.set_state(NULL)` 자체가 멈추면 timeout 지점에 도달하지 못할 수 있다. 운영 적용 전 GStreamer 실행을 종료 가능한 별도 프로세스로 격리한다. 현재 인코딩은 이미 `clip-upload-worker` 스레드에서 실행되므로 네이티브 hang이 호버·캡처·VadCLIP 추론을 직접 멈추지는 않는다. 실제 위험은 업로드 스레드와 snapshot 메모리가 회수되지 않고 이후 증거 영상 전송이 계속 차단되는 것이다.

이벤트별 `mp4v` 자동 폴백은 사용하지 않는다. H.264 실패를 숨기거나 H.264 대기 후 다시 소프트웨어 인코딩해 지연이 누적될 수 있기 때문이다. 운영 모드는 설정으로 `mp4v` 또는 `h264` 중 하나를 선택하며, H.264 문제가 발생하면 설정을 `mp4v`로 되돌려 프로세스를 재시작한다.

## 3. 시험 구현에서 보완할 사항

### 3.1 timeout 범위

현재 구현은 다음 순서다.

1. `pipeline.set_state(PLAYING)`
2. 모든 프레임에 대해 `appsrc.emit("push-buffer", ...)`
3. `end-of-stream` 전송
4. `runner.join(timeout=15)`

따라서 15초 timeout은 4번에만 적용된다. `block=true`인 appsrc는 downstream 정체로 내부 큐가 가득 차면 `push-buffer` 호출을 막을 수 있다. `end-of-stream`과 `pipeline.set_state(NULL)`도 별도 deadline이 없다. 이 호출이 네이티브 레벨에서 멈추면 현재 업로드 스레드는 강제 종료할 수 없고 이후 증거 영상 전송이 차단되므로 프로세스 격리가 필요하다.

### 3.2 장시간 자원 정리

12분 36초 시험은 초기 안정성 근거로 충분하지만 수 시간 운용의 근거는 아니다. bus signal watch와 callback, GLib MainLoop 스레드, pipeline, 임시 파일, 프레임 참조를 명시적으로 정리하고 프로세스 RSS·fd·thread 수 추세를 계측한다.

### 3.3 파일 유효성

현재 성공 조건은 파일 존재와 0바이트 초과다. 운영 경로에서는 자식 프로세스 성공 종료, EOS 수신, MP4 `moov` atom과 H.264 stream, 약 9초 재생시간과 fps를 검사한다. `.partial`에 작성하고 검증된 파일만 `.mp4`로 원자적 이름 변경한다.

## 4. 목표 운영 아키텍처

```text
main.py
  → 81프레임 960×540 snapshot
  → uploader.py
      → H264EncoderClient
          → 격리된 H264EncoderWorker 프로세스
              → 검증된 PyGObject/GStreamer 파이프라인
      → 유효 MP4 확인
      → 기존 HTTP multipart 업로드
```

`main.py`, RingBuffer, VadCLIP, `upload_clip_sync()`의 응답 계약은 변경하지 않는다. 변경 범위는 인코더 선택과 H.264 worker에 한정한다.

### 4.1 기본안: 이벤트별 subprocess

CUDA/TensorRT 초기화 이후 Python `fork()`를 사용하지 않는다. 기본안은 이벤트마다 CUDA 모듈을 import하지 않는 독립 Python worker를 `subprocess.Popen`으로 실행하는 것이다. worker는 한 건을 인코딩하고 종료한다. 부모는 전체 subprocess에 timeout을 적용하고 초과 시 process group을 terminate/kill한다.

프레임 전달은 우선 raw 임시파일 또는 stdin 스트림처럼 단순한 방식으로 시험한다. `/dev/shm` raw 파일을 사용할 때는 작업 전에 tmpfs 여유와 `MemAvailable`이 81프레임 payload 및 안전 여유를 충족하는지 확인한다. 전용 prefix와 job UUID를 사용하고 정상·오류·kill 경로에서 부모가 삭제한다. 시작 시 전용 prefix 중 owner PID가 없고 보존시간을 넘긴 파일만 정리한다.

자식은 별도 process group으로 실행하고 Linux parent-death signal 또는 동등한 수단을 적용해 부모가 비정상 종료되면 고아 worker가 남지 않게 한다. 부모는 worker PID와 출력 경로를 구조화 로그에 기록한다.

### 4.2 성능 선택 게이트

이벤트별 subprocess에서 프로세스 기동, raw 입력 전달, GStreamer 인코딩, MP4 검증을 각각 계측한다. 시험의 첫 건 1.621초와 이후 0.796초 차이가 프로세스 초기화인지 파이프라인 최초 생성인지 이 측정으로 구분한다.

subprocess 전체 p95가 동일 경계의 `mp4v` p95보다 최소 20% 빠르면 이 단순 구조를 채택한다. 충족하지 못할 때만 2단계 후보로 상주 worker와 shared memory를 설계·비교한다. 상주 worker는 준비상태, warm-up, hang 시 전체 worker 재기동, orphan IPC 정리를 별도 계획 변경으로 다시 검수받는다.

### 4.3 watchdog

부모가 monotonic clock으로 프레임 전달 시작부터 파일 검증 완료까지 전체 deadline을 관리한다.

- 정상 목표: subprocess 기동·입력 전달·인코딩·검증을 포함한 p95가 동일 경계 `mp4v`보다 최소 20% 빠름
- 하드 deadline 후보: 3초
- 초과 시 worker terminate → 짧은 grace → kill → partial MP4와 raw 입력 임시파일 정리
- 종료 실패 또는 오류 시 해당 업로드를 명시적으로 실패 처리
- 연속 실패 횟수와 worker 재시작 횟수를 구조화 로그 및 상태 파일에 기록하고, 연속 2회 실패 시 운영자가 즉시 `mp4v` 롤백 대상으로 식별할 수 있는 오류 상태를 남김

3초는 격리 구조 시험 후 확정한다. 정상 p95의 최소 2배이면서 운영 허용 지연 안에 드는 값을 사용한다.

### 4.4 모드 선택과 실패 정책

`uploader.py`에 `CLIP_ENCODER=mp4v|h264` 설정을 추가한다.

- `mp4v`: 현재 함수 사용
- `h264`: 격리 worker만 사용
- 알 수 없는 값: 시작 단계에서 실패

동일 이벤트에서 H.264 실패 후 `mp4v`를 재실행하는 자동 폴백은 두지 않는다. 롤백은 `CLIP_ENCODER=mp4v` 변경 후 `main` 재시작으로 수행한다. 시험 중 H.264 오류가 한 건이라도 발생하면 운영 전환 승인을 중지한다.

## 5. 구현과 검증 단계

### 1단계 — 증거 보존

- Jetson의 네 시험 파일과 관련 로그를 로컬 저장소의 검토 가능한 위치로 복사
- SHA-256, 실행 명령, JetPack/GStreamer 버전 기록
- 운영 통합 검증 완료 전 원본 삭제 금지

### 2단계 — production module

- `h264enctest.py`의 파이프라인·PTS·EOS 처리 코드를 이벤트별 worker로 이동
- `uploader.py`의 현행 함수를 `_encode_frames_mp4v`로 보존
- `encode_frames_to_mp4`는 `CLIP_ENCODER` dispatcher로 구성
- 인코더별 시작·완료·오류·elapsed·bytes를 같은 로그 스키마로 기록

### 3단계 — 격리·장애 처리

- `push-buffer`, EOS, NULL 전환 각각에 정지 주입
- deadline 뒤 worker PID 종료 확인
- partial MP4, raw 입력 임시파일, child process, thread, fd 잔존 여부 확인
- main 캡처·VadCLIP worker가 계속 동작하는지 확인

### 4단계 — 성능·품질 회귀

기준 문서의 트리거 영상 5개와 정상·저조도·고동작 영상을 사용한다.

- H.264 최소 100회 연속 인코딩
- subprocess 기동·입력 전달·인코딩·검증의 개별 시간과 전체 p50/p95/max 기록
- 4Mbps부터 시작하고 필요 시 2/3/4Mbps 비교
- H.264 MP4, 81프레임, 9fps, 약 9초 확인
- 기준 트리거 영상 5종에서 서버 VideoMAE·Qwen label과 score를 `mp4v`와 비교
- 전체 회귀 실행에서는 브라우저 변환·DB·알림 성공 여부 확인
- 캡처 fps, 추론 지연, RSS, fd, thread, 온도 확인

### 5단계 — 지속 시험

- 비행 없이 최소 30분 동안 H.264 인코딩·업로드 100회 이상 확보
- hang, 예기치 않은 worker 재시작, 손상 파일이 없어야 통과
- RSS/fd/thread의 시작·중간·종료 값을 비교하고 지속 증가가 없음을 확인
- 증가 추세가 불명확하거나 초기화되지 않으면 2시간 시험으로 연장해 기울기를 판정
- nvargus-daemon 시작 문제는 별도 문서 기준으로 분리

### 6단계 — 제한 전환과 롤백

- 현재 운영 소스 해시와 설정 백업
- `CLIP_ENCODER=mp4v` 기본값으로 배포해 회귀 확인
- 승인된 지상 시험에서 `h264`로 전환
- 성공률, 인코딩 p95, 파일 크기, 서버 처리 성공 확인
- 기준 위반 시 즉시 `mp4v`로 롤백
- 제한 전환이 끝나면 `testermain.py`와 주입 드라이버는 검증 증거와 해시를 보존한 뒤 legacy 위치로 이동하고, production module로 승격된 코드와 이름이 겹치는 시험 파일은 운영 경로에서 제거

## 6. 승인 기준

- OpenCV `VideoWriter + CAP_GSTREAMER` 경로가 운영 코드에 없음
- GStreamer가 별도 종료 가능한 프로세스에서 실행됨
- 모든 네이티브 hang 주입에서 deadline과 worker 강제 종료 성공
- 이벤트별 subprocess 구조에서 100회 이상·30분 이상 시험 시 hang·손상 파일 0건이며, 자원 추세가 불명확하면 2시간 연장 시험까지 통과
- subprocess 전체 H.264 구간 p95가 동일 경계의 `mp4v` p95보다 최소 20% 빠름
- 출력 파일 전부 H.264 MP4이며 약 9초 재생 가능
- 서버 디코딩·분석·저장·알림 성공률 100%
- main 캡처·VadCLIP 성능의 유의한 회귀 없음
- RSS/fd/thread의 지속 증가 없음
- `CLIP_ENCODER=mp4v` 롤백 절차 실제 검증

## 7. 제외 범위

- RingBuffer 프레임 수, 9fps, 960×540, 9초 클립 변경
- 서버 분석 모델 변경
- 자동 이벤트별 `mp4v` 폴백
- 실제 비행 시험 및 운영 배포
- nvargus-daemon 시작 문제 수정

이 계획 승인 후에도 구현과 배포는 별도 작업으로 진행한다.

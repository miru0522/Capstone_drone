# H264 지속 worker 20% 감축 조건 연구

## 목표와 판정식

동일한 실제 81프레임(960×540, 9fps)을 입력으로 사용하고 아래 두 지표를 분리한다.

1. **인코딩 구간:** `encode_frames_to_mp4()` 진입부터 완결 MP4 반환까지
2. **종단 구간:** 이상 판정 시점부터 서버가 업로드 body를 모두 받은 시점까지

후보 채택 기준은 mp4v 대비 H264 p95가 20% 이상 짧고, 서버 판정 결과가 허용
범위에서 유지되며, 파일 크기 때문에 종단 구간이 악화되지 않는 것이다. 3회 최선값은
채택 근거로 사용하지 않는다.

## 현재 근거

- 이벤트별 subprocess: mp4v 중앙값 1.881초, H264 2.092초 — 탈락
- 지속 worker 4Mbps: mp4v 1.943초, H264 1.673초 — 중앙값 13.9% 단축
- 예열 후 최선 회차: H264 1.502초 — 3개 표본 중 최솟값인 참고치이며
  채택 근거나 20% 달성 신호로 사용하지 않음
- 지속 worker 1.2Mbps: mp4v 1.951초, H264 1.678초
- 파일 크기: mp4v 1.32MB, H264 4Mbps 4.61MB, H264 1.2Mbps 1.38MB
- 1단계 n=20 무작위 시험: mp4v p95 2.011초, H264 1.2Mbps p95
  1.420초(29.38% 단축). 단 n=20의 p95는 20개 중 19번째 단일 표본이
  결정하므로 방향성 근거일 뿐 확정 수치가 아니다.

## 단계 0: 실험 설계 검수

변수는 한 단계에서 하나의 축만 바꾼다. 실제 운영 코드나 카메라를 바꾸지 않고
Jetson `/tmp` 복사본과 저장된 시험 영상으로 실행한다. 장시간 부하는 비행 여부가
확인된 별도 시험 시간에만 수행한다.

### 1단계 — 시간 분해와 저비용 후보 선별

측정 전 `nvpmodel -q`, `jetson_clocks --show`를 기록하고 값을 변경하지 않는다.
각 회차의 mp4v/H264 및 후보 순서를 고정 난수 seed로 무작위화하고, 회차 사이에
동일한 idle 간격을 둔다. 측정 중 `tegrastats`를 함께 기록한다.

각 회차를 다음으로 분해한다.

- raw 준비: 형식 검사 + 81개 frame을 `/dev/shm`에 기록
- worker 대기: 요청 전달부터 GStreamer EOS/응답까지
- 응답파일 polling/fsync를 포함한 IPC
- MP4 검증·rename
- 출력 크기

후보:

기준선은 현재 frame별 `frame.tobytes()`+`write()`다.

1. 지속 worker cold 1회와 이후 warm 회차 분리
2. 4Mbps와 1.2Mbps 크기·속도 비교
3. raw 준비 구간만 `tobytes()+write()`와 `memoryview()+os.writev()` 비교

후보별 최소 20회를 무작위 교차 순서로 측정한다. `writev`는 raw 준비 구간의
절대 절감량이 작으면 운영 구현까지 진행하지 않는다. 현재 main.py가 실행 중이므로
이 단계는 선별용이며 최종 p95로 사용하지 않는다.

### 2단계 — 선택 후보 반복성과 영상 품질

1단계 Claude 검수에서 통과한 최소 후보만 대상으로 한다.

- 비행하지 않는 시험 시간에 mp4v/H264 각각 100회, 30분 이상
- p50/p95/max, cold 1회와 warm 회차 분리
- RSS, fd, thread, worker 재시작, 손상 파일 추세
- 1.2Mbps 후보는 동일 원본 대비 PSNR/SSIM 및 서버 판정 결과를 4Mbps와 비교

### 3단계 — 종단 지연

- 동일 크기 조건에서 드론 업로드 시작/완료와 서버 body 수신 시각 계측
- 분석 모델 처리시간과 영상 업로드시간을 분리
- 4Mbps와 1.2Mbps 중 서버 판정 품질을 통과한 후보만 비교
- 종단 p95가 mp4v보다 개선되지 않으면 H264 교체 중단

### 4단계 — 운영 후보 확정

- Claude가 1~3단계 증거와 구현 diff를 최종 검수
- 통과 시에만 Jetson 활성 브랜치 배포 계획 작성
- `CLIP_ENCODER=mp4v` 실제 롤백 후 재시작 검증

## 초기 가설

- 지속 worker도 매 요청마다 `Gst.parse_launch()`와 pipeline 상태 전환을 수행한다.
  따라서 warm 회차 차이는 pipeline 재사용 효과가 아니며 import/Gst.init 캐시,
  드라이버 상태 또는 스케줄링 잡음으로 분리해 확인해야 한다.
- 126MB raw 직렬화 절감은 절대 시간 분해 결과가 충분히 클 때만 채택한다.
- encoder 기본 preset은 이미 `UltraFastPreset`이라 preset 변경은 제외한다.
- 4Mbps는 전송 크기 때문에 종단 지연 후보로 부적합할 가능성이 높다.
- `maxperf-enable=true`는 현재 단계에서 제외하고 비행 없는 유지보수 시간에만
  전력·발열을 함께 측정한다.

## 단계 0 Claude 설계 검수 반영

- 판정: `REVISE`
- MUST 5건을 위 설계에 반영했다.
- `maxperf-enable`과 100회/30분 시험, 실제 업로드는 유지보수 시간으로 분리했다.
- 현재 실행 가능한 1단계는 A) 무작위 mp4v/H264 20회, B) 4/1.2Mbps 20회,
  C) raw 쓰기 방식의 구간 단독 프로파일링이다.

### 재검수

- 판정: `APPROVE`
- 최초 MUST 5건과 SHOULD 4건 반영 완료 확인
- main.py 실행 중에는 위 A/B/C만 허용
- 전력·클럭 변경, `maxperf-enable`, 100회/30분, 실제 업로드는 금지

## 단계 1 Claude 결과 반영

- 판정: `REVISE`
- H264 1.2Mbps만 정식 후보로 2단계 진출
- H264 4Mbps는 속도가 같고 파일이 3.3배이므로 품질 비교 기준선으로만 유지
- `writev`는 전체 약 1.2% 절감이라 기각
- 1단계 시작 시 swap이 이미 약 1.06GB 사용 중이었으며 2단계 전 재확인 필요
- 약 0.30초로 계산한 값은 순수 IPC가 아니라 상태파일 fsync/락, stdin 전달,
  worker JSON parse, response fsync, 10ms polling을 포함한 잔차다.
- seq28의 잔차 0.158초는 다른 회차 약 0.30초 대비 이상치이며, 세부 계측 전에는
  원인을 알 수 없는 계측/스케줄링 잡음으로 취급한다.
- 2단계 전에 위 잔차를 20회 세부 분해하고 Claude 재검수를 받는다.

## 단계 1 IPC 세부 진단

- `started` 상태 atomic JSON 기록: p50 149.59ms, p95 157.31ms
- JSON 직렬화와 stdin write/flush: 합계 p50 약 0.23ms
- worker JSON parse: p50 0.134ms
- response atomic JSON 기록과 감지: p50 148.77ms, p95 151.55ms
- worker encode: p50 815.63ms, p95 952.68ms

기존 약 0.30초 잔차는 IPC 자체가 아니라 ext4 `/tmp`에 있는 상태파일과 response
파일의 atomic write/fsync가 대부분을 차지했다.

추가로 1단계 benchmark가 운영 함수의 마지막 `succeeded` 상태 기록을 누락한 것을
발견했다. 따라서 H264 p95 1.420초와 29.38% 단축 주장은 운영 함수 경계 수치로
폐기한다. 약 0.15초를 단순 가산한 22%는 가설일 뿐이며, 두 상태 기록을 모두
포함한 수정 기준선을 다시 측정하기 전에는 20% 달성으로 판정하지 않는다.

## 단계 1 저장소 2x2 결과

- `/tmp` state + `/tmp` response: p50 1.451초
- `/dev/shm` state + `/tmp` response: p50 1.209초, 16.69% 단축
- `/tmp` state + `/dev/shm` response: p50 1.360초, 6.30% 단축
- `/dev/shm` state + `/dev/shm` response: p50 1.061초, 26.86% 단축

단일 파일 전환은 H264 함수 내부 20% 목표에 미달하고 두 파일 전환만 넘었으므로
다음 후보는 state와 response를 모두 `/dev/shm`에 두는 조건이다. 전역 첫 cold
회차가 반드시 한 조건에 배정되는 구조 때문에 n=20 p95는 확정하지 않는다.

이 수치는 H264 후보 내부의 `/tmp,/tmp` 대비 개선율이다. mp4v 대비 또는 서버 전송
종단 20% 달성을 뜻하지 않으며, 동일 영상에서 실제 `_encode_frames_mp4v()`와
선택된 `_encode_frames_h264()` 전체 반환 경계를 교차 측정해야 한다.

## 단계 1 실제 mp4v/H264 함수 경계 비교

동일 프레임 객체를 사용해 실제 함수 경계를 조건별 20회 무작위 교차했다.

- mp4v: p50 1.985초, p95 2.053초, 3,104,481 bytes
- H264 1.2Mbps shm/shm: p50 1.072초, p95 1.462초, 1,398,522 bytes
- H264 단축률: p50 46.01%, p95 28.78%
- 선형보간 p95 단축률: 27.42%
- 파일 크기 감소: 54.95%

1단계 선별에서 20% 조건은 통과했다. n=20 tail과 최초 worker cold 영향 때문에
2단계 반복성·품질 시험 및 3단계 서버 종단 시험 전에는 운영 전환을 승인하지 않는다.
기본 p95는 올림 순위법의 20개 중 19번째이며, 선형보간 정의에서도 결론은 같다.

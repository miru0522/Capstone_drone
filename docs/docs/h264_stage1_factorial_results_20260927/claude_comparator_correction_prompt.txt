직전 결과 검수의 다음 MUST를 재검토하라.

당신은 "mp4v n=20 대조군도 동일 /dev/shm,/dev/shm 저장소 조건과 완전한 started+succeeded 상태 기록 경계"를 요구했다. 그러나 코드를 보면:

- `uploader._encode_frames_mp4v()`는 H264 상태파일과 worker response를 전혀 사용하지 않는다.
- 현재 운영 mp4v도 started/succeeded 상태 기록을 하지 않는다.
- H264 후보만 안전 관측을 위해 `_record_h264_state()`와 worker response를 사용한다.
- H264 최종 MP4와 mp4v 최종 MP4는 둘 다 `tempfile.mkstemp()` 기본 `/tmp`에 생성된다. 이번 `/dev/shm` 요인은 최종 영상 저장소가 아니라 H264 전용 수 KB 상태/IPC 파일만 바꾼 것이다.

따라서 mp4v에 인위적으로 H264 상태 기록과 response 파일을 추가하면 실제 교체 전 mp4v보다 느려져 H264에 유리한 대조군이 된다. 올바른 교체 판단은 같은 저장 영상·같은 fps/해상도에서 실제 운영 함수 경계인 `_encode_frames_mp4v()` 반환 시간과, 안전 오버헤드를 모두 포함한 선택 후보 `_encode_frames_h264()` 반환 시간을 고정 seed 무작위 교차로 각 20회 측정하는 것이라고 판단한다. H264 쪽 state/response만 `/dev/shm` 조건을 사용한다.

## 1. 검수 결과와 계획 범위

검수 결과 기존 두 수정은 모두 승인 가능하며 차단급 결함은 없었다. 후속 보완 제안은 다음 두 건이다.

1. 배터리 단위 `auto` 판정이 프로세스 재시작 후 첫 유효 샘플에 의존하는 문제
2. 실행 스크립트를 거치지 않고 `python3 main.py`를 직접 실행하면 `UPLOAD_MODE=A`가 적용될 수 있으나, 실제 이상 업로드 전까지 이를 알아보기 어려운 문제

이번 문서는 위 두 항목의 구현·시험 계획만 정의한다. 실제 Pixhawk hover 시험, 배터리 RTL 실비행, 임계값 calibration은 별도 승인과 안전 조건이 필요한 후속 작업으로 유지한다.

## 2. 현재 코드에서 확인한 사실

### 2.1 배터리 단위 판정

- `battery_utils.py`의 `BatteryPercentNormalizer`는 `BATTERY_REMAINING_UNIT=auto|fraction|percent`를 지원한다.
- `auto`에서 최초로 `raw > 1.0`이 관측되면 `percent`로 고정한다.
- `raw <= 1.0`인 동안에는 `fraction`으로 간주한다.
- 따라서 실제 percent 입력이 `0.5`인 상황에서는 0.5%가 아니라 50%로 변환될 수 있다.
- `command_receiver.py`와 `telemetry_sender.py`는 각각 별도의 normalizer를 생성하므로 재시작 시점과 관측 순서에 따라 서로 다른 판단을 할 가능성이 있다.
- 기존 회귀 테스트는 `auto + 96.0`, 명시적 `fraction + 0.407`, 비정상 값 거부를 검증하지만 `auto + 0~1 percent`, 재시작, 영속 상태, 두 프로세스 일관성은 검증하지 않는다.
- 현재 실기 텔레메트리는 `remaining_percent=-1.0`을 보고하고 있어 실제 단위 판정을 위한 정상 샘플이 없다.

### 2.2 업로드 모드

- `start_all.sh`와 `restart_component.sh`는 별도 설정이 없을 때 `UPLOAD_MODE=B`를 내보낸다.
- 실행 중인 `main.py` 프로세스에서도 `UPLOAD_MODE=B`가 확인됐다.
- `uploader.py`는 구버전 호환을 위해 자체 기본값 `A`를 유지한다.
- 실행 스크립트를 사용하지 않고 `python3 main.py`를 직접 시작하면 A 모드가 될 수 있다.
- 현재는 업로드 성공 로그에서 `[A안]` 또는 `[B안]`을 확인할 수 있지만, 실제 이상 트리거가 발생하기 전에는 모드가 로그에 나타나지 않는다.

## 3. 보완 항목 A — `UPLOAD_MODE` 기동 로그

### 3.1 목표

`main.py`가 시작될 때 실제 적용된 업로드 모드, 서버 URL, 드론 ID를 즉시 한 번 기록해 잘못된 실행 환경을 사고 발생 전에 발견한다. 비밀값과 장치 키는 로그에 남기지 않는다.

예상 로그 형식:

```text
분석 업로드 설정: mode=B, drone_id=DR-01, url=http://203.249.90.3:8031/analyze-video
```

### 3.2 구현 계획

1. 수정 전 `main.py`와 필요 시 `uploader.py`를 로컬 백업한다.
2. `main.py`가 `uploader.py`의 검증 완료된 설정값 `UPLOAD_MODE`, `ANALYZE_URL`, `DRONE_ID`를 참조하도록 한다.
3. `if __name__ == "__main__":` 진입 직후, 카메라와 TensorRT 초기화 전에 설정 로그를 한 번 출력한다.
4. A 모드이면 구버전 영상 전용 모드임을 `WARNING`으로 표시하고, B 모드이면 `INFO`로 표시한다.
5. 유효하지 않은 모드는 기존 `uploader.py` 검증대로 시작 단계에서 실패시킨다.

### 3.3 시험 계획

| 시험 | 기대 결과 |
|---|---|
| `UPLOAD_MODE=B` 모듈/진입점 테스트 | B 설정이 한 번 출력되고 경고가 발생하지 않음 |
| `UPLOAD_MODE=A` 격리 테스트 | A 설정과 영상 전용 모드 경고가 출력됨 |
| `UPLOAD_MODE=invalid` 격리 테스트 | 카메라 초기화 전에 명확한 `ValueError`로 종료 |
| `restart_component.sh main` 실기 확인 | 실제 프로세스 환경과 시작 로그가 모두 B |

실기 적용 시 전체 파이프라인을 재시작하지 않고 `main.py`만 교체 기동한다.

### 3.4 완료 기준

- `main.py` 시작 로그만으로 A/B 적용 여부를 판단할 수 있다.
- 기존 `130_upload_form_contract_offline.py` 4건이 계속 통과한다.
- Python 문법 검사와 최근 로그 오류 검사가 통과한다.
- 카메라, VadCLIP/TensorRT, 9 FPS 캡처가 정상 복구된다.

## 4. 보완 항목 B — 배터리 단위 판정과 재시작 일관성

### 4.1 안전 원칙

0~1 범위의 값만으로는 fraction 50%(`0.5`)와 percent 0.5%(`0.5`)를 구분할 수 없다. 샘플 수를 늘려도 값의 의미가 확정되지 않으므로 다음 원칙을 적용한다.

1. 정상 센서에서 실제 raw 범위를 확인하기 전에는 단위를 추측해 RTL을 시험하지 않는다.
2. 운영 단위는 `BATTERY_REMAINING_UNIT=fraction|percent` 명시 설정을 우선한다.
3. `auto`는 명확한 근거가 있거나 검증된 영속 상태가 있을 때만 단위를 확정한다.
4. 단위가 불명확하거나 값이 무효이면 RTL 판단을 보류하고 상태를 명확히 기록한다.
5. 비행 중 단위가 바뀌거나 두 프로세스가 서로 다른 단위를 선택하지 못하게 한다.

### 4.2 1단계 — 읽기 전용 실측

배터리와 프로펠러를 안전하게 분리하거나 비행팀이 승인한 지상 조건에서 다음 값을 수집한다.

- MAVSDK `battery.remaining_percent` raw 값
- `battery.voltage_v`
- PX4/QGroundControl에 표시되는 배터리 백분율
- 시동 직후부터 최소 20개 유효 샘플의 범위와 변화 방향
- Pixhawk/MAVSDK 버전 및 배터리 파라미터

현재 `remaining_percent=-1.0` 문제를 먼저 해결한다. 정상 샘플을 확보하기 전에는 단위 설정과 RTL 임계값을 실기에 확정하지 않는다.

### 4.3 2단계 — 단위 결정 정책 구현

검증된 raw 범위에 따라 다음 중 하나를 운영 설정으로 확정한다.

- MAVSDK 표준 fraction이면 실행 스크립트에 `BATTERY_REMAINING_UNIT=fraction`
- 실기에서 0~100 percent가 확인되면 `BATTERY_REMAINING_UNIT=percent`

`auto`를 계속 지원해야 한다면 다음 보강을 함께 적용한다.

1. 공유 상태 파일 경로를 환경변수로 정의한다. 예: `/tmp/drone_battery_unit.json`.
2. `state_store.py`의 원자적 쓰기와 파일 잠금 방식을 사용한다.
3. 상태에는 `unit`, `source`(`configured|observed`), `updated_at`, `schema_version`을 기록한다.
4. 프로세스 시작 시 명시적 환경변수, 유효한 공유 상태, 신규 관측 순으로 우선순위를 적용한다.
5. `raw > 1.0`은 percent 근거로 사용할 수 있지만, 0~1만 관측된 상태는 자동으로 fraction 확정하지 않고 `unresolved`로 유지한다.
6. `unresolved` 상태에서는 텔레메트리에 임의 변환값을 전송하지 않고 배터리 상태 미확정 경고를 30초 제한으로 남긴다.
7. `command_receiver.py`는 미확정 값을 RTL 판정에 사용하지 않는다. 비행 시작 허용 여부는 실제 센서 정상화 후 비행팀과 합의해 별도 결정한다.
8. 명시적 단위와 저장된 단위가 다르면 명시적 설정을 우선하고 불일치 경고를 남긴다.

### 4.4 코드 변경 예상 범위

| 파일 | 예정 변경 |
|---|---|
| `battery_utils.py` | 단위 출처와 unresolved 상태 표현, 공유 상태 불러오기·검증·저장, 불일치 검출 |
| `state_store.py` | 기존 원자적 JSON API 재사용. 추가가 필요하면 배터리 상태 전용 최소 래퍼만 추가 |
| `command_receiver.py` | 확정된 단위만 RTL 판단에 사용하고 기동 시 단위·출처 로그 출력 |
| `telemetry_sender.py` | command receiver와 동일한 공유 단위 사용, 미확정 값을 정상 퍼센트로 보내지 않음 |
| `start_all.sh` / `restart_component.sh` | 실측으로 확정된 `BATTERY_REMAINING_UNIT` 운영 기본값 설정 여부 검토 |
| `129_safety_regression_offline.py` | 재시작·영속 상태·모호값·프로세스 간 일관성 회귀 테스트 추가 |

### 4.5 필수 회귀 테스트

1. 명시적 fraction: `0.407 → 40.7%`
2. 명시적 percent: `40.7 → 40.7%`, `0.5 → 0.5%`
3. auto 신규 상태에서 `96.0` 관측: percent 확정·저장
4. 재시작 후 저장된 percent 상태에서 첫 값 `0.5`: `0.5%` 유지
5. 상태가 없는 auto에서 첫 값 `0.5`: unresolved 처리, 50%로 변환하지 않음
6. 명시적 단위와 저장된 단위 불일치: 명시값 우선·경고
7. NaN, Inf, 음수, 범위 초과 및 손상된 상태 파일 거부
8. 두 normalizer 인스턴스가 같은 공유 상태를 읽어 동일 결과 생성
9. 동시 읽기·쓰기 중 부분 JSON을 관측하지 않음
10. unresolved/무효 배터리 값으로 RTL이 잘못 트리거되거나 해제되지 않음
11. 확정된 단위에서 임계값 이하일 때 기존 RTL 트리거 조건 유지
12. 프로세스 재시작 후에도 확정 단위와 배터리 판단 결과 유지

### 4.6 실기 검증 단계

1. 정적 검사와 오프라인 회귀 테스트 통과
2. 프로펠러 분리 지상 조건에서 두 프로세스의 raw·unit·normalized 로그 일치 확인
3. 각 프로세스를 개별 재시작해 단위가 유지되는지 확인
4. 정상 배터리에서 관제 표시값과 QGroundControl 표시값 대조
5. 임계값 근처 시험은 신호 주입 또는 MOCK으로 먼저 수행
6. 실제 RTL 시험은 배터리 센서 정상화, 지상 안전 조건, 비행팀·관제팀 합의 후 별도 승인받아 수행

### 4.7 완료 기준

- 0~1 모호값을 근거 없이 fraction으로 확정하지 않는다.
- `command_receiver.py`와 `telemetry_sender.py`가 항상 같은 단위와 변환 결과를 사용한다.
- 재시작 후 첫 샘플이 1 이하더라도 이전에 검증된 percent 단위를 유지한다.
- 무효·미확정 값은 정상 배터리 값처럼 서버에 전송되거나 RTL 판단에 사용되지 않는다.
- 기존 비행 명령, 상태 복구, 텔레메트리 주기에는 회귀가 없다.

## 7. 작업 착수 전 확인 사항

- 항목 A는 비행 제어 동작을 바꾸지 않는 진단 로그 보강이므로 독립적으로 진행할 수 있다.
- 항목 B는 RTL 판단에 직접 영향을 주므로 정상 센서 raw 값과 단위 정책이 확정되기 전에는 실기 동작을 변경하지 않는다.
- 실제 Pixhawk 저전압/RTL 시험은 사용자와 비행·관제 담당자의 명시적 합의 후 진행한다.

# H264 600 kbps 교체 준비 세션 정리 (2026-09-29)

## 결론

H264 600 kbps를 mp4v 교체 후보로 확정하고, 로컬 코드와 검토용 배포 번들을 준비했다. 실제 Jetson 운영 checkout 복사와 `main.py` 재시작은 수행하지 않았다.

합격 기준은 기존 연구 목표였던 20%가 아니라 실제 요구인 **p50·p95 각각 0.1초 이상 단축**으로 정정했다. 전체 집계와 고정 참조 영상 2개가 모두 이 기준을 통과했다.

## 이번 세션에서 한 일

1. 운영 Jetson 상태를 읽기 전용으로 다시 확인했다.
   - 브랜치 `vadclip-v4-20260831`, HEAD `f1fade2`
   - `main.py` PID 5563, `UPLOAD_MODE=B`, 인코더 기본 mp4v
   - 운영 `uploader.py`에는 H264 경로가 없고 `h264_encoder_worker.py`도 없음
2. 전체 30영상에서 mp4v/H264 600 kbps 픽셀 품질을 측정했다.
   - 같은 960×540 원본 프레임 81개를 코덱별로 인코딩 후 디코딩 비교
   - 서버 전송과 카메라 접근 없음
3. H264 600 kbps 시작 설정을 로컬 `jetson/code/start_all.sh`와 `restart_component.sh`에 추가했다.
4. 운영 기준본, 배포 후보, 해시 manifest, 사전 검사 스크립트와 결과를 `h264_600_cutover_20260929/`에 구성했다.
5. 후보를 Jetson `/tmp/codex_h264_600_cutover/`에 올려 사전 검사를 실행했다.
   - Python 문법, shell 문법, `nvv4l2h264enc` 플러그인, main PID, 후보 설정 검증 PASS
6. Jetson 격리 디렉터리에서 기존 오프라인 테스트를 실행했다.
   - 업로드 폼 계약 4건 PASS
   - H264 per-event/persistent 성공·실패·timeout·정리 및 mp4v 선택 PASS
7. 2026-09-27부터 고아 상태로 남아 있던 Stage1 격리 시험 프로세스 그룹 PGID 13621을 확인 후 SIGTERM으로 정리했다. 운영 `main.py`는 계속 PID 5563으로 생존했다.

## 측정 결과

### 지연시간

| 범위 | p50 단축 | p95 단축 |
|---|---:|---:|
| 전체 100회 | 0.426초 | 0.739초 |
| 참조 A | 0.264초 | 0.278초 |
| 참조 B | 0.463초 | 0.408초 |

### 픽셀 품질

| 지표 | mp4v | H264 600 kbps |
|---|---:|---:|
| 전체 평균 PSNR | 37.02 dB | 36.36 dB |
| 최저 영상 평균 PSNR | 33.93 dB | 32.00 dB |
| PSNR 30 dB 이상 | 30/30 | 30/30 |
| 전체 평균 SSIM | 0.96820 | 0.95575 |
| SSIM 0.95 이상 | 27/30 | 23/30 |
| 평균 파일 크기 | 1,255,478 bytes | 682,161 bytes |

H264는 집계 PSNR/SSIM 기준을 통과했고 평균 파일 크기는 45.67% 감소했다. mp4v 대비 평균 PSNR은 0.666 dB, SSIM은 0.01245 낮았다. 일부 복잡한 영상의 SSIM 저하는 교체 후 초기 운영 관찰 대상으로 남긴다.

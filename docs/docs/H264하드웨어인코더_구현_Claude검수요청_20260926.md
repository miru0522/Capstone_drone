반드시 `git diff`와 새 파일 전체를 확인하고 아래를 한국어로 답한다.

1. 치명적 오류, 교착·좀비 프로세스·임시파일 누수·불완전 MP4 가능성
2. Jetson GStreamer 파이프라인이 보존한 실기 시험 구현과 양립하는지
3. H264 실패 시 이벤트별 mp4v 자동 fallback이 없는지, 설정 롤백이 명확한지
4. 기존 mp4v 경로와 업로드 계약에 회귀 위험이 있는지
5. 성능 목표에 비해 굳이 들어간 복잡성 또는 빠진 최소 기능이 있는지
6. 운영 배포 전에 반드시 고쳐야 할 항목(MUST)과 선택 개선(SHOULD)을 구분

현재 검증 증거(2차 검수 시점):

- 수정 5개 파일 Python AST 파싱 성공
- `132_h264_subprocess_offline.py` 통과
  - 성공 결과 원자적 확정
  - 작업기 return code 전달
  - timeout 시 작업 프로세스 종료
  - raw/partial/final 임시파일 정리
  - mp4v 선택 경로 유지
- 1차 Claude MUST 3건 반영:
  - `PR_SET_PDEATHSIG(SIGTERM)` 및 부모 PID 경합 검사
  - 검증본과 동일한 `is-live=true`, 기본 filesink pipeline
  - 연속 실패/롤백 권고 상태 파일
- Jetson 실제 새 작업기 3프레임 H264 생성 성공
  - Quicktime/H.264 Constrained Baseline, 0.333초, seekable 판독
- Jetson 부모→작업기 통합 검사 성공
  - 상태 `ok`, success=1, failure=0, raw/output 정리
- Jetson 부모 종료 후 작업기 자식 종료 검사 성공
- 동일 실제 81프레임 3회 비교:
  - 이벤트별 subprocess: mp4v 중앙값 1.881초, H264 중앙값 2.092초(게이트 실패)
  - 조건부 지속 worker: mp4v 중앙값 1.943초, H264 중앙값 1.673초
  - H264 4Mbps 파일 4.61MB, mp4v 1.32MB로 전송 크기 게이트 실패
  - H264 1.2Mbps 후보 파일 1.38MB, 중앙값 1.678초
- 지속 worker는 계획의 이벤트별 subprocess 성능 게이트 실패 후에만 추가함
- 오프라인 회귀에서 per-event/persistent 성공, 오류, timeout 강제종료,
  임시파일 정리, 같은 PID 재사용, mp4v 선택을 검증함

2차 검수에서는 현재 파일을 다시 읽고, 1차 결과의 오래된 pipeline 지적을
그대로 반복하지 말고 반영 여부를 실제 코드와 위 실기 증거로 판정한다.

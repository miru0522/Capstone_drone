## 1. 확인된 선행조건

### 1-1. `nvargus-daemon`이 완전히 기동돼 있어야 한다 (신규 발견, 가장 중요)

**증상**: `main.py`/`testermain.py` 시작 시 다음 중 하나로 카메라 초기화 실패
```
# 패턴 A — 데몬 소켓이 아직 없음 (주로 재부팅 직후)
(Argus) Error FileOperationFailed: Connecting to nvargus-daemon failed: No such file or directory
(Argus) Error FileOperationFailed: Cannot create camera provider

# 패턴 B — 데몬이 내부 에러 루프 상태 (주로 카메라 세션을 반복 열고 닫은 후)
NvMapMemAllocInternalTagged: ... error 12
(Argus) Error InsufficientMemory: (initialize(), copyToNvBuffer())
gstnvarguscamerasrc.cpp, threadFunction:242 (propagating)
```

**근거**:
- `systemctl status nvargus-daemon`으로 실시간 확인한 결과, 위 두 에러가 발생한 시각과 데몬 상태 전환(비활성→활성, 또는 `journalctl -u nvargus-daemon`의 대량 에러 로그 폭증 구간)이 정확히 일치했다.
- 웹 검색으로 NVIDIA 개발자포럼·GitHub 이슈에서 동일 증상과 원인을 확인함:
  - [Nvarguscamerasrc InsufficientMemory: Unable to initialize EGL - Jetson Orin NX](https://forums.developer.nvidia.com/t/nvarguscamerasrc-insufficientmemory-unable-to-initialize-egl/327198) — "InsufficientMemory"는 실제 메모리 부족이 아니라 EGL/카메라 초기화 실패 전반에 붙는 포괄적 에러 메시지.
  - [nvargus-daemon going into an endless error loop (OE4T/meta-tegra #943)](https://github.com/OE4T/meta-tegra/issues/943) — 카메라 에러 발생 시 데몬이 스스로 복구 못 하고 내부 에러 루프에 빠질 수 있음. 표준 대응은 `sudo systemctl restart nvargus-daemon`.

**일반 시스템 메모리(`MemAvailable`)와는 무관함을 실측으로 확인**: 지속부하 테스트(카메라+하드웨어인코더 12분 36초 연속, 30회 투입, 35회 트리거) 동안 `MemAvailable`이 1.46~1.89GB 범위로 안정적이었음에도 문제가 없었던 반면, `MemAvailable`이 5GB 이상으로 넉넉했던 시점에도 이 에러가 발생했다. 즉 **일반 RAM 여유가 아니라 `nvargus-daemon`의 준비 상태·내부 에러 상태가 핵심 변수**다.

**필요한 선행조건**:
1. (재부팅 직후) `nvargus-daemon`이 활성 상태(`systemctl is-active nvargus-daemon` = `active`)가 될 때까지 대기한 뒤 `main.py`를 시작해야 한다. 재부팅 직후 즉시 `start_all.sh`를 돌리면 데몬 소켓이 아직 없어 실패할 수 있다(이번에 실제로 재현됨).
2. (카메라를 반복적으로 여닫은 직후 — 테스트 등) 카메라 초기화가 실패하면, `main.py`만 재시도하지 말고 **`nvargus-daemon` 자체를 재시작**(`sudo systemctl restart nvargus-daemon`)한 뒤 재시도하는 편이 더 근본적인 해결책일 수 있다. 이번 세션에서는 `main.py` 재시도만으로 결국 성공했으나(1~3회 시도), 매번 성공을 보장하지 않는다.

### 1-2. 일반 메모리 회복 대기 (보조적, 필수는 아님으로 확인됨)

프로세스 교체(예: `main.py` ↔ `testermain.py`) 시 `/proc/meminfo`의 `MemAvailable`이 일정 수준(예: 1.5GB) 이상 회복된 뒤 다음 프로세스를 시작하는 것은 안전 마진으로는 유효하나, **이것만으로는 위 1-1의 데몬 타이밍 문제를 막지 못함**을 실측으로 확인했다(메모리가 5GB 이상이어도 실패한 사례 있음). 즉 1-1과 함께 봐야지, 이것만으로 충분하다고 판단하면 안 된다.

### 1-3. 기존에 이미 알려져 있던 조건 (재확인, 변경 없음)

- 카메라 이중 점유 금지: `main.py`가 CSI 카메라를 쓰는 동안 다른 카메라 런타임을 동시에 실행하지 않는다(CLAUDE.md 3장 기존 규칙, 이번 조사와 무관하게 유효).
- `main.py` 내부에서는 이미 "카메라 세션을 모델 로드보다 먼저 확보"하는 순서로 짜여 있다(Xavier NX 통합 메모리 특성 대응, 기존 구현). 이건 **같은 프로세스 안**의 로드 순서 문제이고, 이번에 발견한 1-1은 **프로세스/데몬 간** 타이밍 문제로 서로 다른 층위다.

## 2. 제안하는 반영 방향 (구현은 별도 승인 필요, 여기선 방향만 기록)

`start_all.sh`/`restart_component.sh`가 `main.py`(또는 카메라를 쓰는 프로세스)를 시작하기 전에:

1. `systemctl is-active nvargus-daemon`을 확인하고, `active`가 아니면 활성화될 때까지 폴링(타임아웃 포함)
2. 카메라 초기화가 실패하면(`main.py`가 `RuntimeError`로 종료하는 패턴), 단순 재시도 전에 `nvargus-daemon` 상태를 다시 확인하고 필요시 데몬 재시작을 고려하는 재시도 로직 추가
3. 이 데몬 재시작은 시스템 서비스 재시작이라 카메라를 쓰는 다른 프로세스에도 영향 — 이번 프로젝트에선 `main.py`가 유일한 카메라 사용자이므로 영향 범위는 제한적이지만, 향후 다른 카메라 사용자가 생기면 재검토 필요

**완료 기준(다음 구현자 참고)**: 재부팅 직후 즉시 `start_all.sh` 실행 시 카메라 초기화 실패 없이 1회 시도로 정상 기동되는지, 그리고 카메라를 여러 번 반복해서 여닫은 뒤에도(테스트 시나리오) 동일하게 안정적으로 재기동되는지 확인.

## 3. 오늘 세션에서 실측으로 확인한 사실 요약 (참고용)

| 시나리오 | 결과 |
|---|---|
| 카메라+HW인코더 30회 연속 투입(12분 36초, 재시작 없음) | 문제 없음(35트리거, 21업로드 성공, 인코딩 오류 0) |
| `main.py`↔`testermain.py` 프로세스 교체(메모리 회복 확인 후) | 실패 1회, 성공 1회 — 메모리와 무관하게 간헐적 |
| 재부팅 직후 `start_all.sh` 즉시 실행 | 실패(데몬 소켓 없음) → `main.py`만 재시도 후 성공 |

**결론**: 문제는 카메라+GPU 동시 부하(지속 운용)가 아니라, **카메라 세션을 새로 여는 시점**(프로세스 재시작·재부팅 직후)에 `nvargus-daemon`의 준비 상태와 맞물린 타이밍 문제다.

# H264 하드웨어 인코더 구현 세션 정리

## 결과

H264 운영 후보 코드를 `main` 스냅샷에 구현하고 Jetson `/tmp`에서 실제
`nvv4l2h264enc`까지 검증했다. **Jetson 운영 코드에는 아직 배포하지 않았고,
기본 설정도 `CLIP_ENCODER=mp4v`라 현재 동작은 바뀌지 않는다.**

Claude 2차 검수는 코드 MUST 0건으로 조건부 승인했다. 운영 전환은 성능·내구성·
서버 판정 품질 게이트를 통과해야 한다.

## 구현

- `uploader.py`
  - `CLIP_ENCODER=mp4v|h264` 설정 선택
  - 이벤트별/지속 H264 worker 모드
  - 전체 deadline과 프로세스 그룹 강제 종료
  - raw 공간 사전 확인, partial 출력 검증 후 원자 rename
  - 연속 실패 2회 시 `rollback_recommended` 상태 기록
  - 이벤트별 mp4v 자동 fallback 없음
- `h264_encoder_worker.py`
  - 검증된 PyGObject/GStreamer pipeline
  - `PR_SET_PDEATHSIG(SIGTERM)` 고아 방지
  - 지속 worker JSON 요청/원자 response 파일
- `main.py`
  - 시작 로그에 실제 clip encoder 표시
- 회귀 검사
  - per-event/persistent 성공·실패·timeout·정리·PID 재사용·mp4v 선택

## 검증

- Python AST 및 Jetson `py_compile` 통과
- 업로드 기동 로그 계약 4건 통과
- Jetson H264 MP4 판독: Quicktime, H.264 Constrained Baseline, seekable
- 부모 종료 후 worker 자동 종료 통과
- 부모→worker→상태 파일 통합 통과
- 동일 실제 81프레임 3회 비교
  - per-event: mp4v 중앙값 1.881초, H264 2.092초 — 실패
  - persistent 4Mbps: mp4v 1.943초, H264 1.673초
  - persistent 1.2Mbps: mp4v 1.951초, H264 1.678초
  - 파일 크기: mp4v 1.32MB, H264 4Mbps 4.61MB, H264 1.2Mbps 1.38MB

3회 결과는 p95 승인 근거가 아니다. 4Mbps는 파일이 커 실제 서버 도착 지연에
불리하며, 1.2Mbps는 서버 판정 품질을 확인하기 전에는 운영값으로 채택하지 않는다.

H264 교체를 중단하고 mp4v를 유지한다.

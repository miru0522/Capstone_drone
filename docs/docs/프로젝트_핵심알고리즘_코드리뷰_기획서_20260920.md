## 4. 트랙별 상세 리뷰 계획

## 4.1 R1 — Jetson 영상 입력과 VadCLIP/TensorRT

### 정적 리뷰 질문

1. CSI BGR 프레임의 dtype, 채널 순서, 해상도가 CLIP 전처리 기대값과 일치하는가?
2. 9 FPS의 48-frame window에서 `[0, 5, 10, 14, 19, 24, 29, 34, 38, 43]`을 선택하는 방식이 30 FPS·stride 16 학습 조건의 시간 위치와 일치하는가?
3. 마지막 약 0.45초가 표본에 포함되지 않는 효과가 이상 recall에 영향을 주지 않는가?
4. crop index `5`, 10개 snippet, 512차원 feature, 256 길이 rolling buffer가 학습·검증 조건과 같은가?
5. 유효 길이 masking과 zero padding이 모델 head의 attention/temporal 연산과 일치하는가?
6. 최종 score가 최근 10개 확률의 top-3 평균인 근거가 있으며 다른 집계보다 안정적인가?
7. warmup이 feature history를 완전히 초기화하며 첫 실제 판정에 더미 feature가 남지 않는가?
8. NaN/Inf, shape, dtype, 잘못된 엔진 profile이 명확한 실패로 처리되는가?

### 동적 검증

- 동일 프레임 10개에 대해 PyTorch CLIP feature와 TensorRT feature 비교
- 코사인 유사도, MAE, 최대 절대 오차, 최종 score 오차 측정
- 검정·단색·노이즈·정상 순찰·급격한 움직임·실제 이상 클립을 포함
- cold start, warm start, buffer 0/10/250/256, wrap-around 경계 비교
- 같은 입력을 반복했을 때 결과가 재현되는지 확인
- TensorRT 엔진을 다른 장치/버전에서 사용할 때 발생하는 경고를 별도 위험으로 기록

### 합격 기준

- shape/dtype/시간 매핑이 문서화된 모델 계약과 일치
- PyTorch↔TensorRT 차이가 사전에 합의한 허용 오차 이내
- feature buffer 경계와 warmup 오염 없음
- 비정상 수치가 정상 점수로 조용히 변환되지 않음

수치 허용 오차는 현재 parity 데이터 분포를 먼저 측정한 후 고정한다. 근거 없이 임의의 숫자를 합격선으로 정하지 않는다.

## 4.2 R2 — 이상 트리거와 비동기 업로드

### 정적 리뷰 질문

- `ANOMALY_THRESHOLD=0.4073`의 출처와 운영 적합성
- 5.33초 추론 간격과 9초 cooldown이 만드는 최소·최대 탐지 지연
- threshold 경계에서 float 비교와 score clipping의 영향
- trigger 시 ring buffer 9초 영상이 실제 이상 전후 구간을 충분히 포함하는지
- 업로드 슬롯이 찬 상황에서 새 이상 이벤트를 버리는 정책이 요구사항과 일치하는지
- snapshot 축소가 메모리를 줄이면서 서버 분류 정확도를 훼손하지 않는지
- 서버 180초 응답 대기 중에도 추론·캡처가 계속되는지
- `None`, 실제 `0.0`, 일반 score가 각각 올바른 multipart 계약으로 전송되는지
- hover 요청이 업로드 성공 여부와 무관하게 안전한 순서로 발생하는지

### 시험 시나리오

1. threshold 바로 아래·같음·바로 위 score
2. cooldown 시작·경계·종료 시점의 연속 이벤트
3. 업로드 200/4xx/5xx/timeout/연결 끊김
4. 업로드 중 두 번째 이상 발생
5. 빈 snapshot, 인코더 실패, 임시 파일 삭제 실패
6. `None`, `0.0`, `0.4073`, `1.0` 점수
7. 30분 이상 정상·이상 교차 입력에서 이벤트 수와 예상 수 대조

### 합격 기준

- 동일 입력과 시간축에서 이벤트 생성 결과가 결정적
- 중복 억제와 누락 정책이 명시돼 있고 로그로 추적 가능
- 업로드 지연이 VadCLIP 판정을 멈추지 않음
- 점수·영상·드론 ID가 하나의 이벤트로 일관되게 결합됨

## 4.3 R3 — 비행 상태와 안전 알고리즘

### 검증할 불변조건

1. 비행 상태를 실제로 변경하는 MAVSDK 호출의 소유자는 `command_receiver.py` 하나다.
2. `LAND`, `EMERGENCY_STOP`, `PAUSE_PATROL`, `CANCEL_PATROL`은 진행 중 일반 명령을 선점한다.
3. 취소된 START/RESUME/RETURN 작업은 이후 arm·takeoff·mission start를 계속하지 않는다.
4. hover 성공과 `PAUSED` 상태 확정이 같은 요청 ID에 연결된다.
5. `LANDING`, `BATTERY_RTL`, 안전 복구 중에는 충돌 명령을 허용하지 않는다.
6. 프로세스 재시작 후 실제 `armed/in_air`와 로컬 상태가 모순되지 않는다.
7. AGL 경로 고도가 홈 기준 상대고도로 올바르게 변환되고 범위 오류를 거부한다.
8. 경로 변경 후 과거 resume index를 새 경로에 적용하지 않는다.
9. 배터리 값이 무효·미확정이면 정상 값처럼 RTL 판단에 사용하지 않는다.
10. 상태 파일은 동시 접근 중에도 부분 JSON이나 과거 요청 덮어쓰기를 노출하지 않는다.

### 검증 단계

- 1단계: 상태 머신과 command generation을 표로 모델링
- 2단계: `129_safety_regression_offline.py` 보강 및 fault injection
- 3단계: MAVSDK MOCK으로 명령 경쟁·timeout·취소 테스트
- 4단계: 프로펠러 분리 지상 통합 시험
- 5단계: 비행팀·관제팀 승인 후 제한된 실제 시험

실제 hover, 저전압 RTL, arm/takeoff 시험은 이 문서만으로 승인된 것으로 간주하지 않는다.

## 4.4 R4 — 서버 VideoMAE·VLM·TTS

### VideoMAE 계층 분류

현재 `app.py` 설명 기준으로 1차 binary 정상/이상 분기 후 이상 subclass를 분류하는 5-class 구조다.

리뷰 항목:

- binary와 subclass checkpoint의 클래스 순서·라벨 맵
- 영상 decode, frame 수, sampling stride, resize/crop, normalization
- binary confidence와 subclass confidence를 최종 `confidence`로 만드는 방식
- 정상/폭력/응급/절도/배회·침입의 category ID 일관성
- binary 오판 시 subclass가 실행되지 않는 구조의 누적 recall 손실
- 짧은 영상·가변 FPS·깨진 영상·빈 영상 처리
- softmax/logit, mixed precision, device 이동, deterministic 설정
- confidence calibration과 클래스별 threshold 필요성

### VLM과 TTS

- VideoMAE 라벨을 무조건 확정 사실로 주입할 때 설명이 잘못된 분류를 과도하게 단정하는지
- 영상에서 보이지 않는 세부 내용을 만들지 않도록 프롬프트와 결과 검증이 충분한지
- section parser가 누락·중복·형식 변형에 안전한지
- 정상 분기에서 VLM/TTS 생략이 제품 요구사항과 일치하는지
- VLM 실패와 TTS 실패가 이벤트 전체 손실로 이어지는지, 부분 결과 보존 정책이 있는지
- GPU 단일 lock에서 VideoMAE·VLM·TTS 직렬화가 처리량 요구를 만족하는지

### 합격 기준

- 클래스·전처리·confidence 의미가 학습 설정과 코드에서 일치
- 실패 입력이 잘못된 정상 이벤트로 저장되지 않음
- VLM/TTS 실패 시 분류 결과와 영상의 보존 정책이 명확함
- 동일 입력의 분류가 재현 가능하고 클래스별 성능이 목표를 충족

## 4.5 R5 — 점수·라벨 데이터 계약

다음 필드의 타입, 범위, null 의미, 이름 변환을 끝까지 추적한다.

| 의미 | Jetson/AI 서버 | Spring Boot/화면 | 확인 사항 |
|---|---|---|---|
| 1차 점수 | `anomaly_score` → `vadScore` | `firstAnomalyScore` | 없음과 실제 0.0 구분, 0~1 범위 |
| 2차 점수 | `maeConfidence` | `secondAnomalyScore` | 계층 분류에서 confidence의 정확한 의미 |
| 분류 라벨 | `category`, `categoryId`, `label` | `secondClassificationResult` | 클래스 이름·ID 고정 |
| 이벤트 등급 | `type=CRITICAL|INFO` | 상태·알림 표시 | 정상/이상 분기와 일치 |
| 설명/TTS | `description`, `ttsText` | 상세·승인·방송 | 실패 시 null/대체값 정책 |

특히 `eventData`가 모델 결과를 override할 수 있는 경로는 MOCK 전용인지 운영에서도 허용되는지 확인하고, 출처가 다른 값이 조용히 덮어써지지 않도록 계약을 검토한다.

계약 테스트는 한 컴포넌트의 단위 테스트로 끝내지 않고 실제 JSON/multipart 예제를 고정해 Python·Java·React가 같은 fixture를 사용하도록 한다.

- 이상 발생부터 score, hover 요청, 업로드 시작, 서버 응답, 관제 표시까지 단계별 시간
- Jetson RSS, GPU/통합 메모리, 온도, 전력 모드
- 서버 GPU 메모리, 요청 대기시간, 동시 요청 처리량
- MP4 인코딩 시간·크기·업로드 재시도 수
- 1시간·4시간·8시간 실행 중 메모리 증가율과 오류 수

### 복구 시나리오

- CSI/Argus 초기화 실패와 `InsufficientMemory`
- TensorRT 엔진 load 실패·CUDA OOM

## 5. 평가 데이터와 정량 지표

## 5.1 데이터 구성

1. 공개 검증 데이터: 기존 UCF-Crime/AIHub 평가 자산
2. 드론 실환경 정상 데이터: 고도·속도·밝기·그림자·카메라 흔들림·사람 밀집도별
3. 드론 실환경 이상 데이터: 폭력·응급·절도·배회/침입의 대표 시나리오
4. 경계·오류 데이터: 빈 영상, 매우 짧은 영상, 저조도, 역광, 블러, 프레임 손실, 깨진 컨테이너

같은 촬영 세션의 인접 구간이 train/calibration/test에 나뉘어 들어가지 않도록 촬영일·장소·시나리오 단위로 분리한다.

## 5.2 1차 VadCLIP 지표

- AUROC, AUPRC
- threshold별 precision, recall, F1, false positive rate
- 정상 순찰 시간당 오탐 횟수
- 이상 구간별 miss rate와 time-to-detect
- 장면·조도·고도·움직임별 성능 분해
- PyTorch↔TensorRT score 오차 분포

`0.4073`은 UCF-Crime 기반 임시값이므로 실환경 validation set에서 목표 recall과 허용 오탐률을 먼저 합의한 후 새 임계값을 선택한다. test set은 임계값 선택에 사용하지 않는다.

## 5.3 2차 VideoMAE 지표

- binary 정상/이상: recall, specificity, AUROC, AUPRC
- 5-class: confusion matrix, macro/weighted F1, 클래스별 precision·recall
- confidence calibration: reliability diagram, ECE 또는 Brier score
- binary→subclass 계층 전체의 end-to-end 클래스 recall

## 5.4 전체 시스템 지표

- 실제 이상 사건 기준 최종 관제 표시 recall
- 이벤트 중복률과 누락률
- 1차 trigger부터 관제 표시까지 p50/p95 latency
- 영상·점수·라벨·설명·TTS 완전 수신율
- hover 요청 성공률은 MOCK과 실제 시험 결과를 구분해 기록

각 발견 사항은 다음 형식으로 기록한다.

- ID와 심각도

## 7. 심각도와 처리 기준

## 11. 착수 시 우선 확인할 공개 이슈

1. `ANOMALY_THRESHOLD=0.4073`은 드론 실데이터 calibration 전 임시값이다.
2. 실제 Pixhawk hover 경로는 현재까지 승인된 실기 검증이 없다.
3. 배터리 `remaining_percent=-1.0` 문제와 단위 정책이 미확정이다.
4. VideoMAE 핵심 추론 파일이 Git 스냅샷 밖에 있어 배포본 확보가 필요하다.
5. VadCLIP 원본 모델 모듈도 `/home/hpc/edge_vadclip_2026` 외부 경로에 의존한다.
6. 다음 실제 이상 트리거에서 1차 점수의 관제 표시 E2E 확인이 남아 있다.
7. main 재기동 중 Argus `InsufficientMemory`가 한 차례 발생했으므로 재현 조건과 메모리 여유를 R6에서 확인한다.

착수 순서는 외부 소스 기준선 확보 → 데이터 흐름과 상태 머신 작성 → Jetson·서버 정적 리뷰 → 오프라인 자동 검증 순으로 한다. 실기 안전 시험은 마지막 승인 단계로 분리한다.

## 검수 항목

### 1. 지연시간 판정

- 원시 결과 `docs/docs/h264_600_acceptance_results_20260927/results.jsonl`에서 다음 단축 시간이 재계산되는지 확인:
  - 전체 p50 0.426초, p95 0.739초
  - 참조 A p50 0.264초, p95 0.278초
  - 참조 B p50 0.463초, p95 0.408초
- 새로운 0.1초 절대 단축 기준에서 H264 600 kbps를 통과로 판정한 것이 수치상 맞는지 확인
- 일부 개별 영상에서 H264가 느렸다는 결과가 운영 채택을 막는 수준인지 별도로 평가

### 2. PSNR/SSIM 구현과 판정

- `pixel_quality_600.py`의 프레임 대응, 리사이즈, 디코딩 수 검증, PSNR 및 11×11 Gaussian SSIM 계산이 올바른지 확인
- mp4v와 H264가 정확히 같은 81개 원본 프레임을 사용했는지 확인
- 결과 재계산:
  - H264 평균 PSNR 36.3563 dB
  - H264 평균 SSIM 0.95575
  - H264 영상별 PSNR 30 dB 이상 30/30
  - H264 영상별 SSIM 0.95 이상 23/30
  - mp4v 영상별 SSIM 0.95 이상 27/30
  - 평균 파일 크기 45.67% 감소
- 현재 문서가 **데이터셋 전체 평균 gate**로 PSNR≥30 dB, SSIM≥0.95를 통과 처리한 것이 타당한지 검토
- H264의 최저 영상 평균 SSIM 0.8563과 7/30 미달을 운영 차단 조건으로 봐야 하는지 명확히 판정

### 3. 후보 코드 정합성

- `baseline/uploader.py`에서 `candidate/uploader.py`로 바뀌는 전체 diff를 검토해 H264 외 동작 변화가 무엇인지 분류
- `candidate/uploader.py`와 `candidate/h264_encoder_worker.py`의 persistent worker, timeout, cleanup, 부모 종료 신호, `/dev/shm` 용량 검사, 상태 기록, mp4v 롤백 선택 경로 검토
- 운영 `main.py`가 후보 uploader의 기존 공개 인터페이스와 호환되는지 확인
- `UPLOAD_MODE=B`에서 `anomaly_score=None`일 때 키 생략, 실제 `0.0` 보존이 유지되는지 확인
- `maxperf-enable=true`를 제외한 것이 0.1초 기준과 현재 시험 결과에 비춰 타당한지 확인

### 4. 배포 설정과 안전성

- `start_all.sh`와 `restart_component.sh`의 다음 기본값이 정확히 적용되는지 확인:
  - `CLIP_ENCODER=h264`
  - `H264_BITRATE=600000`
  - 기존 외부 환경변수로 override 가능
- 이 환경변수가 `command_receiver`나 `telemetry_sender`에도 전달되는 부작용이 있는지 검토
- 실제 교체 순서가 운영 파일 백업 → 후보 반영 → 문법/diff 검사 → Jetson 커밋·push → `restart_component.sh main`만 실행하는지 확인
- 롤백 명령 `CLIP_ENCODER=mp4v ./restart_component.sh main`이 시작 스크립트 기본값보다 우선하며 실제로 mp4v로 돌아가는지 확인
- 전체 `start_all.sh`, `pkill python3`, `dae_*` 종료 없이 복구 가능한지 확인

### 5. 번들 무결성 및 누락

- `manifest.json`의 SHA-256이 baseline/candidate 실제 파일과 일치하는지 확인
- `cutover_preflight.sh`가 운영 파일을 수정하지 않는지 확인
- 교체 직전에 추가로 반드시 해야 할 검사가 있는지 확인
- 첫 실제 트리거 검증 전에 운영 배포를 막아야 할 MUST 이슈가 있는지 확인

## 1. 담당 영역 개요

- **담당 영역**: 드론 탑재 컴퓨터(Jetson Xavier NX) — 실시간 카메라 캡처, 1차 이상탐지(엣지 AI), 비행 명령 수신·실행, 텔레메트리 송신, 영상 스트리밍/업로드
- **담당 기능**: CSI 카메라 캡처 파이프라인, VadCLIP(TensorRT) 기반 엣지 이상탐지, 이상탐지 트리거→호버링→영상업로드 파이프라인, STOMP 기반 비행 명령 수신·MAVSDK 비행 제어, 배터리 자율복귀 페일세이프, 실시간 스트리밍(요청 기반), 텔레메트리 송신
- **사용 기술**: Python 3.8, OpenCV+GStreamer(CSI 카메라), PyTorch+TensorRT(VadCLIP 추론), MAVSDK-Python(PX4 비행 제어), `stomp.py`+`websocket-client`(STOMP over WebSocket), `requests`(HTTP 업로드), asyncio+threading(비동기/동시성)
- **전체 시스템에서 담당 영역의 역할**: 실제 비행체에 탑재되어 (1) 카메라로 주변을 실시간 감시하고 (2) 엣지에서 1차로 이상 여부를 판단해 관제 서버에 불필요한 트래픽을 걸러내며 (3) 관제 서버가 내리는 비행 명령을 실제 PX4 비행 컨트롤러(Pixhawk)에 실행하는, **시스템의 최종 실행 계층**
- **다른 파트와 연결되는 부분**:
  ```
  웹 프론트엔드 → Spring Boot 백엔드(STOMP) → Jetson(command_receiver.py) → MAVSDK → Pixhawk(PX4) → 드론
  드론 카메라 → Jetson(main.py, VadCLIP) → [트리거 시] HTTP 업로드 → FastAPI AI서버(VideoMAE) → 백엔드 → 프론트엔드
  Jetson(telemetry_sender.py) → STOMP → 백엔드 → 프론트엔드(실시간 상태 표시)
  ```

## 2. 전체 구현 기능 목록 (드론/Jetson)

### 2-1. CSI 카메라 실시간 캡처

**기능 목적**: 드론 주변을 지속적으로 촬영해 이상탐지·스트리밍의 입력 데이터 확보

**구현 상태**: 구현 완료

**구현 방법**: GStreamer 파이프라인(`nvarguscamerasrc` → `nvvidconv` → `videoconvert`, sensor-mode=2, 1920×1080) 을 OpenCV `cv2.VideoCapture(pipeline, cv2.CAP_GSTREAMER)`로 오픈. 목표 9fps로 캡처 루프가 자체 페이싱(`frame_interval = 1.0/FPS`)하며 프레임 처리 지연을 진단 로그로 매초 기록. 모델(VadCLIP) 로드보다 카메라 세션을 먼저 확보해야 하는 제약(Xavier NX 통합메모리에서 모델이 먼저 메모리를 점유하면 CaptureSession 생성이 실패하는 실기 이슈 확인됨)이 있어, `main.py`는 카메라 초기화 → 첫 프레임 확인 → 모델 로드 순서를 강제함

**입력**: CSI 카메라 하드웨어 신호

**처리**: 프레임을 `RingBuffer`(스레드 세이프 deque, 최대 81프레임/9초)에 push. 최신 프레임은 스트리밍용으로 별도 변수에도 보관

**출력**: 초당 ~9프레임의 BGR numpy 배열 스트림

**관련 시스템**: Jetson (자체 완결, 타 시스템과 직접 통신 없음 — 다운스트림인 VadCLIP/스트리밍이 소비)

**예외 상황**: 프레임 읽기 실패(`ret=False`) 시 0.1초 대기 후 재시도(무한 재시도, 크래시 안 함). CaptureSession 자체 생성 실패 시 `RuntimeError`로 즉시 실패(모델 로드로 넘어가지 않음, main.py 전체 기동 실패)

### 2-2. 엣지 1차 이상탐지 (VadCLIP, TensorRT)

**기능 목적**: 모든 영상을 서버로 올리면 네트워크·서버 부하가 크므로, 엣지에서 1차로 "이상해 보이는" 순간만 걸러내 서버 트래픽/AI서버 연산량을 줄임

**구현 상태**: 구현 완료 (모델 자체는 완료, **threshold 보정은 미완료** — 아래 참고)

**구현 방법**:
- CLIP ViT-B/16(TensorRT 엔진화) + VadCLIP C-branch(UCF-Crime 학습, PyTorch, strict state_dict 로드) 조합
- 라이브 9fps 카메라를 VadCLIP의 학습 규약(30fps, stride 16)에 맞추기 위해, 48프레임(~5.33초) 윈도우에서 10개 대표 프레임을 간격 샘플링(index `[0,5,10,14,19,24,29,34,38,43]`)해 CLIP 특징을 추출
- 추출된 특징을 256-snippet 크기의 rolling feature buffer(`FeatureRingBuffer`)에 누적하며, 최근 10개 snippet 중 top-k(기본 3) 평균을 최종 anomaly score(0.0~1.0)로 산출
- 원래 이 자리에는 Jigsaw-VAD/WideBranchNet(YOLOv5n+TensorRT)이 있었으나 2026-08-31 VadCLIP으로 전면 교체(모듈형 설계 — 외부 인터페이스 `AnomalyPipeline.compute_score(window)`는 유지한 채 내부만 교체), 이후 2026-09-06~07 TensorRT 최적화(`anomaly_model_trt.py`/`vadclip_adapter_trt.py`) 적용
- 카메라 캡처 루프와 완전히 분리된 별도 워커 스레드(queue 기반, maxsize=1 — 밀리면 오래된 window를 버리고 최신 window로 교체)에서 추론 실행, 48프레임(약 5.33초)마다 1회

**입력**: `(48, H, W, 3)` uint8 BGR numpy 배열(라이브 캡처 윈도우)

**처리**: 대표 프레임 추출 → CLIP 특징 추출(TensorRT) → feature buffer 누적 → VadCLIP C-branch 추론(PyTorch, CUDA) → top-k 평균

**출력**: anomaly_score(float, 0.0~1.0)

**관련 시스템**: Jetson 내부 완결 (모델 추론 자체는 서버와 무관, 결과가 threshold를 넘을 때만 서버로 업로드 트리거)

**예외 상황**: 추론 중 예외 발생 시 fail-safe로 0.0(정상)을 반환해 오탐/불필요한 호버링을 막음. 단, 연속 10회 이상 실패 시 `critical` 레벨 경고 로그를 남겨 운영자가 엔진/GPU 이상을 인지할 수 있게 함(무한히 조용히 실패하는 것을 방지)

**⚠️ 미완료 사항**: `ANOMALY_THRESHOLD=0.4073`은 UCF-Crime(공개 CCTV 데이터셋) 기준으로 잠정 설정된 값이며, 드론(항공뷰) 도메인 데이터로 재보정되지 않았습니다. 2026-09-14 실기 테스트에서 실제 폭력 상황을 담은 영상 주입 시 score 0.7~1.0으로 정상 트리거됐으나, 일부 영상(서버 2차 분류기가 "폭력"으로 판정한 것 포함)은 엣지에서 score 0.001~0.01 수준으로 전혀 반응하지 않는 경우도 확인됨 — 엣지(VadCLIP)와 서버 2차 분류기(VideoMAE)의 판단 기준이 다를 수 있음을 시사.

### 2-3. 이상탐지 트리거 → 호버링 → 영상 업로드 파이프라인

**기능 목적**: 이상 상황 발생 시 드론을 즉시 안전하게 정지시키고, 관제 서버가 추가 판단을 내릴 수 있도록 증거 영상을 전달

**구현 상태**: 구현 완료 (실기 E2E 검증 완료 — 2026-09-14, 아래 참고)

**구현 방법**:
- `_check_trigger(score)`: `score >= ANOMALY_THRESHOLD` 이고 마지막 트리거 이후 `TRIGGER_COOLDOWN_SEC`(9초) 경과 시에만 트리거 인정(중복 전송 방지)
- 트리거 시 `DroneHoverController.hover_now()` 호출 → MAVSDK `action.hold()`로 즉시 제자리 호버링(이미 호버링 중이면 중복 호출 방지 플래그 존재)
- RingBuffer 전체 스냅샷(81프레임/9초)을 960×540으로 다운스케일 후 OpenCV `mp4v`로 인코딩(원래 Jetson 하드웨어 인코더 `nvv4l2h264enc`를 썼으나 write/release 단계에서 무한 hang되는 실기 버그가 발견되어 폐기, 소프트웨어 인코더로 교체)
- 업로드는 **별도 워커 스레드+큐(maxsize=1)**로 분리(V6 구조) — 서버 응답이 최대 180초까지 걸릴 수 있어, 이를 추론 스레드에서 동기 처리하면 그동안 새 이상탐지 판정이 전부 멈추는 문제가 있어 분리. 업로드 중 새 트리거가 오면 "이미 진행 중" 로그를 남기고 스킵(드롭)

**입력**: anomaly_score(트리거 판정 결과), RingBuffer 스냅샷

**처리**: 호버링 → 다운스케일 → mp4v 인코딩 → HTTP POST(`/analyze-video`, multipart/form-data) → 서버 응답 대기(최대 180초)

**출력**: 서버 응답(JSON: 상황 판정 결과, 이벤트 ID 등), 호버링 상태 유지(재개는 관제사 명령 대기)

**관련 시스템**: Jetson → AI 서버(FastAPI) → 백엔드(Spring Boot, 이벤트 등록) → 프론트엔드(알림 표시)

**예외 상황**: 업로드 실패/무응답 시 로그만 남기고 드론은 계속 호버링 유지(별도 비행 안전조치 없음 — 관제사 명령 대기가 유일한 재개 경로). 업로드 슬롯이 이미 사용 중이면 새 트리거는 조용히 드롭됨(재시도 없음 — **알려진 한계**, 연속 이상상황 발생 시 일부 영상이 누락될 수 있음)

**✅ 실기 E2E 검증 완료 (2026-09-14)**: 실제 폭력 상황이 담긴 영상을 카메라 캡처 루프에 실시간 주입(자체 개발한 `TestVideoInjector` 사용)하여, VadCLIP score 상승 → 트리거 → MAVSDK `action.hold()` 실제 호출 → mp4v 인코딩 → 업로드 → AI서버 VideoMAE 분석("폭력"/"배회·침입" 판정) → 백엔드 이벤트 등록(event ID 289~296)까지 **전체 파이프라인을 실제 하드웨어(Pixhawk 연결 상태)로 6회 반복 검증** 완료.

### 2-4. STOMP 기반 비행 명령 수신 및 MAVSDK 비행 제어

**기능 목적**: 관제 서버(프론트엔드 조작)로부터 비행 명령을 실시간으로 받아 실제 드론을 제어

**구현 상태**: 구현 완료

**구현 방법**:
- `stomp.py` 라이브러리로 백엔드의 STOMP 브로커(`/ws`, SockJS 아님, 순수 WebSocket)에 연결, 드론별 전용 채널(`/topic/drones/{droneId}/commands`) 구독
- STOMP CONNECT 프레임에 `X-Device-Key` 헤더로 인증(서버 `DeviceKeyFilter`가 검증)
- 수신한 JSON 명령의 `action` 필드로 10종 명령 분기: `START_PATROL`, `RESUME_PATROL`, `PAUSE_PATROL`, `CANCEL_PATROL`, `RETURN_TO_STATION`, `LAND`, `EMERGENCY_STOP`, `SET_ROUTE`, `SET_STATION`, `PLAY_AUDIO`(+ `REQUEST_STREAM`/`STOP_STREAM`)
- 각 명령은 asyncio 코루틴으로 MAVSDK System 객체(공유 `mavsdk_server`, gRPC localhost:50051)를 통해 실제 비행 명령으로 변환
- 내부 상태머신(`IDLE/PATROLLING/PAUSED/RETURNING/LANDING`)을 유지하며, 상태에 맞지 않는 명령은 무시(예: 이미 순찰 중인데 START_PATROL 재수신 시 무시)
- 순찰 경로(waypoint 목록)는 `SET_ROUTE`로 미리 저장만 해두고, 실제 비행은 `START_PATROL`/`RESUME_PATROL`이 별도로 트리거(경로 설정과 비행 시작을 분리)

**입력**: STOMP 메시지(JSON: `{action, droneId, route?, station?, ...}`)

**처리**: 메시지 파싱 → droneId 검증(자기 채널 전용이라 원칙적으로 불필요하나 이중 확인) → 상태 검증 → MAVSDK 명령 실행 → 내부 상태 갱신 → 상태 공유 파일 기록

**출력**: 실제 비행 동작(이륙/호버링/착륙/경로비행/모터정지), 상태 공유 파일(`/tmp/drone_status_state.json`) 갱신 → `telemetry_sender.py`가 읽어 서버로 전송

**관련 시스템**: 백엔드(Spring Boot, STOMP 발신) ↔ Jetson(`command_receiver.py`) ↔ Pixhawk(MAVSDK)

**예외 상황**:
- STOMP 연결 끊김: 5초 후 자동 재연결(무한 루프)
- MAVSDK 명령 타임아웃(15초, `EMERGENCY_STOP`은 5초): 타임아웃 로그 남기고 다음 명령 대기(재시도 안 함)
- `SET_ROUTE` 없이 `START_PATROL` 수신 시(경로 비어있음): 순찰이 아닌 "제자리 이륙"만 수행하며 경고 로그로 명시(과거 실기에서 이 케이스로 2m 저고도 호버링만 지속된 사례가 있어 진단 강화됨)

### 2-5. 배터리 자율복귀 페일세이프

**기능 목적**: 서버/통신과 무관하게, 배터리 부족 시 드론이 스스로 안전하게 복귀하도록 보장

**구현 상태**: 구현 완료

**구현 방법**: `command_receiver.py`가 MAVSDK 배터리 텔레메트리 스트림을 상시 구독하는 별도 asyncio 태스크(STOMP 연결/서버 통신 상태와 무관하게 동작 — 서버팀 요청사항 "통신 두절 중에도 페일세이프는 동작해야 한다"를 만족시키기 위한 설계). 배터리가 `BATTERY_RTL_THRESHOLD_PERCENT`(기본 40%) 이하이고 비행 중(`IDLE`/`LANDING` 아님)이면 1회만 자율복귀 트리거

**입력**: MAVSDK `telemetry.battery()` 스트림

**처리**: 임계값 비교 → SET_STATION으로 저장된 스테이션 좌표로 비행 → 도착 감지 → **착륙까지 자동 수행**(일반 `RETURN_TO_STATION`은 도착 후 호버링만 하고 착륙 안 함 — 배터리 자율복귀는 나머지 배터리로 계속 대기하다 추락하는 것을 막기 위해 반드시 착륙까지 진행하도록 구분)

**출력**: 자율 복귀 비행 + 착륙

**관련 시스템**: Jetson 내부 완결(서버 개입 불필요, 단 상태 공유 파일을 통해 결과는 텔레메트리로 서버에 보고됨)

**예외 상황**: 스테이션 좌표(`SET_STATION`)가 아직 설정 안 된 경우 복귀 불가 — 즉시 `action.hold()`(제자리 정지)만 시도하고 에러 로그 남김(추락 방지를 위한 최소 안전조치)

### 2-6. 텔레메트리 송신

**기능 목적**: 드론의 실시간 상태(위치, 배터리, 비행상태)를 관제 서버/프론트엔드에 지속 전달

**구현 상태**: 구현 완료

**구현 방법**: `telemetry_sender.py`가 `command_receiver.py`와는 별도의 독립 STOMP 연결(같은 커넥션을 프로세스 간 공유 불가하므로)로 `/app/telemetry`에 1초 주기로 SEND. MAVSDK로 GPS(`position()`)·배터리(`battery()`) 스트림 구독, `command_receiver.py`가 남기는 상태 공유 파일(`status`, `currentAction`, `hasRoute`, `hasStation`)을 읽어 병합

**입력**: MAVSDK 텔레메트리 스트림 + 상태 공유 파일

**처리**: 1초마다 payload 조립(`droneId, status, currentAction, hasRoute, hasStation, gps{lat,lon,alt}, battery{remaining_percent}`) → STOMP SEND

**출력**: STOMP 메시지 → 백엔드 → 프론트엔드 실시간 갱신

**관련 시스템**: Jetson → 백엔드(STOMP) → 프론트엔드

**예외 상황**: Pixhawk 미연결(Heartbeat 없음) 시 "하드웨어 연결 대기" 로그(30초 간격, 로그 폭주 방지)만 남기고 전송 보류. STOMP 연결 끊김 시 자동 재연결 후 전송 재개

**참고(버그 수정 이력)**: MAVSDK `battery.remaining_percent`는 항상 0.0~1.0 fraction인데, 과거 "이미 0~100으로 온 경우" 방어 코드가 이중 변환을 일으켜 배터리 9900%로 표시되는 사고가 있었음(2026-07-18) — 스펙대로 항상 고정 변환(`*100.0`)하도록 수정, `command_receiver.py`의 배터리 RTL 판정 로직도 동일하게 수정

### 2-7. 요청 기반 실시간 스트리밍

**기능 목적**: 관제사가 필요할 때만 영상을 보고, 안 볼 때는 셀룰러 데이터를 쓰지 않도록 함

**구현 상태**: 구현 완료 (2026-09-12 재시작 무한루프 버그 수정 완료, 실기 재검증 완료)

**구현 방법**: 별도 프로세스(`command_receiver.py`)가 `REQUEST_STREAM`/`STOP_STREAM` STOMP 명령을 받아 신호 파일(`/tmp/drone_stream_request.json`)에 `stream_enabled` 플래그를 기록 → `main.py`의 `StreamUploader`(독립 스레드)가 1초마다 이 파일을 확인해 전송 on/off. 영상은 STOMP가 아니라 **HTTP POST**(`/drones/{droneId}/stream/frame`, 원본 JPEG 바이너리)로 전송 — STOMP에 영상을 얹으면 `EMERGENCY_STOP` 같은 제어 명령이 영상 프레임 뒤에 큐잉되어 늦게 도착하는 안전 문제가 있다는 서버팀 판단 반영. 서버 응답 규칙: `204`(계속 전송) / `410`(즉시 중지, Gone) / `401`(디바이스 키 문제, 중지) / `10초 무응답`(자체 중지)

**입력**: `REQUEST_STREAM`(streamId, uploadPath, fps, width, height, quality) / `STOP_STREAM`

**처리**: 최신 캡처 프레임 → JPEG 인코딩 → HTTP POST → 응답코드별 분기

**출력**: JPEG 프레임 스트림(HTTP)

**관련 시스템**: Jetson → 백엔드(Spring Boot, 프레임 수신 엔드포인트) → 프론트엔드(영상 표시, **구현 세부는 확인 필요**)

**예외 상황(버그 수정 완료)**: 2026-09-12 이전에는 서버가 `410`/`401`을 보내도 신호 파일 자체는 안 바뀌어 1초 뒤 재시작을 무한 반복하는 버그가 있었음(관제 로그에서 1.3~1.5초 간격으로 `410` 무한 반복 확인, 배터리/셀룰러 낭비) — `_disable_stream_state()`를 추가해 응답 코드 수신 시 신호 파일 자체를 내리도록 수정, 실기 재배포 후 정상 동작(재시작 반복 없이 1회만 중지) 확인

### 2-8. 실시간 비행 명령/텔레메트리 데이터 정합성

**기능 목적**: 서버가 알고 있는 드론 상태(예: "경로 있음")와 드론이 실제로 가진 상태가 어긋나지 않도록 보장

**구현 상태**: 구현 완료

**구현 방법**: `hasRoute`(순찰 경로 보유 여부) 필드를 텔레메트리에 추가(2026-08-26) — 과거 이 필드가 아예 전송이 안 되고 있었고 프론트엔드가 `?? true`로 낙관적 기본값 처리해 크래시는 없었지만, "경로 없을 때 재개를 막는 안전장치"가 사실상 무력화돼 있었음(2026-08-25 실기에서 2m 저고도 호버링만 지속되는 사고와 연관). `hasStation`(스테이션 좌표 보유 여부)도 동일 패턴으로 추가(2026-09-12, 백엔드팀 요청 반영)

**입력**: 드론 내부 상태(`self._route`, `self._station`)

**처리**: `bool(self._route)`, `bool(self._station)` → 상태 공유 파일 → 텔레메트리 payload

**출력**: 서버가 실제 드론 상태를 정확히 인지 → 프론트엔드 버튼 활성화 로직(예: "순찰 시작" vs "순찰 재개") 정확도 향상

**관련 시스템**: Jetson → 백엔드(Telemetry DTO) → 프론트엔드(`DroneStatus.jsx` 등)

**예외 상황**: 해당 없음(단순 상태 반영)

## 3~12. 프론트엔드/백엔드 기술 구조, API, DB, 실시간통신, AI서버 연동

> **이 부분은 제(드론/Jetson) 담당이 아니며, 실제 구현자가 아닙니다.** 이번 세션에서 소스코드
> 열람·DB 직접 조회·API 연동 테스트를 통해 **확인한 범위**에서만 작성합니다. 프론트엔드 내부

### 3. 백엔드 전체 구조 (확인된 범위)

- **사용 언어/프레임워크**: Java, Spring Boot
- **서버 구성(Docker Compose 기준, 실제 확인)**: `dae_backend`(Spring Boot, 8080), `dae_frontend`(React 정적파일 + nginx, 외부 8031), `dae_ai_server`(FastAPI, 8000), `dae_mariadb`(MariaDB 10.11), `dae_virtual_drone`(시뮬레이션용 가상 드론 컨테이너)
- **주요 모듈(컨트롤러, 실제 파일 확인)**: `DroneController`(순찰 명령 10종 엔드포인트), `StreamController`(REQUEST_STREAM/STOP_STREAM, 프레임 업로드), `EventController`(AI서버로부터 이벤트 수신, TTS 승인, 방송완료 콜백), `TelemetryController`/`TelemetryHistoryController`, `UserController`/`AdminController`, `CommandLogController`(2026-09 추가, 명령 이력 로깅)
- **인증**: `DeviceKeyFilter`가 `X-Device-Key` 헤더를 특정 POST 경로(`/events`, `/events/{id}/broadcast-complete`, `/drones/{id}/stream/frame`)에서 검증
- **리버스 프록시**: nginx(`dae_frontend` 컨테이너 내)가 외부 8031 포트로 전체 트래픽을 받아 `/ws`→backend, `/analyze-video`→ai_server, `/drones/*/stream*`→backend, REST API→backend로 라우팅. **현재 이 구간은 TLS 없이 평문 HTTP**(2026-09-10 확인)이며, nginx→backend 내부 구간만 자체서명 HTTPS(`proxy_ssl_verify off`로 검증은 꺼져있음)
- **DB 연결**: Spring Data JPA로 추정(**정확한 ORM 설정 확인 필요**), MariaDB 컨테이너에 직결

**데이터/명령 흐름(확인된 형태)**:
```
Frontend → nginx(8031) → Backend(REST API 또는 STOMP) → Jetson(command_receiver.py, STOMP)
                                                        → AI Server(HTTP, 이상탐지 결과만)
Backend ↔ MariaDB (이벤트/사용자/드론/경로 등 영속화)
```

### 6. AI 서버 연동 (실제 확인)

- Jetson `uploader.py`가 트리거 시 **81프레임(9초) 전체 클립을 mp4로 인코딩해 HTTP multipart로 통째 전송**(프레임 단위 스트리밍 아님)

    "status": "success",
    "message": "Pipeline completed",

      "type": "CRITICAL",
      "label": "배회·침입",

  ```
- AI서버가 백엔드에 이벤트를 등록하는 것까지 AI서버 자체가 수행(`backend_response` 필드로 확인 — 즉 Jetson→AI서버→백엔드 순서로, Jetson이 백엔드에 직접 이벤트를 등록하지 않음)
- 프론트엔드에 어떻게 전달되는지(알림 UI 등)는 **확인 필요**

### 7. 오류/예외 처리 (Jetson 관점에서 확인된 것만)

| `mavsdk_server` | Pixhawk 시리얼 포트 독점, gRPC(50051)로 다른 프로세스에 공유 |
| `telemetry_sender.py` | GPS/배터리/상태 → STOMP 송신 (1초 주기) |
| `command_receiver.py` | STOMP 명령 수신 → MAVSDK 비행 제어, 배터리 페일세이프 상시 감시 |
| `main.py` | 카메라 캡처 + VadCLIP 추론 + 트리거/호버링 + 영상업로드 + 스트리밍 |

프로세스 간 통신은 **파일 기반**(공유 상태 파일: `/tmp/drone_status_state.json`, `/tmp/drone_stream_request.json`) — 각자 독립 프로세스라 메모리 공유 불가, 1초 주기 폴링으로 신호 전달

## 15. 서버 ↔ 드론(Jetson) 통신 구조

- **명령 전달(서버→드론)**: STOMP over WebSocket, `/ws` 엔드포인트, 드론별 전용 채널 구독(`/topic/drones/{droneId}/commands`)
- **상태 전달(드론→서버)**: STOMP SEND `/app/telemetry`, 1초 주기
- **영상 업로드(트리거)**: HTTP POST(`/analyze-video`), multipart/form-data, 타임아웃 180초
- **영상 스트리밍**: HTTP POST(`/drones/{id}/stream/frame`), JPEG 바이너리, 요청 기반(관제사가 볼 때만)
- **인증**: STOMP CONNECT 헤더 / HTTP 헤더에 `X-Device-Key` 고정값(`HPC-2026`)
- **연결 유지**: STOMP는 연결 끊김 감지 시 5초 후 자동 재연결. HTTP 업로드는 재시도 로직 있음(최대 2회, backoff)
- **TLS**: 관제 접속 구간(8031) 자체가 현재 평문 HTTP — **TLS 미적용 상태**(2026-09-10 확인, 별도 과제로 남아있음)

## 16. Jetson ↔ Flight Controller 통신

- **프로토콜**: MAVLink(MAVSDK-Python 라이브러리로 추상화, ROS/MAVROS 미사용)
- **연결 방식**: `mavsdk_server`가 시리얼 포트(`/dev/pixhawk`)를 독점하고, 다른 프로세스는 gRPC(localhost:50051)로 공유 접속 — 여러 프로세스가 동시에 시리얼 포트를 열 수 없는 제약을 우회
- **주요 명령**: `action.arm()`, `action.takeoff()`, `action.hold()`(호버링), `action.land()`, `action.kill()`(강제 disarm), `action.return_to_launch()`(PX4 기본 RTL, 스테이션 좌표 없을 때 폴백)
- **미션(Waypoint) 비행**: `WaypointMissionController`(자체 모듈, `waypoint_mission.py`) — `upload_and_start()`로 좌표 목록을 미션으로 업로드 후 시작. 복잡한 경로계획 알고리즘은 없고 **MAVSDK 표준 waypoint 미션 기능을 그대로 사용**(직선 이동, PX4 자체 경로 유도)
- **비행 모드 변경**: 명시적 모드 전환 API 대신 `action.*` 고수준 명령 사용(PX4가 내부적으로 모드 전환 처리)
- **텔레메트리 조회**: `telemetry.battery()`, `telemetry.position()`, `telemetry.armed()`, `telemetry.in_air()`, `telemetry.connection_state()` 스트림 구독

## 17. 자율주행 (순찰)

**전체 흐름**:
```
관제사가 지도에서 경로점 지정 (Frontend, 세부 구현 확인 필요)
→ Frontend가 SET_ROUTE 관련 API 호출 (확인 필요: PUT /drones/{id}/route로 추정, DroneController.java 확인됨)
→ Backend가 STOMP로 SET_ROUTE 명령을 Jetson에 전달
→ command_receiver.py의 _set_route(route)가 좌표 목록을 self._route에 저장만 함 (비행 시작 안 함)
→ 관제사가 "순찰 시작" 버튼 클릭 → START_PATROL 명령
→ command_receiver.py._start_patrol(): 상태가 IDLE/PAUSED일 때만 수락
→ self._route가 있으면 WaypointMissionController.upload_and_start()로 MAVSDK 미션 업로드+시작
→ 상태를 PATROLLING으로 변경, 완주 감지 백그라운드 태스크 시작
→ Pixhawk(PX4)가 실제 waypoint를 따라 비행
→ 완주 시 wait_for_mission_complete() 콜백 → 상태를 PAUSED로 전환, currentAction=PATROL_COMPLETE로 텔레메트리 통지 (자동착륙 폐지 — 착륙 안 하고 호버링 유지)
```

- **좌표 데이터 형태**: `{"lat": float, "lon": float, "alt_agl": float(선택, 기본 50m)}` 객체 배열(2026-08-21 스펙, 과거 `[lat,lon]` 배열에서 변경됨)
- **목적지 도착/완주 판단**: MAVSDK 미션 진행 상태 폴링(`wait_for_mission_complete`, 구체적 폴링 로직은 `waypoint_mission.py` — **세부 알고리즘 확인 필요**, 반경 기반 도착 판정은 `RETURN_TO_STATION`/배터리RTL에서 `radius_m=5.0` 확인됨)
- **비행 중 경로 변경**: `SET_ROUTE`는 언제든 수신 가능하나 저장만 하고, 실제 반영은 재시작(`START_PATROL`/`RESUME_PATROL`)해야 함 — 비행 중 실시간 경로 변경은 **미구현**
- **장애 상황**: 경로가 비어있는데 START_PATROL 수신 시 "제자리 이륙"만 수행하고 경고 로그(§2-4 참고)
- **자율주행 종료 조건**: 경로 완주, `PAUSE_PATROL`(일시정지), `CANCEL_PATROL`(경로 초기화+호버링), `RETURN_TO_STATION`(복귀), `EMERGENCY_STOP`(강제정지) 중 하나

## 18. 긴급 착륙 / 긴급 복귀

**긴급상황 판단 조건(실제 구현된 것만)**:
- 배터리 40% 이하(자율, 통신 두절과 무관하게 상시 감시) → 자율복귀+착륙
- 관제사의 수동 `EMERGENCY_STOP` 명령 → 즉시 kill(모터 강제 차단)
- 관제사의 `LAND` 명령 → 현재 위치 하강 착륙
- **GPS 신호 상실/통신 단절 자체를 감지해 자동 긴급조치하는 로직은 미구현** — 배터리 페일세이프만 통신 두절과 무관하게 동작하고, 그 외에는 서버 개입(수동 명령) 필요

**LAND vs RETURN_TO_STATION vs EMERGENCY_STOP 구분**:
| 명령 | 동작 | 모터 | 이동 |
|---|---|---|---|
| `LAND` | 현재 위치에서 하강 착륙 | 착륙 후 자동 disarm | 없음(제자리 하강) |
| `RETURN_TO_STATION` | 스테이션 좌표로 비행, 도착 후 **호버링**(착륙 안 함) | 유지 | 있음 |
| 배터리 자율복귀(RTL) | 스테이션으로 비행, 도착 후 **착륙까지** | 착륙 후 disarm | 있음 |
| `EMERGENCY_STOP` | 고도 무관 즉시 `action.kill()` | **즉시 강제 차단** | 없음(그 자리에서 추락 위험 — 관제사 승인 하 최후 수단) |
| `CANCEL_PATROL` | 호버링 + 경로 초기화 | 유지(모터 안 끔) | 없음 |

**전체 흐름(배터리 자율복귀 예시)**:
```
MAVSDK 배터리 스트림에서 40% 이하 감지 (Jetson 내부, 서버 무관)
→ 스테이션 좌표 존재 확인
→ 상태를 RETURNING으로 변경, 상태공유파일 갱신
→ WaypointMissionController로 스테이션 좌표 비행 시작
→ 도착 감지(반경 기반) → 착륙 콜백 실행
→ action.land() → 텔레메트리로 IDLE 상태 서버 전달
→ 프론트엔드에 상태 갱신 표시 (확인 필요: 실제 UI 반응)
```

```

## 22. 기능별 End-to-End 동작 흐름

### 기능명: 이상탐지 트리거 → 호버링 → 이벤트 등록 (가장 완전하게 검증된 기능)

1. 카메라가 이상 상황을 촬영한다(실기 테스트에서는 사전 녹화 영상을 캡처 루프에 실시간 주입해 재현).
2. `main.py`의 추론 워커가 48프레임 윈도우를 VadCLIP(TensorRT)에 입력한다.
3. anomaly_score가 threshold(0.4073)를 넘고 쿨다운(9초)이 지났으면 트리거로 판정한다.
4. `DroneHoverController.hover_now()`가 MAVSDK `action.hold()`를 호출 — **실제 Pixhawk에 호버링 명령 전달**(실기 확인).
5. 81프레임 RingBuffer 스냅샷을 960×540으로 축소, mp4v로 인코딩한다.
6. 업로드 워커 스레드가 `POST /analyze-video`로 AI서버에 전송한다(최대 180초 대기).
7. AI서버(VideoMAE)가 영상을 분석해 `label`(폭력/배회·침입/절도/정상 등), `maeConfidence`, 자연어 설명, TTS 문구를 생성한다.
8. AI서버가 백엔드에 이벤트를 등록한다(`backend_response`로 이벤트 ID 확인, 예: ID 295).
9. Jetson은 서버 응답(JSON)을 수신해 로그로 기록한다.
10. 드론은 관제사의 다음 명령(RESUME_PATROL 등)을 기다리며 계속 호버링 상태를 유지한다.
11. 프론트엔드에 어떻게 표시되는지는 **확인 필요**(코드는 `EventController`/알림 관련 컴포넌트 존재 확인했으나 직접 검증 안 함).
12. 실패 시: 업로드 실패는 로그만 남기고 호버링 유지(재시도 없음), 업로드 슬롯이 사용 중이면 새 트리거는 드롭됨(§2-3 참고).

### 기능명: 순찰 시작(자율주행)

§17 참고 — 프론트엔드 조작 세부(1~3단계)는 확인 필요, 4단계(Backend STOMP 전달)부터 12단계(완주 통지)까지는 코드로 확인됨.

## 23. 핵심 기술 선택 이유 (Jetson 측에서 확인된 것)

| 기술 | 무엇을 위해 | 왜 이 방식 | 장점 | 한계 |
|---|---|---|---|---|
| VadCLIP(CLIP 기반) → Jigsaw-VAD/WideBranchNet 대체 | 1차 이상탐지 정확도 개선 | 초기 설계부터 모델 교체 가능하도록 인터페이스(`AnomalyPipeline.compute_score()`)를 분리해둠 — 실제로 프로젝트 중간에 교체 실행 | weakly-supervised 방식이라 라벨된 이상 데이터 활용 가능(one-class 계열보다 CCTV→드론 도메인 이동에 유리하다고 판단) | threshold 미보정, 드론 항공뷰 도메인 데이터로 파인튜닝 안 됨 |
| TensorRT 변환(CLIP visual encoder) | Xavier NX에서 추론 속도 확보 | PyTorch 순수 추론 대비 latency 단축 | 추론 latency 평균 0.7~0.9초(TRT) 수준으로 캡처 fps(9) 유지 가능 | 엔진 파일이 하드웨어/버전 종속적(재빌드 필요시 시간 소요), git에 포함 안 함 |
| HTTP(영상) vs STOMP(제어명령) 분리 | 제어명령 지연 방지 | 서버팀 판단: 영상을 STOMP에 얹으면 비상정지 등 제어 프레임이 영상 프레임 뒤에 큐잉되어 늦게 도착하는 안전 문제 | 제어 채널이 영상 트래픽과 독립적 | 두 개의 서로 다른 프로토콜/연결을 관리해야 하는 복잡도 |
| OpenCV mp4v(소프트웨어) vs nvv4l2h264enc(하드웨어 인코더) | 안정적인 클립 인코딩 | 하드웨어 인코더가 write/release 단계에서 실기 hang 확인(0바이트 mp4 생성) — fallback도 없어 구조적 문제 | 검증된 안정성(반복 테스트에서 hang 없음) | 소프트웨어 인코딩이라 상대적으로 느림(81프레임 인코딩에 4~5초) |
| 업로드 워커 스레드 분리(V6) | 서버 응답 대기(최대180초) 동안 추론이 멈추지 않게 | 동기 업로드를 추론 스레드에 넣으면 그 시간 동안 새 이상탐지가 전부 멈춤 | 업로드 대기 중에도 VadCLIP 추론 계속 동작 | 업로드 슬롯 1개 제한이라 연속 트리거 시 드롭 발생 가능(§2-3) |
| 파일 기반 프로세스 간 통신(status_state.json 등) | 독립 프로세스 간(카메라 프로세스 vs 명령 수신 프로세스) 상태 공유 | 각 프로세스가 서로 다른 역할(카메라 점유 vs MAVSDK 명령)로 분리돼야 해서 단일 프로세스로 합치기 어려움 | 프로세스 격리(한쪽이 죽어도 다른 쪽 생존) | 최대 1초 지연(폴링 주기), 파일 I/O 오버헤드 |

백엔드/프론트엔드의 기술 선택 이유(WebSocket vs Polling, React 등)는 **확인 필요**.

## 24. 최종 시스템 데이터 흐름 (확인된 범위)

### 제어 흐름
```
사용자(관제사) → Web Frontend(확인 필요) → Backend(REST API) → STOMP → Jetson(command_receiver.py)
→ MAVSDK(gRPC, localhost:50051) → Pixhawk(MAVLink, 시리얼) → 드론(모터/비행)
```
- 기술/프로토콜: HTTP(Frontend↔Backend, 확인 필요) / STOMP over WebSocket(Backend↔Jetson) / MAVSDK gRPC(Jetson 내부) / MAVLink(Jetson↔Pixhawk)
- 데이터 형식: JSON(모든 구간)

### 상태정보 흐름
```
Pixhawk(MAVLink) → Jetson(telemetry_sender.py, MAVSDK) → STOMP(/app/telemetry, 1초주기) → Backend → Frontend(확인 필요)
```

### 영상 흐름
```
Camera(CSI/GStreamer) → Jetson(main.py)
  ├─ [평시] JPEG 프레임 → HTTP POST → Backend → Frontend(요청 시에만, 확인 필요)
  └─ [트리거 시] mp4 클립 → HTTP POST → AI Server
```

### AI 흐름
```
Jetson(트리거 클립) → AI Server(FastAPI, VideoMAE) → 이상상황 분류(폭력/절도/배회침입/정상 등)
→ AI Server가 직접 Backend에 이벤트 등록(POST /events, backend_response로 확인)
→ Frontend(확인 필요) → 필요 시 관제사가 수동으로 드론 제어(자동 후속조치 없음)
```

## 25. 심사위원 예상 질문 (드론/Jetson 파트)

**Q1. 왜 이상탐지를 엣지(드론)와 서버 두 단계로 나눴는가?**
A. 모든 영상을 서버로 무조건 올리면 네트워크·서버 AI 연산 부하가 크다. 엣지에서 1차로 걸러(VadCLIP) 트리거된 경우만 서버(VideoMAE)에 보내 2차 정밀 판단을 받는 구조로, 트래픽과 연산을 절약한다.

**Q2. 엣지 모델(VadCLIP)과 서버 모델(VideoMAE)의 판단이 다르면 어떻게 되는가?**
A. 현재는 엣지 threshold를 넘긴 것만 서버로 전송되므로, 서버가 최종 판단을 내린다(엣지는 필터 역할). 실기 테스트에서 실제로 두 모델의 기준이 다름을 확인했다(§2-2) — 이는 threshold 재보정이 필요한 근거이며, 아직 완료되지 않은 항목으로 명시해뒀다.

**Q3. 통신(Jetson↔서버)이 끊기면 드론은 어떻게 되는가?**
A. 배터리 자율복귀 페일세이프는 통신 상태와 무관하게 Jetson 내부에서 상시 동작한다(§2-5). 다만 GPS 상실이나 기타 이상상황에 대한 자동 긴급조치는 현재 없고, 서버 명령(수동) 없이는 진행 중인 순찰을 계속 수행한다 — 이는 알려진 한계다.

**Q4. 서버가 다운되면 드론은 어떻게 되는가?**
A. STOMP 연결이 끊기고 5초 후 자동 재연결을 계속 시도한다. 이미 진행 중인 MAVSDK 명령(예: 순찰 비행)은 Jetson 내부 상태로 계속 유지되며, 배터리 페일세이프도 독립적으로 동작한다. 단, 서버가 다운된 동안 새 명령을 받을 수 없어 관제사의 개입(비상정지 등)이 즉시 불가능한 것은 리스크로 남는다.

**Q5. CANCEL_PATROL과 EMERGENCY_STOP을 왜 분리했는가?**
A. 과거 버전은 CANCEL_PATROL이 곧 Kill Switch(모터 즉시 차단)였는데, 관제사가 단순히 "순찰 취소"를 눌렀을 때 드론이 추락하는 심각한 안전 문제가 있었다. 진짜 강제정지(EMERGENCY_STOP)와 안전한 취소(호버링+경로초기화, 모터 유지)를 명확히 분리해 오조작으로 인한 추락을 방지했다.

**Q6. 이상탐지 트리거가 연속으로 여러 번 발생하면 어떻게 되는가?**
A. 업로드 워커가 슬롯 1개만 허용하는 구조라, 이미 업로드 중일 때 새 트리거가 오면 조용히 드롭된다(재시도 없음). 이는 서버 응답을 최대 180초까지 기다릴 수 있는 구조에서 메모리/네트워크 백로그를 막기 위한 설계지만, 연속 이상상황에서 일부 영상이 누락될 수 있는 한계로 인지하고 있다.

**Q7. 정말 "자율주행"이라고 할 수 있는가?**
A. 사전에 설정된 waypoint(경도/위도/고도) 목록을 MAVSDK 표준 미션 기능으로 순차 비행하는 방식이다. 실시간 장애물 회피나 동적 경로 재계획 같은 고급 자율주행 요소는 없고, PX4의 표준 waypoint 미션 유도를 그대로 활용한다 — 정확히는 "사전계획 경로의 자동 순찰 비행"이며, 이 표현이 더 정확하다.

**Q8. 실시간성은 어떻게 확보했는가?**
A. 텔레메트리는 1초 주기 STOMP SEND, 명령은 STOMP push(polling 아님)로 즉시 전달된다. 카메라 캡처는 9fps로 페이싱되고, 추론은 별도 워커 스레드로 분리해 캡처 fps를 막지 않는다. 다만 모델 추론 자체는 5.33초 윈도우 단위라, "이상 발생 후 트리거까지" 최대 5.33초의 지연은 구조적으로 존재한다.

**Q9. 왜 프로세스를 4개로 분리했는가(단일 프로세스로 합치지 않은 이유)?**
A. Pixhawk 시리얼 포트는 동시에 하나의 프로세스만 열 수 있어 `mavsdk_server`로 공유해야 했고, 카메라(GStreamer)와 명령 수신(STOMP+asyncio)은 서로 다른 이벤트 루프/블로킹 특성을 가져 분리하는 것이 안정적이었다. 한 프로세스가 크래시해도 나머지가 생존할 수 있는 격리 효과도 있다(예: 2026-09-14 카메라 프로세스 크래시 시 명령수신/텔레메트리는 영향받지 않음 — 실기로 확인됨).

**Q10. 실제로 기체에 위험한 명령이 잘못 전달될 가능성은 없는가?**
A. 두 가지 안전장치가 있다: (1) 명령 수신 시 내부 상태머신이 현재 상태에 맞지 않는 명령은 무시(예: 착륙 중에 START_PATROL 무시), (2) 채널 자체가 드론별 전용이라 다른 드론 명령이 섞일 수 없고, payload의 droneId도 이중 확인한다. 다만 서버-드론 간 인증은 고정 디바이스 키 하나이고 TLS도 적용 안 된 상태라, 통신 구간 자체의 보안(스푸핑/변조 방지)은 강하지 않다 — 이는 스스로도 인지하고 있는 한계다.

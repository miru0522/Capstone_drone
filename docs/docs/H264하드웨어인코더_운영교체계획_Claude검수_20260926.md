## 승인 근거

- 테스트 문서의 PyGObject/GStreamer 파이프라인, 몽키패치 구조, 성능·안정성 수치를 계획이 정확히 반영했다.
- 현재 운영 경로가 `main.py:843`의 `upload_clip_sync()`임을 정확히 반영했다.
- `push-buffer`, EOS, `set_state(NULL)`이 기존 timeout 범위 밖이라는 실제 구조적 갭을 올바르게 식별했다.
- 별도 프로세스 격리와 부모 watchdog으로 hang 및 timeout 위험을 닫았다.
- CUDA/TensorRT 초기화 이후 `fork()`를 피하고 bounded IPC를 사용하도록 했다.
- 자원 정리, MP4 유효성, 단계별 롤아웃, 설정 기반 롤백과 수치 승인 기준이 포함됐다.

## 선택적 개선 의견

1. 독립 Python worker를 이벤트마다 실행할지 상시 재사용할지 구현 전에 명시한다. 신규 프로세스 기동 비용은 기존 0.796초 측정에 포함되지 않았다.
2. 제한 운영 전환 완료 뒤 `h264enctest.py`, `testermain.py`, 주입 드라이버를 삭제 또는 legacy 이동하는 시점을 명시한다.

두 의견은 승인 차단 사항이 아니다. 구현 단계에서 반영한다.

## 과잉 설계·오류·누락 재검수

초기 승인 후 별도로 “굳이 필요한가”라는 관점의 비판 검수를 수행했다. 첫 검수에서는 상주 worker와 shared memory를 기본안으로 확정할 근거가 부족하다는 지적이 나왔다. 이를 반영해 운영 계획을 다음과 같이 단순화했다.

- 이벤트마다 종료 가능한 subprocess를 실행하는 방식을 기본안으로 변경
- raw 임시파일 또는 stdin 등 단순 IPC부터 측정
- 동일 경계 `mp4v`보다 p95가 20% 이상 빠를 때만 채택
- 목표 미달 시에만 상주 worker와 shared memory를 별도 계획·검수 대상으로 검토
- 2시간 고정 시험을 100회·30분 기본 시험으로 줄이고, 자원 추세가 불명확할 때만 2시간으로 연장
- 서로 정의가 다른 `mp4v` 2.214초와 2.062초 수치를 구분하고 동일 프레임·함수 경계에서 재측정

수정 후 최종 비판 검수 판정은 **APPROVED AS-IS**였다.

## 2. MUST — 배포 전 반드시 해결

### MUST-1. `manifest.json` / `preflight_result.txt`의 candidate uploader SHA-256이 저장소 내용과 불일치

기록된 해시는 **CRLF 줄끝 사본**의 해시다. 저장소에 커밋된 내용(LF)의 해시는 다르다.

| 대상 | 기록된 해시 | 커밋된 내용(LF) 해시 | 일치 |
|---|---|---|---|
| `baseline/uploader.py` | `ac214f96…` | `ac214f96…` | ✅ |
| `candidate/uploader.py` | `248a15b0…` | **`5ea7aaae…`** | ❌ |
| `candidate/h264_encoder_worker.py` | `91700efa…` | `91700efa…` | ✅ |
| `candidate/start_all.sh` | `62bcb38c…` | `62bcb38c…` | ✅ |
| `candidate/restart_component.sh` | `9c268d38…` | `9c268d38…` | ✅ |

재현 근거:
```
git ls-files --eol  → docs/.../candidate/uploader.py : i/lf  w/crlf
                      jetson/code/uploader.py        : i/lf  w/crlf
                      jetson/code/start_all.sh       : i/lf  w/mixed
                      jetson/code/restart_component.sh: i/lf w/mixed
sha256sum docs/.../candidate/uploader.py                  → 248a15b0…  (작업트리, CRLF)
git cat-file blob HEAD:docs/.../candidate/uploader.py|sha256sum → 5ea7aaae…  (커밋, LF)
git cat-file blob HEAD:jetson/code/uploader.py|sha256sum   → 5ea7aaae…  (동일 내용 ✅)
```

Python은 CRLF를 정상 처리하므로 **기능 결함은 아니다.** 그러나 실제 영향이 셋 있다.

1. manifest의 목적(무결성 증명)이 성립하지 않는다. Jetson에서 git으로 파일을 받으면 해시가 절대 맞지 않고, scp로 받으면 맞는다 — 어느 쪽이 "승인된 바이트"인지 문서로 판별 불가.
2. baseline만 LF 규약, candidate uploader만 CRLF 규약이라 baseline↔candidate 해시 대조가 무의미하다.
3. CRLF 사본을 Jetson에 복사해 `vadclip-v4-20260831`에 커밋하면 Jetson 브랜치 blob이 CRLF가 되어 `main`의 `jetson/code/uploader.py`(LF)와 **영구적으로 전체 파일 diff**가 생긴다. CLAUDE.md §2-2의 스냅샷 동기 워크플로가 매번 거짓 변경을 보고하게 된다.

**조치:** candidate 4개 파일을 LF로 정규화 → 4개 해시 재산출 → manifest 갱신 → Jetson에서 `cutover_preflight.sh` **원본 출력 그대로** 재기록. 그리고 실제로 Jetson에 올라간 파일의 `sha256sum`이 갱신된 manifest와 일치하는지 복사 직후 확인.

> 참고: `jetson/code/*.sh` 작업트리 사본은 CRLF/LF 혼재다. **여기서 복사하면 안 된다** — CRLF 셸 스크립트는 `set -eu` 하에서 `$'\r': command not found`로 실패한다. `candidate/*.sh`는 순수 LF이므로 계획대로 `candidate/`에서만 복사할 것.

## 3. SHOULD — 배포 후 관찰 또는 후속 개선

1. **작업기 예열.** H264 최댓값 1.758초는 `results.jsonl:6`(`sequence:5`, `state_total_successes:1`), 즉 **첫 인코딩**이다. p95(1.201초)보다 +0.557초, **mp4v p50(1.490초)보다 0.268초 느리다.** 이상 이벤트는 드물어서 실제 트리거의 상당수가 "재시작 후 첫 건"일 수 있다 → 그 건은 이득이 없다. main.py 시작 시(카메라 초기화 후) 지속 작업기를 미리 띄우면 해소된다.
2. **`H264_TIMEOUT_SEC`가 기본 15초로 방치돼 있다** (`candidate/uploader.py:54`). 관측 최댓값 1.758초의 약 8.5배이고 manifest `runtime` 블록에도 기록이 없다. `upload_clip_sync`는 호버링 판정 경로이므로 인코더가 멈추면 15초를 버린 뒤 영상 없이 실패한다. 5초 수준으로 조이고 manifest에 기록할 것. 이전 검수의 "timeout 기준 확정"이 아직 미해결이다.
3. **인코딩 실패 시 대체 경로가 없다.** 2회 연속 실패면 상태파일에 `rollback_recommended`가 찍히지만(`uploader.py:312-332`) 아무것도 동작하지 않고 **해당 이상 클립은 서버로 전혀 가지 않는다.** 주석(`uploader.py:50-51`)의 근거 중 "중복 업로드 방지"는 성립하지 않는다 — 인코딩이 실패하면 업로드된 것이 없으므로 mp4v 1회 재시도가 중복을 만들 수 없다. 최소한 `rollback_recommended`를 main.log에만 남기지 말고 텔레메트리/관제로 올리고, 가능하면 1회 mp4v fallback을 검토할 것(2번의 5초 타임아웃과 합치면 최악 약 6.5초).
4. **이벤트당 `/dev/shm`에 120 MiB raw를 쓴다** (960×540×3×81 = 125,971,200 B). mp4v 경로에는 없던 RAM 압력이다. `_check_raw_space`(`uploader.py:261-269`)는 tmpfs 여유만 보는데, tmpfs 페이지는 RAM/swap이라 **실제 메모리 고갈을 막지 못한다.** 1단계 기록에 "swap이 이미 약 1.06GB 사용 중이며 2단계 전 재확인 필요"가 남아 있고, 600k 수락 실행 `environment.txt`에는 `df`만 있고 `MemAvailable`/swap이 없다. 첫 실제 트리거 전후로 `MemAvailable`·`SwapFree`를 기록할 것.
5. **작업기 로그 무한 증가.** `/tmp/drone_h264_worker.log`를 append로만 열고 회전이 없다(`uploader.py:218`). 이전 검수 SHOULD가 그대로 남아 있다.
6. **`upload_clip_async`는 여전히 공개돼 있고 호출마다 새 스레드를 만든다.** Linux `PR_SET_PDEATHSIG`는 자식을 만든 **스레드**가 끝날 때 발동하므로, 이 경로에서 띄운 작업기는 그 호출의 스레드가 끝나는 순간 SIGTERM을 받는다. 운영은 안전하다 — main.py는 단일 장수 스레드 `clip-upload-worker`(`main.py:900-905`)에서 `upload_clip_sync`만 쓴다. 하지만 `test_live_upload.py:9`는 `upload_clip_async`를 쓴다. 코드에 주석으로 못 박을 것(이전 검수 SHOULD와 동일).
7. **고정 참조 집계 표본은 20이 아니라 22다.** 참조 2영상이 `all_videos` 단계에도 2회씩 들어가기 때문이다(summary `reference_conditions`의 `count: 22`). 판정은 바뀌지 않지만(모든 단축폭이 0.1초를 크게 넘음) 문서의 "각 코덱으로 20회"는 정정 필요.
8. **`analyze_results.py`가 헤드라인 수치를 재산출하지 않는다.** p50/p95는 실행 시점 summary 레코드에만 있고 `analysis.json`에는 없다. 분석기에 추가해 재현 가능하게 할 것.
9. **수락 실행 `environment.txt`에 시험된 uploader/worker의 SHA-256이 없다.** `run_stage2_600_acceptance.sh`가 인자로 받은 파일을 기록하지 않아, 200회 지연 결과가 정확히 `candidate/` 바이트에서 나왔음을 증명할 수 없다.
10. **저복잡도 장면에서는 H264 파일이 오히려 커진다.** 평균 −45.67%는 맞지만 개별로는 `top5/04_Fighting018` 260,776→552,087 B(+112%), `kakao_20260914` 423,456→662,322 B(+56%), `ucf/RoadAccidents128` 286,568→521,538 B(+82%). 600 kbps CBR 바닥(≈675 KB/9초) 때문이다. 조용한 장면에서는 업로드 시간 이득을 기대하지 말 것. 최악 파일은 3,104,481→737,219 B로 크게 줄어드므로 **꼬리는 개선, 하단은 악화**가 정확한 표현이다.
11. **`preflight_result.txt`는 스크립트 원본 출력이 아니다.** `cutover_preflight.sh:44-45`는 `sha256sum` 형식(`<해시>  <경로>`)을 출력하고 `checked_on=`은 출력하지 않는다. 재타이핑된 요약이라 증빙 가치가 떨어진다. 원본 그대로 보관할 것.
12. `cutover_preflight.sh`에 `python3 -c "import gi"`와 `df -B1 /dev/shm`, `free -m` 확인 추가를 권한다.

### 4-5. 집계 gate가 타당한가 / 최저 SSIM 0.8563과 7/30 미달을 운영 차단으로 봐야 하는가

**결론: SSIM만으로는 차단 사유가 아니다. 단, gate를 바꿨다는 사실은 문서에 명시해야 한다.**

판단 근거는 원시 자료에서 나왔다. `pixel_quality_600.py:163-166`은 스크립트 자체 판정식으로 **영상별** gate를 내장하고 있다.

```python
"all_video_means_pass": all(row["psnr_mean_db"] >= 30.0 and row["ssim_mean"] >= 0.95 ...)
```

그리고 `quality_results/results.jsonl:62`의 결과는:

```
mp4v:      "all_video_means_pass": false
h264_600k: "all_video_means_pass": false
```

**현행 운영 코덱인 mp4v도 이 영상별 gate를 통과하지 못한다.** 따라서 SSIM≥0.95 영상별 gate를 H264 차단 조건으로 쓰면, 논리적으로 오늘 돌고 있는 mp4v도 차단해야 한다. 운영 차단 기준으로 쓸 수 없는 지표다.

그래서 `analyze_quality.py:61-68`의 데이터셋 평균 gate로 판정한 것은 **타당하다.** 다만:

- `analyze_quality.py`는 `all_video_means_pass`를 출력에서 **누락**시켰다. 시험 스크립트 자체 판정식이 false였다는 사실이 `analysis.json`에서 사라졌다.
- 최저 SSIM 0.8563(`04_…assault_7-4`)은 mp4v 최저 0.9306보다 확실히 나쁘다. 그러나 **프레임 단위 최악은 거의 차이가 없다** — `ssim_worst_frame` mp4v 0.8618 vs H264 0.8378, `psnr_worst_frame_db` 31.87 vs 31.16 dB. 즉 H264가 새로 만든 재앙적 프레임은 없고, 해당 1영상이 전 구간에서 균일하게 0.85대다.
- 결정적으로, **그 최악 영상의 서버 판정은 바뀌지 않았다**(4-2절 MUST-5 주석 참조). 화질 지표와 하위 작업 성능이 분리돼 있다는 직접 증거다.

**권고:** SSIM 0.95 영상별 미달은 차단 조건이 아니라 **관찰 항목**으로 유지한다. 대신 품질의 실질 합격 근거는 서버 판정 동등성이며, 거기에 MUST-5의 커버리지 공백(28/30)과 `Abuse028` 카테고리 변경이 있으므로 **그쪽을 조건으로 건다.** 문서에는 "`pixel_quality_600.py`에 내장된 영상별 gate는 mp4v·H264 모두 false였고, 두 코덱 공통 미달이므로 집계 평균 gate로 판정한다"를 명시할 것.

### 중단 조건 — 아래 중 하나라도 발생하면 즉시 중단, 롤백 후 사용자 보고

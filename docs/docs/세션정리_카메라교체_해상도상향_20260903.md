# 세션정리 - 2026-09-03

카메라(IMX219) 교체 대응 + 해상도 상향 + 스트리밍 미재생 진단 + 부하 측정

====================================================
1. 배경
====================================================

Jetson의 CSI 카메라가 IMX219로 교체된 상태에서 세션 시작. 기존 main.py(1280x720, sensor-mode=4)가 새 카메라에서 정상 동작하는지 확인 요청으로 시작.

====================================================
2. 카메라 호환성 문제 - 발견 및 해결
====================================================

**증상**: main.py가 "CSI 카메라 CaptureSession은 열렸지만 첫 프레임 획득에 실패했습니다"로 크래시. gst-launch 단독 테스트로는 "Done Success"가 떠서 처음엔 정상으로 오판했으나, 실제로는 매번 `NvBufSurfaceFromFd Failed` / `dmabuf_fd -1 mapped entry NOT found` 에러가 동반되고 있었음 (fakesink는 버퍼 내용을 검증 안 해서 겉으로는 성공처럼 보였을 뿐).

**원인 진단 과정**:
- v4l2-ctl로 드라이버/모드 테이블 확인 → 정상 (imx219 9-0010으로 정상 바인딩, mode4=1280x720@60fps 등 정상 열거)
- nvargus-daemon 재시작 → 효과 없음, 오히려 테스트 도중 데몬이 크래시하는 것 확인(RPC 소켓 에러)
- `sudo dmesg` 확인 → 결정적 단서: 이 Jetson이 **2026-08-25 부팅 이후 한 번도 재부팅 안 된 상태**였고, imx219 드라이버는 그 부팅 시점에 바인딩됨. 카메라를 **전원 켠 채로 교체(hot-swap)**해서 드라이버가 새 센서를 파워온리셋하지 못한 것으로 결론.

**해결**: Jetson 물리적 재부팅(자동 재부팅 명령은 안전분류기에 막혀 사용자가 직접 수행) → 재부팅 후 카메라 완전 정상화, main.py가 카메라 초기화+VadCLIP 초기화+추론까지 전부 정상 동작 확인(목표 9fps 대비 처리 9~10프레임, 밀린시간 0ms).

**⚠️ 신규 규칙**: CSI 카메라 모듈은 전원 켠 채로 교체 금지. 교체 후 반드시 Jetson 재부팅.

====================================================
3. 해상도 상향 시도 (1280x720 → 최대 → 1920x1080)
====================================================

카메라가 살아있는 걸 확인한 뒤, 스트리밍 화질을 위해 캡처 해상도 자체를 올려보는 작업 진행.

**1) sensor-mode=0 (3280x2464, IMX219 물리적 최대해상도) 시도 → 실패, 심각한 결과 초래**
- `NvMapMemHandleAlloc error 12`(메모리부족) 반복 발생
- VadCLIP 추론 타이밍 붕괴: 9.3초 구간 동안 6프레임만 처리(목표 84프레임), 밀린시간 8.6초까지 누적
- 급기야 **Jetson 전체가 네트워크 응답불가 상태**(SSH 타임아웃, ping 100% 손실)까지 감. 소프트웨어 복구 불가, **물리적 전원 재시작으로만 복구**됨.
- → **sensor-mode=0은 이 Xavier NX + VadCLIP 조합에서 사용 금지.** 실패 기록을 `main.py.bak_20260903_imx219_최대해상도상향`으로 보존.

**2) sensor-mode=2 (1920x1080) 시도 → 성공, 채택**
- 재부팅 후 재시도. 카메라 초기화, VadCLIP 초기화, 캡처 루프 진입까지 모두 정상.
- 초반에 `NvMapMemHandleAlloc error 12`가 몇 차례 있었으나 **일시적**(1.1~1.3초 정도만 밀리고 즉시 회복, 8MP 때와 달리 누적/붕괴 없음)
- 90초 소크테스트로 안정성 1차 확인 후, 이어서 **15분 정식 소크테스트**(tegrastats 5초 간격, 3분 단위 집계) 실시:

| 구간 | RAM(MB) | CPU% | CPU온도 | GPU온도 |
|---|---|---|---|---|
| 0~3분 | 4942 | 9.2% | 45.9°C | 45.8°C |
| 3~6분 | 4932 | 9.4% | 45.8°C | 45.8°C |
| 6~9분 | 4931 | 9.2% | 45.7°C | 45.7°C |
| 9~12분 | 4948 | 9.5% | 45.7°C | 45.5°C |
| 12~15분 | 4941 | 9.3% | 45.8°C | 45.8°C |

전 구간 거의 변화 없음 - 메모리 누수/발열 상승 추세 없이 안정. **단, 이 테스트는 지상 정지(호버링 대기) 상태 기준이며 실비행 중 부하는 검증 안 됨.**

→ main.py를 **CAMERA_WIDTH=1920, CAMERA_HEIGHT=1080, sensor-mode=2로 최종 확정, git 커밋+푸시 완료** (jetson-live, vadclip-v4-20260831 브랜치 반영).

====================================================
4. 스트리밍 기본해상도 상향 (부분 완료, 서버 협의 필요)
====================================================

`command_receiver.py`의 `STREAM_DEFAULT_WIDTH/HEIGHT`를 640x480 → 1280x720으로 상향, 커밋+반영 완료.

**단, 실질적 효과 없음이 확인됨**: 서버(`StreamController.java`)가 `REQUEST_STREAM` 발송 시 `width=640, height=480`을 상수로 항상 명시적으로 못박아 보내는 중이라, 드론쪽 기본값은 서버가 값을 안 줄 때만 쓰이는 fallback이라 지금 구조에선 적용이 안 됨. **실제로 화질을 올리려면 서버측 `StreamController.java`의 `WIDTH/HEIGHT` 상수를 같이 올려야 함** (서버팀 협의 필요, 이번 세션엔 서버 코드 미수정).

====================================================
5. 실시간 영상(관제 대시보드) 미재생 문제 - 원인 절반 진단
====================================================

사용자 제보: 관제 페이지에서 실시간 영상이 안 뜸.

서버 코드(`StreamController.java`, `StreamService.java`) 확인 결과, 구조는:
1. `POST /stream/start` (관제 버튼 클릭) → 서버가 드론에 REQUEST_STREAM 전송 - **정상 동작 확인**
2. `GET /drones/{id}/stream` (브라우저 `<img>` 태그) → 이 연결이 있어야 서버가 "시청자 있음"으로 판단
3. 드론이 프레임 업로드 → 서버가 시청자 0명이면 **410 Gone** 응답, 드론은 즉시 전송 중단

실제 로그 확인 결과, 드론은 REQUEST_STREAM 수신 후 정상적으로 프레임 업로드를 시도하지만 **서버가 계속 410 Gone을 응답** → 2번(`GET /stream`, 실제 영상 수신 연결)이 브라우저에서 정상적으로 안 붙고 있는 것으로 추정.

**미해결 - 다음 확인 필요**: 관제 페이지에서 브라우저 개발자도구(F12) → Network 탭 열고 "실시간 영상" 버튼 클릭 → `/drones/DR-01/stream` 요청의 실제 상태코드 확인 (401/404/502 등). 이건 프론트엔드/서버팀 영역이라 여기까지만 좁혀놓음.

6. 기타
====================================================

- `command_receiver.py`를 세션 중 수동 재시작하면서 `DEVICE_KEY` 환경변수 export를 한 번 빠뜨렸던 자체 회귀를 발견, 즉시 재수정함 (현재는 정상).
- `test_telemetry_sender.py`에 이미 가짜 GPS/배터리 테스트 모드가 구현되어 있음을 확인 (`python3 test_telemetry_sender.py <1|2|3>`, 모드3 = 가짜GPS+가짜배터리 77% 고정값). `start_all.sh` 자체는 인자를 받지 않는 고정 스크립트 - 가짜텔레메트리가 필요하면 `start_all.sh` 실행 후 별도로 `test_telemetry_sender.py`를 추가 실행해야 함. 테스트 후 세션 종료 전 정리(kill)함.
- 배터리 % 컨벤션 재확인: 100~1% = 배터리 연결, 0% = 배터리 제거 개발모드, -100% = 배터리 연결 후 분리 개발모드.

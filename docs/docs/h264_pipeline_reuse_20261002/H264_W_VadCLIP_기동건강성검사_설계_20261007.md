# H264 W + VadCLIP 기동 건강성 검사 설계 (2026-10-07)

## 1. 목적과 범위

H264 600 kbps의 운영 후보는 W 방식, 즉 main 프로세스 안에서 persistent worker를
기동하고 검은 프레임 2장을 실제 `nvv4l2h264enc`로 인코딩하는 방식으로 유지한다.
이 방식은 부팅 중 NVENC cold 비용을 지불해 첫 실제 이상 트리거가 warm 경로를
사용하게 한다.

2026-10-06 실카메라 W/C 비교 5회차에서는 프로세스와 카메라는 정상 종료됐지만,
H264 웜업 뒤 첫 실제 VadCLIP 추론이 `NvMapMemAllocInternalTagged` 및
`CUDNN_STATUS_NOT_INITIALIZED`로 실패했다. 기존 `detect_anomaly()`는 예외를
`score=0.0`으로 바꾸므로 프로세스 생애주기만 보면 PASS처럼 보였다.

이번 변경의 목적은 다음과 같다.

- H264 웜업 직후 실제 운용과 같은 VadCLIP 추론 경로를 검증한다.
- 정상적인 0.0 점수와 추론 예외를 구조적으로 구분한다.
- 일시적 오류는 제한적으로 재시도한다.
- H264 자원 사용과 연관된 실패라면 mp4v로 폴백해 감시는 계속한다.
- H264를 제거한 뒤에도 VadCLIP이 실패하면 감시 불능으로 판정하고 추론 루프를
  시작하지 않는다.
- 자동 재시작 루프를 만들지 않는다.

이번 문서는 설계 단계다. 운영 `main.py`, `uploader.py`, 카메라 프로세스에는 아직
반영하지 않는다.

## 2. 핵심 판정

### 2.1 건강성 검사는 `detect_anomaly()`를 호출하지 않는다

`detect_anomaly()`는 운영 중 오탐과 불필요한 hover를 막기 위해 예외를 0.0으로
바꾼다. 기동 건강성 검사가 이 함수를 사용하면 2026-10-06 사례를 다시 PASS로
오판한다.

건강성 검사는 `AnomalyPipeline.compute_score()`를 직접 호출하고 결과를 다음처럼
분리한다.

```text
ok=true,  score=0.0  -> 정상 추론 결과 0점
ok=false, score=null -> 추론 예외 또는 timeout
```

성공 여부는 score 값으로 판단하지 않는다. 반환값이 유한한 0.0~1.0이고 예외가
없을 때만 성공이다.

### 2.2 검사용 입력은 새 CSI 카메라 프레임을 사용한다

224×224 검은 프레임만 사용하면 1920×1080 라이브 프레임의 전처리와 메모리
압력을 충분히 재현하지 못한다. 건강성 검사 한 번마다 카메라에서
`INFER_WINDOW_LEN`(현재 48)개의 새 프레임을 수집해 실제 `compute_score()`에
전달한다.

- 카메라는 기존 순서대로 모델보다 먼저 열고 첫 프레임을 확인한다.
- VadCLIP 기본 warmup과 H264 W 웜업을 완료한다.
- 그 뒤 새 카메라 프레임 48장을 수집해 건강성 검사를 수행한다.
- 검사용 프레임은 업로드 큐, ring buffer, threshold, hover 경로에 넣지 않는다.
- 각 시도 뒤 VadCLIP feature history를 성공/실패와 관계없이 `finally`에서
  초기화해 운영 추론 기록을 오염시키지 않는다.
- 검사 프레임 참조를 해제한 뒤 운영 capture loop를 시작한다.

## 3. 재시도 정책

### 3.1 H264 활성 상태

건강성 검사는 최대 3회 수행한다.

- 환경변수 기본값: `VADCLIP_HEALTHCHECK_MAX_ATTEMPTS=3`
- 시도 간 대기: `VADCLIP_HEALTHCHECK_BACKOFF_SEC=2.0`
- 매 시도마다 이전 배열을 재사용하지 않고 새 카메라 프레임을 수집한다.
- 첫 실패 뒤 성공하면 `healthy_h264_recovered`로 기록하고 H264를 유지한다.
- 3회 모두 실패하면 H264/NVMM 기여 가능성을 분리하기 위해 mp4v 폴백 단계로
  넘어간다.

3회를 선택한 이유는 기존 운영 코드에서 다음 추론 시 자동 복구된 사례가 있어
한 번의 일시적 오류만으로 감시를 포기하지 않기 위해서다. 동시에 무한 재시도와
반복적인 GPU/NVMM 할당은 막아야 하므로 상한을 3회로 고정한다. 값은 환경변수로
조정할 수 있지만 1~5 범위 밖이면 기동 시 설정 오류로 처리한다.

### 3.2 mp4v 폴백 상태

H264 활성 상태에서 3회 실패하거나 `warmup_clip_encoder()` 자체가 실패하면 다음
순서로 처리한다.

1. persistent H264 worker를 종료하고 종료 여부를 확인한다.
2. 활성 인코더를 `mp4v`로 바꾼다.
3. 폴백 사유와 시각을 상태 파일에 기록한다.
4. 새 카메라 프레임으로 VadCLIP 건강성 검사를 최대 2회 다시 수행한다.
5. 한 번이라도 성공하면 `degraded_mp4v` 상태로 운영 추론 루프를 시작한다.
6. 2회 모두 실패하면 `startup_failed`로 기록하고 main을 비정상 종료한다.

mp4v 단계 재시도 기본값은 `VADCLIP_FALLBACK_HEALTHCHECK_ATTEMPTS=2`다. H264를
제거한 뒤에도 실패가 지속되면 인코더 문제가 아니라 VadCLIP/GPU 감시 기능 자체를
신뢰할 수 없으므로 감시가 정상인 것처럼 계속 실행하지 않는다.

## 4. 기동 실패 시 최종 동작

최종 동작은 단순한 “항상 종료” 또는 “항상 mp4v 계속” 중 하나가 아니라 원인
분리를 포함한 단계형 폴백으로 정한다.

| 상황 | 최종 동작 | 근거 |
|---|---|---|
| H264 웜업 및 건강성 검사 성공 | H264 600 W로 감시 시작 | 목표인 첫 트리거 warm 인코딩 확보 |
| H264 건강성 3회 실패, H264 제거 후 VadCLIP 성공 | mp4v로 감시 시작 | H264를 포기해도 이상 감시는 유지하는 편이 안전 |
| H264 웜업 실패, mp4v 상태에서 VadCLIP 성공 | mp4v로 감시 시작 | 인코더 장애가 감시 전체 중단으로 번지는 것을 방지 |
| mp4v 상태에서도 VadCLIP 2회 실패 | 추론 루프 시작 금지, main 비정상 종료 | 0.0 폴백만 반복하는 상태는 감시 불능을 숨김 |
| 건강성 검사 timeout | 상태 기록 후 main 종료 | 멈춘 CUDA 호출은 같은 프로세스에서 안전하게 취소·복구할 수 없음 |

`start_all.sh`와 `restart_component.sh`에는 자동 재시작 루프를 추가하지 않는다.
main이 실패 종료하면 상태 파일과 로그를 운영자가 확인한 뒤 RAM/lfb 회복을
검증하고 수동으로 조치한다. 카메라와 H264 worker 정리는 `finally` 및 worker의
PDEATHSIG를 함께 사용한다.

## 5. 런타임 인코더 폴백 인터페이스

현재 `CLIP_ENCODER`는 import 시 정해지는 전역 문자열이다. 환경변수만 나중에
바꾸면 이미 import된 uploader에는 반영되지 않는다. 따라서 구현 단계에서
uploader에 다음 명시적 인터페이스를 추가한다.

```python
get_active_clip_encoder() -> str
activate_mp4v_fallback(reason: str) -> None
```

`activate_mp4v_fallback()`은 동일 lock 아래에서 다음을 원자적으로 수행한다.

1. persistent H264 worker 종료
2. active encoder를 `mp4v`로 변경
3. 상태 파일에 configured=`h264`, active=`mp4v`, reason 기록
4. 이후 `encode_frames_to_mp4()` 요청이 mp4v 경로를 사용하도록 전환

설정값과 현재 활성값을 분리한다. `CLIP_ENCODER=h264`라는 원래 설정은 보존하고,
운영 로그와 상태 파일에는 실제 활성 인코더를 별도로 표시한다. 이벤트 하나가
H264 실패한 뒤 같은 이벤트를 mp4v로 재인코딩하는 기존 금지 규칙은 유지한다.
이번 폴백은 이벤트 처리 중이 아니라 운영 루프 시작 전 한 번만 결정된다.

## 6. timeout 처리

Python thread의 timeout만으로는 cuDNN/TensorRT 네이티브 호출을 취소할 수 없다.
timeout 뒤 같은 프로세스를 정상이라고 간주해 계속 실행하지 않는다.

- 전체 시도 제한시간 기본값: `VADCLIP_HEALTHCHECK_TIMEOUT_SEC=20`
- 별도 watchdog이 parent PID와 `/proc/<pid>/stat` 시작 시각을 함께 확인한다.
- 정상 완료 시 parent가 watchdog을 해제한다.
- 제한시간 초과 시 watchdog이 상태 파일에 `timeout`을 원자 기록한다.
- parent에 SIGTERM을 보내고 5초 안에 종료되지 않으면 해당 parent PID에만
  SIGKILL을 보낸다.
- process group 전체나 `pkill python3`를 사용하지 않는다.
- H264 worker는 parent death signal로 종료되는지 확인한다.

watchdog은 프로토타입에서 독립적으로 검증한 뒤 채택한다. PID 재사용 방지를 위해
시작 시각이 달라지면 신호를 보내지 않고 오류만 기록한다.

## 7. 상태 파일과 로그

기본 상태 경로는 `/tmp/drone_startup_health.json`이며 환경변수
`STARTUP_HEALTH_STATE_PATH`로 격리 시험 경로를 지정할 수 있다. 모든 갱신은 기존
`atomic_write_json()`을 사용한다.

최종 상태는 다음 중 하나다.

- `checking`
- `healthy_h264`
- `healthy_h264_recovered`
- `degraded_mp4v`
- `startup_failed`
- `timeout`

예시:

```json
{
  "schema_version": 1,
  "status": "healthy_h264_recovered",
  "pid": 12345,
  "configured_encoder": "h264",
  "active_encoder": "h264",
  "h264_warmup_ok": true,
  "started_at": 1791340000.1,
  "completed_at": 1791340018.5,
  "attempts": [
    {
      "phase": "h264_active",
      "attempt": 1,
      "ok": false,
      "score": null,
      "elapsed_ms": 1410.9,
      "error_type": "RuntimeError",
      "error_message": "cuDNN error: CUDNN_STATUS_NOT_INITIALIZED",
      "memory_before": {"ram_used_mb": 3650, "lfb_count": 45, "lfb_mb": 4},
      "memory_after": {"ram_used_mb": 3810, "lfb_count": 42, "lfb_mb": 4}
    },
    {
      "phase": "h264_active",
      "attempt": 2,
      "ok": true,
      "score": 0.0,
      "elapsed_ms": 880.2
    }
  ]
}
```

cuDNN 오류는 Python 예외의 type/message/traceback으로 기록한다. NvMap 메시지는
네이티브 계층이 stderr에 직접 출력하므로 main 내부에서 무리하게 가로채지 않는다.
대신 각 시도 전후에 다음 구조화된 로그를 남겨 같은 `main.log` 안의 NvMap 줄을
시도 ID와 시간 범위로 연결한다.

```text
vadclip_healthcheck_start phase=h264_active attempt=1 ...
NvMapMemAllocInternalTagged: ...
vadclip_healthcheck_failed phase=h264_active attempt=1 error_type=... ...
```

메모리 샘플은 각 시도 직전과 직후에 tegrastats 한 줄을 수집해 RAM, SWAP,
lfb count/크기를 구조화한다. tegrastats 수집 실패만으로 건강성 검사를 실패시키지는
않지만 `memory_sample_error`를 남긴다.

## 8. 기동 순서

```text
1. 설정 로그 및 startup health 상태=checking 기록
2. CSI 카메라 open + 첫 프레임 확인
3. VadCLIP 모델 load + 기존 synthetic warmup
4. H264 W 웜업(더미 2프레임 실제 NVENC 인코딩)
5. 실제 CSI 프레임 기반 VadCLIP 건강성 검사(최대 3회)
   ├─ 성공: H264 유지
   └─ 모두 실패 또는 H264 웜업 실패
      5-1. H264 worker 종료
      5-2. active encoder=mp4v
      5-3. VadCLIP 건강성 재검사(최대 2회)
          ├─ 성공: degraded_mp4v로 운영 시작
          └─ 실패/timeout: startup_failed 후 main 종료
6. 최종 active encoder와 health status 로그
7. CameraAnomalyPipeline.run() 진입
```

건강성 검사가 끝나기 전에는 upload/inference/periodic recorder/stream worker를
시작하지 않는다. 따라서 실패한 기동에서 서버 업로드, hover, 비행 명령, 주기
녹화가 발생하지 않는다.

## 9. 구현 파일 계획

운영 파일은 검수와 사용자 승인 전까지 수정하지 않는다. 후보 구현은
`docs/docs/h264_pipeline_reuse_20261002/candidate_startup_health/`에 둔다.

| 파일 | 후보 변경 |
|---|---|
| `main.py` | 건강성 상태기계, 실제 프레임 수집, 기동 gate, 최종 상태 로그 |
| `uploader.py` | active encoder 조회, mp4v 폴백, H264 worker 종료 인터페이스 |
| `anomaly_model_trt.py` | 예외를 숨기지 않는 healthcheck API |
| `vadclip_adapter_trt.py` | 성공/실패 모두 feature history를 정리하는 healthcheck/reset API |
| 신규 watchdog | 네이티브 호출 timeout 시 parent PID만 회수 |

기존 `detect_anomaly()`의 운영 중 0.0 폴백은 이번 변경에서 제거하지 않는다.
기동 gate가 정상 상태를 확인한 뒤에도 런타임 일시 오류가 발생할 수 있으므로 기존
연속 실패 경고와 복구 로그를 유지한다.

## 10. `/tmp` 격리 프로토타입 시험

서버 URL은 `127.0.0.1:9`로 고정하고 StreamUploader, hover, periodic recorder,
threshold 처리 경로를 호출하지 않는다. 카메라를 사용하지 않는 단계에서 다음을
먼저 검증한다.

1. 정상 점수: `ok=true`, active=`h264`, `healthy_h264`.
2. 정상 0점: score=0.0이어도 `ok=true`.
3. 1회 cuDNN 예외 주입 후 성공: 2번째 시도에서
   `healthy_h264_recovered`, H264 유지.
4. H264 단계 3회 실패 후 mp4v 단계 성공: H264 worker 종료,
   `degraded_mp4v`, 운영 loop 진입 허용.
5. H264와 mp4v 단계 모두 실패: `startup_failed`, 운영 loop 미호출.
6. sleep/hang 주입: timeout 상태 기록, parent PID만 종료, worker 잔존 없음.
7. 카메라 프레임 획득 실패: 예외 구조화, 재시도 상한 준수.
8. 각 경로에서 상태 파일 원자성, feature history 초기화, 임시 파일 정리를 확인.

## 11. 실카메라 P0 계획

프로토타입과 Claude Code 검수를 통과한 뒤 사용자 승인 하에 수행한다.

- 대상: W + 기동 건강성 검사 후보
- 횟수: 정상 cold start 최대 5회
- 서버 전송: 0회
- hover/비행 명령: 호출 금지
- 각 회차: 카메라 첫 프레임 → VadCLIP warmup → H264 W → 건강성 검사 →
  첫 운영 추론 1회까지
- 측정: 단계별 시각, 모든 health attempt, RAM/SWAP/lfb 0.2초 간격,
  cuDNN/NvMap/Argus 로그, worker PID, 종료 상태
- 첫 health attempt라도 실패하거나 mp4v 폴백이 발생하면 해당 회차 뒤 전체 시험을
  중단하고 원시 증거를 재검수한다.
- `InsufficientMemory`, `IImageNativeBuffer not supported`, timeout, 프로세스
  잔존, SIGTERM 무응답 중 하나라도 발생하면 즉시 중단한다.
- 각 회차 종료 후 RAM/lfb 회복을 확인한 뒤에만 다음 회차를 시작한다.

P0 통과 기준은 5/5 `healthy_h264`, 건강성 검사 예외 0건, 첫 운영 추론 성공
5/5, H264 worker PID 유지, 외부 동작 0건이다. `healthy_h264_recovered`는 운영상
허용 가능한 상태지만 P0 통과로 세지 않고 원인 검토 대상으로 분류한다.

## 12. 운영 반영과 롤백

P0 통과 후에도 다음 순서를 분리한다.

1. 기존 H264 600 기본 전환 커밋 유지
2. W 프로세스 웜업 커밋 유지
3. 기동 건강성 검사와 mp4v 폴백을 별도 커밋
4. 사용자 승인 후 main.py만 재기동
5. 상태 파일이 `healthy_h264`인지 확인
6. 첫 실제 트리거의 인코딩 시간이 warm 수준인지 확인
7. `vadclip-v4-20260831` push 및 `jetson-live` fast-forward

롤백은 건강성 검사 커밋만 되돌릴 수 있어야 한다. H264 600 기본 전환과 W 웜업
커밋은 섞지 않는다. `PeriodicRingRecorder` 미커밋 변경은 구현·배포 전 과정에서
보존한다.

## 13. 미해결 사항과 검수 요청 포인트

- 실제 CSI 프레임 48장 수집이 기동 메모리 피크를 얼마나 늘리는지 실측 필요
- watchdog의 SIGTERM/SIGKILL 및 PID 재사용 방지 구현 검수 필요
- H264 worker 종료 뒤 lfb 회복을 기다릴 최소 조건과 최대 대기시간 결정 필요
- mp4v 폴백 상태를 관제/운영자에게 전달할 채널은 현재 로컬 상태 파일과 로그뿐임
- 기존 런타임 `detect_anomaly()`의 장기 연속 실패 정책은 별도 작업 범위

Claude Code 검수에서는 특히 재시도 상한, H264 제거 후 mp4v 재검사, 실제 0점과
예외 분리, timeout 회수, 운영 loop 진입 gate가 안전 원칙과 일치하는지 확인한다.

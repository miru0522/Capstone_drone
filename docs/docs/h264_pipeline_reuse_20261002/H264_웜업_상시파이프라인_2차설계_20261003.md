# H264 웜업·상시 파이프라인 2차 설계 및 채택 판정

- 작성일: 2026-10-03
- 대상: Jetson H264 600 kbps 이상클립 인코더
- 상태: 격리 프로토타입 검증 완료, 운영 파일 미변경
- 선행 후보: `docs/docs/h264_600_reapply_20260930/` (P0-1~P0-7 통과, 별도 배포 승인 대기)

## 1. 판정

1. **프로세스 웜업은 채택한다.** 현재 승인 후보의 요청별 GStreamer 파이프라인은 유지하고, 카메라와 VadCLIP 초기화가 끝난 뒤 2프레임 더미 인코딩을 1회 실행한다. 이미 2026-09-30 실기에서 웜업 1.915초, 이후 실제 트리거 1.388초가 확인됐다. 기본 H264 600 배포와 섞지 않고 별도 커밋으로 추적한다.
2. **진짜 상시 GStreamer/NVENC 파이프라인 재사용은 현재 Jetson 조합에서 채택하지 않는다.** 정확한 파일 경계를 만든 appsink 방식은 안정적이지만 9초 클립 처리 중앙값이 8.485초였다. 같은 합성 입력을 현재 승인 worker가 warm 0.928초에 처리했다. 상시 방식은 지연을 줄이지 않고 약 9.1배 늘린다.
3. **`splitmuxsink`는 운영 후보에서 제외한다.** 실제 Jetson 시험에서 3개 요청이 81/80/82프레임으로 분리돼 요청 경계를 침범했고, 마지막 조각은 EOS 전에는 완결되지 않았다. push 시간도 요청당 9.18~10.75초였다.
4. 동적 pad unlink/relink와 지속 elementary stream 후 재-mux도 이번 구현 범위에서 제외한다. 둘 다 encoder 출력의 요청 종료를 EOS 없이 확정해야 하는 같은 문제를 남기며, pad 차단·sticky event·keyframe·mux 종료 순서를 새로 관리해야 한다. 현재의 단순 요청별 파이프라인보다 장애면만 늘어난다.

## 2. Claude 1차 설계에서 수정한 전제

### 2.1 실제 버전

- GStreamer core: **1.16.3**
- `splitmuxsink` plugin: **1.16.3**
- `nvv4l2h264enc` plugin: **1.14.0**

따라서 “Jetson GStreamer 전체가 1.14.0”이라는 전제는 틀렸다. 버전이 혼재한 NVIDIA JetPack 구성으로 봐야 한다.

### 2.2 기동 시 `ASYNC_DONE` 대기

입력이 없는 appsrc 파이프라인은 `set_state(PLAYING)` 뒤에도 `current=PAUSED`, `pending=PLAYING`으로 남았다. 입력 전에 `ASYNC_DONE`을 기다린 최초 구현은 30초를 모두 소모했다. 기동 성공 판정은 다음처럼 바꾼다.

1. `set_state(PLAYING)`의 즉시 실패만 검사한다.
2. 입력 전 `ASYNC_DONE`을 성공 조건으로 삼지 않는다.
3. 실제 더미 프레임을 넣고 완결된 MP4를 검증해 GStreamer import, caps negotiation, NVENC, mux를 한 번에 증명한다.

### 2.3 첫 negotiation 전 `force-IDR`

`nvv4l2h264enc`가 첫 buffer로 negotiation되기 전에 `force-IDR` action을 호출하자 Python 예외가 아니라 native segmentation fault가 발생했다. 새 pipeline의 첫 프레임은 원래 IDR이므로 첫 요청에는 action을 호출하지 않고, 첫 요청이 성공한 뒤의 경계에서만 호출해야 한다. 이 동작은 상시 구조의 추가 위험으로 기록한다.

## 3. 2차 구조 후보와 실측 결과

### 3.1 후보 A: 지속 NVENC + appsink + 요청별 qtmux

```text
상시: appsrc -> videoconvert -> nvvidconv -> nvv4l2h264enc
      -> h264parse(byte-stream, AU) -> appsink

요청별: appsrc(H264 AU) -> h264parse -> qtmux -> filesink
```

이 구조는 각 요청에서 정확히 81개 AU를 수집한 뒤 별도 MP4를 만들기 때문에 경계 정확성을 직접 검증할 수 있다. 20회 연속 호출과 1/30/300초 유휴 후 호출 모두 81프레임이었고, 첫·마지막 프레임의 색상 패턴도 해당 요청과 일치했다. 잘못된 입력 거부와 강제 pipeline 중단 후 재생성도 통과했다.

그러나 `appsrc.push-buffer`/AU 출력이 클립의 9fps 재생시간에 가까운 속도로 진행됐다. 다음 변경도 병목을 제거하지 못했다.

- appsink 동시 drain thread
- `appsrc block=false`, `max-bytes=0`
- 입력 PTS를 1ns 단조 증가로 축소
- PTS/DTS 제거
- pipeline clock 비활성화

최종 20회 총시간은 최소 8.465초, 중앙값 8.485초, 최대 10.339초였다. mux 자체는 대체로 약 0.018초이므로 병목은 요청별 MP4 작성이 아니다.

### 3.2 기준 worker

같은 960x540, 9fps, 81프레임 합성 입력을 현재 승인 worker의 persistent Python 프로세스에 넣었다.

| 호출 | 시간 |
|---|---:|
| 첫 호출 | 1.385초 |
| 후속 1 | 0.928초 |
| 후속 2 | 0.928초 |

worker는 요청마다 파이프라인을 만들고 EOS로 닫지만 Python 프로세스와 GStreamer import 비용은 재사용한다. 현재 실측상 이 방식이 가장 빠르고 단순하다.

### 3.3 후보 B: `splitmuxsink`

`split-after`와 요청 시작 IDR을 사용한 3요청 결과는 다음과 같다.

| 파일 | 프레임 수 | 경계 판정 |
|---|---:|---|
| fragment_00 | 81 | 정상 |
| fragment_01 | 80 | 1프레임 부족 |
| fragment_02 | 82 | 이전 요청 프레임 포함 |

세 번째 파일은 EOS 전 파일 목록에 없었고 EOS 뒤에만 완결됐다. `splitmuxsink`는 연속 스트림을 GOP 경계로 자르는 도구이므로, 이미 메모리에 완성된 독립 요청 81프레임을 즉시 파일 하나로 닫는 요구와 맞지 않는다.

## 4. 채택하는 프로세스 웜업 설계

운영 반영은 기본 H264 600 후보가 배포·안정화된 뒤 별도 승인과 별도 커밋으로 진행한다.

```text
1. CSI 카메라 세션 생성 및 첫 프레임 확보
2. VadCLIP 로드 및 warmup
3. H264 persistent worker에 960x540 BGR 더미 2프레임 인코딩 요청
4. 생성 MP4의 ftyp/moov/avc1 또는 avc3 확인 후 즉시 삭제
5. 실제 추론 루프 시작
```

H264 요청별 pipeline은 웜업 종료 때 닫히므로 NVMM을 계속 선점하지 않는다. 웜업의 목적은 worker 프로세스, Python/GI import, 첫 NVENC 호출 비용을 실제 트리거 전에 지불하는 것이다.

필수 동작은 다음과 같다.

- `CLIP_ENCODER != "h264"`이면 no-op
- 웜업 실패는 경고와 진단 로그를 남기고 main 추론은 계속
- 웜업 실패를 실제 이벤트의 `consecutive_failures`에 포함하지 않음
- 더미 raw/partial/final/response 파일을 성공·실패 모두 정리
- 실제 이벤트와 같은 worker lock을 사용해 동시 요청 방지
- 웜업 시간, worker PID, 결과 크기를 기록

## 5. 기동 순서 가설 판정

Claude의 `카메라 -> 상시 인코더 -> VadCLIP` 순서는 상시 인코더 채택을 전제로 한 가설이다. 이번 결과로 상시 인코더를 기각했으므로 운영 기동 순서에 적용하지 않는다.

프로세스 웜업은 pipeline/NVMM을 계속 보유하지 않는다. 이미 실측된 `카메라 -> VadCLIP warmup -> H264 웜업` 순서를 유지한다. 카메라·main 재시작이 필요한 순서 비교는 이 격리 시험의 승인 범위를 벗어나 실행하지 않았다. 향후 순서를 바꿀 이유가 생기면 다음 조건으로 별도 P0 실카메라 시험을 승인받는다.

- 순서 A: 카메라 -> VadCLIP -> H264 웜업
- 순서 B: 카메라 -> H264 웜업 -> VadCLIP
- 각 순서 cold 5회 이상, 재시작 전 `tegrastats` RAM/lfb 기록
- Argus 첫 프레임 성공률, H264 웜업 시간, VadCLIP warmup 시간 기록
- 연속 재시작 금지 및 각 회차 메모리 회복 확인

## 6. 자원과 운영 리스크

- 10분 격리 시험에서 lfb는 `250x4MB`로 유지됐다.
- RAM은 1638MB에서 종료 직전 1778MB로 140MB 증가했다. 합성 프레임 생성·OpenCV 디코딩·Python allocator가 함께 포함돼 있어 NVMM 누수로 단정할 수 없다.
- 상시 encoder는 정상 상태에서도 NVENC/NVMM 핸들을 장시간 보유한다. 기존 Argus `InsufficientMemory` 전례를 고려하면 지연 이득 없는 상시 점유를 운영에 추가할 이유가 없다.
- 실제 카메라+VadCLIP 기동 순서 비교는 운영 카메라 재시작 승인이 필요한 별도 시험이다.

## 7. 최종 반영 순서

1. 현재 H264 600 기본 후보의 배포 절차는 그대로 진행한다.
2. 본 문서와 원시 증거를 Claude Code로 재검수한다.
3. 격리 후보 `candidate_warmup/uploader.py`, `candidate_warmup/main.py`를 검수한다. 후보는 실제 이벤트 통계를 건드리지 않도록 `record_state=False` 경로를 분리했고 로컬 단위시험을 통과했다.
4. 사용자 승인 뒤 Jetson 운영 checkout에 반영한다.
5. 문법 검사, 더미 웜업, 실제 저장영상 주입, 필요 시 승인된 실카메라 1회 시험을 수행한다.
6. 상시 pipeline 코드는 연구 프로토타입으로만 보존하고 운영 반영하지 않는다.

# H264 GStreamer 선로딩 후보 C 격리 검증 (2026-10-06)

## 1. 목적

2026-10-05 운영 기동에서 첫 실제 VadCLIP 추론 직후 Argus
`InsufficientMemory`가 발생했다. 과거 P0-6 run2에서도 H264 웜업 코드가 없는
상태로 같은 시점과 같은 3종 오류가 재현됐으므로, 2프레임 H264 웜업을 단독
원인으로 볼 수는 없다. 다만 카메라가 열린 상태에서 NVENC/NVMM을 실제 할당하는
웜업이 메모리 여유를 줄일 가능성도 배제할 수 없다.

후보 C는 persistent worker 프로세스와 GStreamer Python 모듈만 미리 준비하고,
실제 트리거 전에는 `Gst.parse_launch()`와 `nvv4l2h264enc`를 실행하지 않는다.
운영 main.py에는 아직 반영하지 않았다.

## 2. 설계 변경

### worker

- `_get_gstreamer()`가 `gi`, `Gst` import와 `Gst.init(None)`을 1회 수행한다.
- persistent JSON 프로토콜에 `action=prepare`를 추가했다.
- `prepare`는 GStreamer만 초기화하고 응답한다.
- 기존 요청은 `action`이 없으면 그대로 `encode`로 처리하므로 기존 호출과
  하위 호환된다.
- `encode()`는 같은 `_get_gstreamer()` 결과를 재사용한다.

### uploader

- 2개의 검은 프레임을 실제 인코딩하던 `warmup_clip_encoder()`를
  `prepare_clip_encoder()`로 교체했다.
- 준비 요청은 기존 `_persistent_worker_lock`과 `_run_persistent_worker()`를
  그대로 사용한다.
- `record_state=False`로 운영 H264 jobs/success/failure 통계를 변경하지 않는다.
- 준비 실패는 기존 웜업과 마찬가지로 추론 기동을 막지 않고 경고를 남긴다.

### main

- 카메라 첫 프레임 확보 → VadCLIP warmup → H264 worker/GStreamer prepare →
  추론 루프 순서를 유지한다.
- 실제 NVENC/NVMM 할당은 첫 이상 트리거의 encode 요청까지 미룬다.

## 4. 검증 결과

### 4.1 로컬 정적·단위 시험

- 후보 Python 3개와 시험 스크립트 `py_compile`: PASS
- `preload_only_unit_test.py`: PASS
  - uploader가 `{"action": "prepare"}`만 전달함
  - `record_state=False` 확인
  - mp4v/per-event 모드에서는 no-op 확인
  - worker prepare 응답 확인
- 승인된 H264 600 worker와의 diff는 `_get_gstreamer()` 캐시 및 prepare 분기뿐이다.
- 승인된 warmup 후보 main.py diff는 import/호출 이름 2곳뿐이다.

### 4.2 Jetson 격리 prepare 시험

경로: `/tmp/h264_preload_only_20261006`, raw 경로:
`/dev/shm/h264_preload_only_20261006`. 운영 checkout, 카메라, 서버를 사용하지
않았다.

```json
{
  "ok": true,
  "worker_pid": 41063,
  "worker_alive": true,
  "gstreamer_mapped": true,
  "nvenc_device_fds": [],
  "state_existed_before": false,
  "state_existed_after": false,
  "state_unchanged": true,
  "temporary_leftovers": []
}
```

`/proc/41063/maps`에서 `libgstreamer-1.0` 로드를 확인했고,
`/proc/41063/fd`에는 이름에 `msenc` 또는 `nvenc`가 포함된 장치가 없었다.

### 4.3 prepare 후 첫 encode 호환 시험

동일 격리 worker에서 640×360 검은 프레임 2장을 H264 600 kbps로 인코딩했다.

```json
{
  "prepared": true,
  "worker_pid": 41169,
  "same_worker_after_encode": true,
  "prepare_sec": 0.46733159897848964,
  "first_encode_sec": 1.0801183209987357,
  "output_bytes": 3200
}
```

prepare와 encode가 같은 worker PID를 사용했고 MP4 검증도 통과했다. 시험 종료 후
worker를 종료했으며 잔존 시험 worker가 없음을 확인했다.

## 5. 현재 운영 상태

- Jetson main.py와 H264 worker는 중지 상태다.
- 기존 커밋은 보존했다.
  - `0fcbd0d Enable H264 600 kbps clip encoding`
  - `5728ae1 Warm H264 clip encoder before inference loop`
- 두 커밋은 아직 원격에 push하지 않았다.
- 운영 checkout의 미커밋 `PeriodicRingRecorder` 변경은 그대로 보존돼 있다.
- 후보 C는 문서 후보 디렉터리에만 존재하며 운영 checkout에는 반영하지 않았다.

## 6. 다음 실카메라 비교 시험안

실제 카메라 재시작이 반복되므로 사용자 승인 후 수행한다. 서버 전송, threshold
변경, hover 상태 파일, 비행 명령 경로는 사용하지 않는다. P0-6과 같은 격리
runner로 실제 CSI 카메라와 VadCLIP 첫 실제 추론까지만 실행한다.

1. 조건 W: 현재 2프레임 실제 H264 웜업, cold start 5회.
2. 조건 C: worker/GStreamer 선로딩만 수행, cold start 5회.
3. 순서는 `W-C-C-W-W-C-C-W-W-C`로 교차한다.
4. 매 회 시작 전 `tegrastats`의 RAM/SWAP/lfb를 기록한다.
5. 카메라 첫 프레임, VadCLIP warmup, prepare/warmup, 첫 실제 추론 직전·직후,
   Argus 오류 여부를 단조 시각으로 기록한다.
6. 매 회 종료 후 프로세스가 정상 종료됐는지 확인하고 RAM/lfb가 시작 수준으로
   회복된 뒤에만 다음 회를 수행한다. 회복되지 않으면 연속 재시작하지 않는다.
7. 한 조건에서 Argus 실패가 2/5에 도달하면 해당 조건의 추가 시험을 중단한다.
8. SIGTERM 무응답 여부와 SIGKILL 필요 여부를 별도 필드로 기록한다.

이 10회 시험은 H264가 Argus 실패의 필수 원인인지를 증명하는 시험이 아니다.
실제 NVENC 웜업이 실패율과 메모리 여유에 영향을 주는지, 후보 C가 그 위험을
낮추면서 어느 정도 cold 비용을 줄이는지를 비교한다.

## 7. 실행 준비 상태

- 1회용 runner `run_camera_first_inference_case.py`와 probe
  `camera_first_inference_probe.py`를 작성하고 `py_compile`을 통과했다.
- Claude Code가 외부 동작 차단, W/C 분기, 시간축, process group 종료, timeout
  회수, 회차별 수동 진행을 검수해 `APPROVED WITH CONDITIONS`로 판정했다.
- 자체 배치 점검에서 W 후보 디렉터리에 worker 사본이 없는 점을 발견해 승인된
  H264 600 worker를 그대로 복사했다. 원본과 사본 SHA-256은 모두
  `91700efafa09c755bb30ad7438b9c6c7ab49c31fc3f08e51c4dda88a4e7a30e2`다.
- Jetson `/tmp/h264_preload_compare_20261006/`에 두 후보와 runner를 복사했다.
  로컬과 Jetson의 8개 실행 파일 SHA-256이 모두 일치하고 Jetson
  `py_compile`도 통과했다.
- 카메라 점유 가능 프로세스는 현재 없으며, 준비 직후 자원은 RAM 897/6833MB,
  lfb 256×4MB, SWAP 81/3417MB였다.
- 실제 카메라 실행은 아직 0회다. 사용자 승인 전에는 실행하지 않는다.

각 회차 직전 `main.py|h264_encoder_worker.py` 점유를 사람이 다시 확인한다.
각 회차 종료 후 `runner_result.json`, `probe_result.json`, timestamped tegrastats,
RAM/lfb 회복을 확인한 뒤 다음 회차 명령을 하나씩 실행한다.

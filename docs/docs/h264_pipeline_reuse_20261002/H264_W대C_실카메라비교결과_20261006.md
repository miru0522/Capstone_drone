# H264 웜업(W) vs GStreamer 선로딩(C) 실카메라 비교 결과 (2026-10-06)

## 1. 수행 범위

- 승인된 순서 `W-C-C-W-W-C-C-W-W-C` 10회 전부 수행, 중단 없음.
- 각 회차 직전 `main.py`/`h264_encoder_worker.py` 점유 확인(전부 없음),
  `tegrastats` 1회 기록, 이전 회차 프로세스 종료·자원 상태 확인 후 진행.
- 전체 시험 중 운영 checkout 미수정, main.py/카메라 재기동 없음(격리
  runner만 사용), 서버 전송 없음, `dae_*` 프로세스 영향 없음.
- 종료 후 Jetson에 `main.py`/`h264_encoder_worker.py`/probe 잔존 프로세스 0개.

### 5회차(W) "저하된 PASS" 상세

`probe_result.json`의 `status`는 `PASS`이고 `runner_result.json`도 정상
종료(returncode 0)였지만, 첫 실제 추론이 `score=0.0`으로 찍혔다. `probe.log`를
직접 확인한 결과:

```
H264_PROBE_EVENT {"name": "first_inference_start", ...}
NvMapMemAllocInternalTagged: 1074810371 error 12
NvMapMemHandleAlloc: error 0
NvMapMemAllocInternalTagged: 1074810371 error 12
NvMapMemHandleAlloc: error 0
[INFO] main: [진단] ...
[ERROR] main: 모델 추론 실패 (1회 연속): cuDNN error: CUDNN_STATUS_NOT_INITIALIZED
```

`InsufficientMemory`/`IImageNativeBuffer not supported` 문자열은 없었다 —
즉 카메라(Argus) 자체가 죽은 과거 P0-6 run2 사례와는 다른, **cuDNN
초기화 실패 + NvMap 할당 경고가 동반된 1회성 추론 실패**다. `main.py`의
"추론 실패 시 안전하게 정상으로 처리(score=0.0)" 폴백이 그대로 작동해
프로세스는 정상 종료됐다. probe가 추론을 1회만 수행하고 끝내는 구조라,
이 실패가 다음 프레임에서 자동 복구됐는지는 이번 시험에서 관찰할 수 없다.

## 4. W vs C 비교

| 항목 | W (n=5) | C (n=5) |
|---|---:|---:|
| H264 prepare/웜업 median | **3.165초** | **1.745초** |
| H264 prepare/웜업 min~max | 1.632~3.854 | 1.486~1.866 |
| VadCLIP warmup median | 75.419초 | 73.456초 |
| VadCLIP warmup min~max | 73.169~89.060 | 68.623~77.837 |
| 카메라 첫프레임 median | 1.801초 | 1.679초 |

**관찰 가능한 차이**: H264 단계 자체는 C가 W보다 명확히 빠르다(median
1.745s vs 3.165s, 약 1.8배). 이는 설계 의도와 일치한다 — C는 실제
`nvv4l2h264enc`/NVENC 할당을 하지 않고 GStreamer 모듈만 올리기 때문이다.

**표본이 작아 결론 못 내리는 부분**:
- Argus 완전 실패가 양쪽 다 0건이라, "H264 웜업이 Argus 실패율을
  높인다"는 가설도 "C가 낮춘다"는 가설도 이번 10회로는 증명·반증 불가.
- VadCLIP warmup 시간(73~89초)이 두 조건 간 겹치는 범위라 조건에 따른
  차이로 보기 어렵다 — 이 변동은 H264 조건과 무관한 다른 요인(시스템
  상태, 캐시 등)으로 보인다.
- 5회차의 cuDNN/NvMap 1회성 실패가 W 조건과 인과관계가 있는지, 단순
  우연인지는 n=5로 구분 불가능하다. 같은 cuDNN 패턴이 이전 세션(9/30,
  P0-6 포함)에서도 조건 무관하게 간헐적으로 나타난 전례가 있어, 이번
  1건만으로 "W가 이 실패를 유발한다"고 말할 근거는 부족하다.

## 5. 자원 관찰

- 모든 회차 시작 전 lfb는 256×4MB에서 출발해 회차가 진행되며 완전히
  복귀하지 않고 150~185×4MB 대 어딘가에서 안정화됐다(과거 Argus 실패
  임계로 관측된 1×2MB와는 거리가 멀다).
- RAM은 매 회차 중 VadCLIP 로드 시점에 2900~3700MB까지 치솟고, 회차 종료
  후 1500~1900MB대로 내려오는 패턴이 반복됐다 — 조건(W/C)에 따른 체계적
  차이는 보이지 않는다.
- 10회 전체에서 RAM/lfb가 지속적으로 악화되는 추세는 관찰되지 않았다
  (3~4회차 이후 새로운 평형 수준에서 안정).

## 6. 판정

**이번 10회(n=5+5) 결과로는 후보 C를 운영에 반영할 근거도, 추가 대규모
시험이 불필요하다는 근거도 아직 충분하지 않다.** 다음과 같이 해석한다.

1. **속도 차이는 설계대로 재현됐다** — C가 H264 단계에서 확실히 빠르다.
   다만 이 단계 자체가 전체 부팅 시간(최대 기여 요인은 VadCLIP warmup
   73~89초)에 비하면 작은 비중이다.
2. **Argus 완전 실패는 양쪽 다 0건**이라, 애초에 이번 10회가 검증하려던
   "H264 웜업이 Argus 위험을 높이는가"라는 질문에 긍정도 부정도 할 수
   없다. 표본을 늘리거나(각 조건 10회 이상), VadCLIP 메모리 사용 패턴을
   먼저 조사하는 쪽이 더 효율적일 수 있다.
3. **5회차의 cuDNN 1회성 실패는 조건 C에서는 재현되지 않았지만, 단일
   사례로 패턴을 확정할 수 없다.**

### 다음 작업 제안 (택1, 사용자 판단 필요)

- (a) 각 조건 표본을 10회 이상으로 늘려 Argus/cuDNN 이벤트 발생률의
  통계적 차이를 다시 본다.
- (b) VadCLIP 자체의 메모리 사용 패턴(로드 시점 RAM 피크 2900~3700MB)을
  먼저 조사한다 — H264 조건과 무관하게 이 피크가 Argus/cuDNN 실패와 더
  직접적으로 연관될 가능성이 있다.
- (c) 지금 단계에서는 후보 C 채택 여부를 보류하고, 이미 검수된 웜업(W)
  설계를 그대로 별도 커밋으로 진행한다(원래 계획대로) — C는 연구
  프로토타입으로 유지.

## 9. Codex 원시 증거 재검토 및 선택 권고

10개 `probe_result.json`과 `runner_result.json`의 단조 시각을 다시 계산한 결과,
3절의 시간과 중앙값은 모두 원시 증거와 일치했다. timeout과 SIGTERM 무응답도
각각 0건이다.

다만 5회차 W는 두 기준을 분리해 기록해야 한다.

- 프로세스/카메라 생애주기 기준: PASS(returncode 0, 정상 정리)
- 이상 탐지 기능 기준: **FAIL**(첫 실제 추론이 cuDNN 오류로 실패하고 안전 폴백
  `score=0.0` 반환)

따라서 첫 실제 VadCLIP 추론의 기능 성공률은 W 4/5, C 5/5다. 표본이 작고 같은
오류 계열이 H264 웜업이 없던 과거 P0-6에서도 발생했으므로 W와의 인과관계는
확정할 수 없다. 그렇더라도 운영 검수에서는 이를 단순 PASS로 합산하면 안 된다.

또한 C의 H264 단계 1.745초는 **부팅 시간** 단축이다. C는 NVENC pipeline을 실제로
열지 않기 때문에 첫 이상 트리거의 인코딩 cold 비용을 제거하지 않는다. 이
프로젝트는 부팅 지연을 허용하고 런타임 트리거 지연을 줄이는 것이 목적이므로,
C의 이번 속도 우위는 W를 대체할 근거가 아니다. W는 부팅 때 실제 인코딩을 한 번
수행해 첫 트리거가 warm 경로를 사용하도록 만든다.

현재 증거에 따른 선택 권고는 다음과 같다.

1. 후보 C는 연구 후보로 보존하고 운영 후보에서는 제외한다.
2. 런타임 지연 목표에는 원래 승인된 W를 유지한다.
3. W 운영 재개 전에 “H264 웜업 이후 VadCLIP 건강성 확인”을 별도 P0로 설계한다.
   단순히 score 값만 보면 실제 0점과 추론 실패를 구분할 수 없으므로, 예외 여부를
   명시적으로 반환·기록해야 한다.
4. 건강성 확인이 실패하면 추론 루프를 정상 기동한 것으로 간주하지 말고 worker
   재초기화 또는 기동 실패 처리 후 운영자가 원인을 확인하게 한다.
5. 표본 확대보다 먼저 VadCLIP load/warmup/첫 실제 추론의 RAM·lfb·cuDNN 상태
   변화를 조사한다. W/C 모두 Argus 완전 실패가 0건이었던 이번 조건에서 같은
   카메라 재시작을 단순 반복하는 것은 얻는 정보가 적다.

이 권고는 운영 반영 승인이 아니다. W 재기동과 건강성 확인 코드 반영은 별도
설계·검수·사용자 승인 후 수행한다.

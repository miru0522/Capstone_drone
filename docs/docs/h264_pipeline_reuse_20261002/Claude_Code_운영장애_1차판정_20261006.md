# H264 웜업·상시 파이프라인 운영 장애 재검수 (2026-10-06)

## Context

2026-10-05 Jetson 운영 반영 직후 Argus `InsufficientMemory`가 재현됐다. CLAUDE.md 0-1절에 따라
Claude는 읽기 전용 검수만 수행하며, 이 문서는 구현 계획이 아니라 요청받은 검수 판정 결과다.
실행/커밋/revert 등 실제 조치는 사용자 승인 후 별도로 이뤄져야 한다.

검토한 자료: `operational_main_argus_failure_20261005.log`,
`h264_pipeline_reuse_20261002/candidate_warmup/{uploader.py,main.py}`,
`H264_웜업_상시파이프라인_2차설계_20261003.md`,
`h264_600_reapply_20260930/evidence/p0_live_{runner,main}*{,_run2,_run3}.*` (P0-6 3회 중 1회 실패 전례).

## 핵심 발견: P0-6 run2와 사실상 동일한 실패 패턴을 H264가 전혀 없는 상태에서도 재현했다

`h264_600_reapply_20260930` 3회 실측(H264 웜업 코드 자체가 존재하지 않던 시점, 순수
카메라→VadCLIP 기준 시험):

| run | 결과 | 실패 시점 |
|---|---|---|
| run1 | PASS | - |
| run2 | **FAIL** | VadCLIP warmup 완료 → 캡처 루프 시작 → **첫 실제 추론(581.2ms) 완료 직후** `NvMapMemAllocInternalTagged error 12` / `InsufficientMemory` / `IImageNativeBuffer not supported` |
| run3 | PASS | - |

2026-10-05 운영 장애(H264 웜업 포함)의 타임라인:

VadCLIP warmup 완료 → H264 persistent worker 기동·2프레임 더미 인코딩 성공(2.562s) → 캡처 루프 시작 →
**첫 실제 추론(596ms) 완료 직후** 동일한 3종 Argus 에러.

두 사건은 에러 메시지, 발생 순서(첫 실제 VadCLIP 추론 완료 → 1~2초 내 Argus 실패)가 동일하다.
run2는 H264 코드가 아예 존재하지 않을 때 일어났으므로, **H264 웜업은 이 실패의 필수 조건이 아니다**.
공통 요인은 "VadCLIP 첫 실제 추론(더미 warmup과 다른 실제 10-snippet 피처 경로)이 끝나는 시점"이며,
이는 기존에도 3회 중 1회 빈도로 독립 재현된 비결정적 Argus 단편화 문제다.

다만 H264 웜업은 카메라가 이미 스트리밍 중인 상태에서 NVENC/NVMM 할당을 추가로 수행하므로,
근본 원인은 아니더라도 가용 여유(margin)를 줄여 기존 비결정적 문제의 발생 확률이나 타이밍에
영향을 줬을 가능성은 배제할 수 없다. 현재 증거(운영 1회 vs 격리 3회)로는 H264 웜업의 기여도를
정량적으로 분리할 수 없다 — 두 조건을 모두 통제한 대조 시험이 없기 때문이다.

## 1. 판정: REJECTED (현재 조합의 운영 지속)

웜업+H264 커밋 자체를 "결함"으로 판정하는 것은 아니다(REJECTED는 "더 검증 없이 지금 조합을
운영에서 계속 돌리는 것"에 대한 판정). 근거:

- 실패가 SIGTERM에 반응하지 않고 main PID가 다음날까지 생존, RSS가 4.7GB까지 증가한 뒤에야
  SIGKILL로 정리됐다 — 자원 누수/행 상태가 안전 조치(재시작) 없이 방치될 수 있는 P0급 운영 리스크.
- 원인이 H264 웜업 고유 결함인지, 기존 Argus 비결정적 재발인지 현재 증거만으로는 분리되지 않는다.
  확신도: "H264 웜업이 원인"에 대해서는 낮음(run2가 반증), "기존 Argus 비결정적 재발"에 대해서는
  중간~높음(동일 트리거 지점, 동일 에러 3종 일치)이나, "H264가 margin을 줄여 기여했을 가능성"은
  배제 불가.

## 2. 즉시 조치 (사용자 승인 필요, Claude는 실행하지 않음)

- 현재 두 커밋(`0fcbd0d`, `5728ae1`)은 **revert하지 말고 유지**한다. run2 증거만으로도 보존 가치가
  있고, 실패를 H264 웜업 탓으로 단정할 근거가 부족한 상태에서 revert하면 원인 분리 기회를 잃는다.
- 대신 **운영 실행을 일시 중단**한다(질문 5 답변: "커밋 유지, 실행만 중단"). 사용자 승인 전까지
  Jetson에서 `CLIP_ENCODER=h264` + warmup 조합으로 main.py를 재기동하지 않는다.
- SIGTERM이 먹히지 않는 현상 자체도 별도 조사 대상으로 기록한다(Argus 네이티브 에러 후 Python
  시그널 핸들러가 응답하지 못한 것으로 보이며, 원인 불명 — 6-1/6-2절 기준 P0 미해결 항목에 추가 권고).

## 3. 다음 코드 후보 판정 (A/B/C/D)

- **A(웜업 제거, 기본 H264 600만 사용)**: 비교적 안전하지만 P0-6 run2가 보여주듯 웜업이 없어도
  동일 실패가 발생하므로 "해결책"이 아니라 "위험 요인 하나를 줄이는 보수적 선택"일 뿐이다. 근본
  원인 조사를 포기하지 않는다면 A만으로 재배포를 승인할 근거는 부족하다.
- **B(카메라→H264 웜업→VadCLIP 순서)**: 2차 설계 문서 5절에서 이미 "상시 인코더 전제의 가설이므로
  미적용"으로 명시했고, 웜업(비상시) 방식으로 순서를 바꾸는 시나리오는 아직 한 번도 실측되지 않았다.
  공통 트리거가 "VadCLIP 첫 실제 추론"이라는 이번 분석과도 맞지 않는 가설이라 우선순위가 낮다.
- **C(H264 worker 프로세스만 미리 spawn, 2프레임 인코딩은 보류)**: 이번 분석과 가장 부합한다 —
  Python/GStreamer import 비용은 선점하면서 NVENC/NVMM 실제 할당(가장 의심되는 margin 소모 지점)은
  첫 실제 트리거까지 미룬다. **1순위 후보로 권고.**
- **D(그 외 — 권고 추가)**: 근본 원인이 "VadCLIP 첫 실제 추론 직후 메모리 스파이크"일 가능성이 높으므로,
  VadCLIP 쪽에도 별도 진단이 필요하다 — 추론 직전/직후 `tegrastats`(RAM, lfb) 자동 샘플링을 main.py
  로깅에 추가해, 다음 재발 시 "웜업 유무와 무관하게 첫 실제 추론이 공통 트리거"라는 가설을 직접
  수치로 검증할 수 있게 한다.

## 4. 재시험 절차와 중단 기준 (실행 전 사용자 승인 필요)

1. **대조 시험 설계**: 동일 Jetson, 동일 체크아웃에서 (i) H264 웜업 포함, (ii) H264 웜업 제외(A) 두
   조건을 각각 cold 기동 5회 이상 실시한다. 순서는 현재와 동일(카메라→VadCLIP→H264 웜업).
2. 각 회차마다 기동 전 `tegrastats` 1회, VadCLIP 첫 실제 추론 완료 직후 `tegrastats` 1회를 반드시
   남긴다(RAM, lfb, SWAP).
3. **연속 재시작 금지** — 2차 설계 문서 5절과 동일 기준: 각 회차 종료 후 RAM/lfb가 기동 전 수준으로
   회복됐는지 확인하고서 다음 회차를 시작한다.
4. **중단 기준**: 두 조건 중 하나라도 실패율이 2/5 이상이면 해당 조건은 운영 부적합으로 즉시 보류하고
   추가 회차를 진행하지 않는다. 두 조건의 실패율이 통계적으로 구분 안 되면(예: 둘 다 1/5 내외) H264
   웜업이 유의한 기여 요인이 아니라는 결론을 잠정 채택하고 VadCLIP 쪽 조사로 넘어간다.
5. SIGTERM 무응답 재발 여부도 각 실패마다 별도로 기록한다(좀비 상태 지속 시간, 최종 SIGKILL 필요
   여부) — 이것 자체가 별도의 안전 이슈일 수 있다.

## 5. 사용자 승인 요청 전에 준비할 자료

- 이 문서(판정 요약)와 원본 비교표(운영 실패 vs P0-6 run1/2/3 타임라인 3종 나란히 정리).
- 후보 C(worker pre-spawn, encode 보류)의 격리 유닛 테스트 결과(실제 Jetson 자원 재시작 없이
  먼저 검증 가능한 부분).
- 대조 시험 실행 계획서(3절/4절 내용을 Jetson 실기 시험 승인 요청 양식으로 재정리) — 특히 "카메라
  재시작이 반복적으로 필요하다"는 점을 사용자에게 명시해 사전 승인받는다.
- SIGTERM 무응답 현상에 대한 별도 조사 필요성 안내(현재 미해결로 6-1/6-2절에 추가 권고할 항목).

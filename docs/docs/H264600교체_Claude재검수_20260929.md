# REVISE

MUST는 **1건**입니다. 요청하신 7개 항목 중 6개(1~6)는 저장소 원문과 원시 자료에서 해결을 확인했고, 7번(새 배포 차단 문제)에서 한 건이 남았습니다. 승인 없이 동적 게이트를 실행하지 않은 것은 결함으로 보지 않았습니다 — 게이트의 **위치·중단 조건·검증 항목**만 평가했습니다.

## MUST-1. 운영 파일이 `baseline/`과 일치하는지 확인하는 단계가 없다 — 덮어쓰기 전 검증 부재

`manifest.json`에 `baseline` 해시 5개가 들어 있지만 **이 값을 소비하는 검사가 어디에도 없다.**

- `cutover_preflight.sh:66-67`은 `$CANDIDATE/*`만 `sha256sum`한다. 운영 파일(`$CODE_DIR`)은 `ring_buffer.py`/`state_store.py` 존재 여부만 본다(`:14-19`).
- README 3단계 "manifest 해시와 Jetson 격리 사본의 `sha256sum`을 대조한다"는 **후보↔manifest** 대조다. 운영↔baseline 대조가 아니다.
- 4단계는 백업만, 5단계는 복사 후 `py_compile`/`bash -n`/`git diff --check`다. `git diff --check`는 공백 오류 검사이지 내용 검토가 아니다.
- 중단 조건의 "해시 불일치"도 문맥상 3단계(후보) 기준이다.

**왜 이번에 MUST가 되는가.** 1차 MUST-2를 해결하면서 배포 집합에 `main.py`(1019줄)가 새로 들어왔다. 이 파일은 팀원 작업 영역(`MJPEGStreamServer`, `StreamUploader`, `DroneHoverController`)을 포함하고, 교체 집합 중 동시 수정 가능성이 가장 높다. 그런데 순서상 **5단계에서 이미 덮어쓰고 6단계에서 그 상태로 재시작**한 뒤, 내용 diff를 실제로 보게 되는 시점은 7단계(커밋)다. 운영 `main.py`가 `baseline/main.py`와 다르면 팀원 변경이 조용히 되돌아간 상태로 mp4v 리허설이 돌아간다. 4단계 백업으로 복구는 되지만, 탐지가 사후다.

`baseline/main.py`가 운영본이라는 근거도 현재는 간접적이다. 내가 확인한 바로는 `baseline/main.py`(`e6ab8de8…`)는 `a1ab160^:jetson/code/main.py`와 정확히 일치한다. 이는 `main` 브랜치 스냅샷 기준이고, CLAUDE.md §2-2는 `jetson/code/`를 **실시간 동기가 아닌 주기적 수동 스냅샷**으로 규정한다. 게다가 `a1ab160` 이후로는 `main` 스냅샷이 Jetson보다 앞선 상태로 운용돼 왔다. 따라서 "스냅샷과 같으니 운영본과도 같을 것"은 확인되어야 할 가정이지 확인된 사실이 아니다.

**최소 수정 (3줄 규모):**

1. `cutover_preflight.sh`에 운영 파일 해시 출력 추가 —
   `sha256sum "$CODE_DIR"/main.py "$CODE_DIR"/uploader.py "$CODE_DIR"/start_all.sh "$CODE_DIR"/restart_component.sh` (읽기 전용 유지)
   그리고 `[[ ! -e "$CODE_DIR/h264_encoder_worker.py" ]]` 확인(있으면 중단 — 운영에 없어야 정상).
2. README 교체 순서에 4단계 **앞**으로 새 단계 삽입: "운영 4개 파일의 `sha256sum`이 `manifest.json`의 `baseline`과 일치하는지 대조한다. **불일치 시 복사하지 않고 중단**하고 원인을 확인한다."
3. §중단 및 롤백 조건에 "운영 파일 해시가 `baseline`과 불일치" 추가.

## 해결 확인한 항목 (원문 대조 결과)

### 1. LF 고정과 해시 일치 — ✅

`.gitattributes`가 번들 4개 경로 + 시험 아티팩트를 `text eol=lf`로 고정한다. `git ls-files --eol` 결과 번들 9개 파일 전부 `i/lf w/lf attr/text eol=lf`다.

1차에서 지적한 불일치가 해소됐음을 3중으로 확인했다 — 작업트리 `sha256sum` = 커밋 blob = `manifest.json` = `preflight_result.txt:13-17`의 Jetson 원본 출력.

| 파일 | 해시 | 작업트리 | blob | manifest | Jetson preflight |
|---|---|:-:|:-:|:-:|:-:|
| `candidate/main.py` | `ba020a8d…` | ✅ | ✅ | ✅ | ✅ |
| `candidate/uploader.py` | `5ea7aaae…` | ✅ | ✅ | ✅ | ✅ |
| `candidate/h264_encoder_worker.py` | `91700efa…` | ✅ | ✅ | ✅ | ✅ |
| `candidate/start_all.sh` | `62bcb38c…` | ✅ | ✅ | ✅ | ✅ |
| `candidate/restart_component.sh` | `9c268d38…` | ✅ | ✅ | ✅ | ✅ |

`candidate/uploader.py`가 1차의 CRLF 해시 `248a15b0…`에서 커밋 내용 해시 `5ea7aaae…`로 정정됐다. `preflight_result.txt`도 재타이핑 요약이 아니라 `sha256sum` 원본 형식으로 바뀌었다.

### 2. `baseline/main.py`·`candidate/main.py` — ✅

- `baseline/main.py`(`e6ab8de8…`) = `a1ab160^:jetson/code/main.py` — 인코더 로그 추가 **이전** 버전 (운영본과 같아야 할 기준)
- `candidate/main.py`(`ba020a8d…`) = `HEAD:jetson/code/main.py` — `main` 스냅샷과 후보가 일치
- 두 파일 diff는 **로그 전용 3줄 순증**뿐이다: `CLIP_ENCODER` import 1줄, 기본 인자 `clip_encoder` 1줄, 포맷 문자열 2곳에 `encoder=%s`, 인자 2줄. 새 실행 경로·예외 경로 없음.
- 배포 집합(README:11), `manifest.json` baseline/candidate 양쪽, `cutover_preflight.sh:8`(존재)·`:21`(py_compile)·`:66`(해시), 교체 순서 4·5단계에 모두 포함됐다.

### 3. 종단 게이트 철회 기록 — ✅ (SHOULD 1건 첨부)

철회가 연구 문서 최상단에 명시적으로 기록됐고("측정하지 않은 지표를 합격 근거로 쓰지 않기 위한 범위 변경"), 채택 문서 3곳에 한정 문구가 들어갔다. 저장소 전체 `종단` 검색 결과 **개선을 주장하는 문장은 한 건도 남아 있지 않다.**

### 4. mp4v 리허설 게이트 위치 — ✅

README 6단계에 배치됐고 7단계가 "6단계가 통과한 경우에만" 커밋·push로 조건화됐다. 8단계에서 H264 활성화. **커밋 이전에 리허설을 두어** 깨진 상태가 브랜치에 올라가지 않게 한 점은 내가 1차에서 제안한 순서보다 낫다. 중단 조건에도 "mp4v 확인 재시작에서 기존 동작과 차이 발생"이 들어갔다.

코드상 롤백 우선순위는 재확인했다 — `restart_component.sh:56`의 `${CLIP_ENCODER:-h264}`는 호출 환경 값이 우선하고, `uploader.py:52` 코드 기본값도 `mp4v`라 이중 보호다.

### 5. 서버 판정 원시 자료와 재집계 — ✅

- 원시 JSONL 30개 + `quality_server_judgment_test.py` + `video_list.txt` 커밋됨
- 실패한 2건의 **traceback이 실제로 포함**됨 (`Assault006…jsonl` 55줄, `Burglary017…jsonl` 56줄)
- `analyze_server_judgment.py`가 비-JSON 줄을 `hard_failure_files`로 계수한다 — 1차에서 지적한 `errors=0` 오집계의 근본 원인이 고쳐졌다
- `analysis_corrected.json`: 28/30, `missing_conditions` 2건, `category_change_count: 1`(`Abuse028` categoryId 1→2, 양쪽 CRITICAL) — **내 독립 집계와 정확히 일치**
- 교체 README, 수락 README, 세션정리 3곳에 28/30·미커버·카테고리 변경이 공개됐고 "30/30 검증 완료" 표현이 제거됐다

### 6. 새 preflight 검사 — ✅

요청한 5개 항목이 모두 들어갔다: `python3 -c 'import gi'`(`:23`), 잔존 worker `pgrep -f '[h]264_encoder_worker.py'`(`:32-35`, 자기 자신 매칭 회피 처리까지 정확), `/dev/shm` 잔재 3종(`:36-41`, `anomaly_clip_*.bgr`·`*.response.json`·`drone_clip_encoder_state.json`), `logs/main.pid`와 실제 PID 일치(`:49-53`), `df -B1 /dev/shm` + `free -m`(`:62-65`).

운영 파일 비수정도 유지됐다 — `$CODE_DIR`에 대해서는 존재 확인·`logs/main.pid` 읽기·`/proc/<PID>/environ` 읽기뿐이고, `py_compile`의 `__pycache__`는 번들 디렉터리에 생긴다. 실행된 preflight 스냅샷도 여유가 충분하다(`/dev/shm` 3.58 GB 중 1% 사용, MemAvailable 2138 MB — 이벤트당 120 MiB 대비 충분, Swap 1076/3416 MB).

## SHOULD (배포 차단 아님)

1. **구 계획 문서에 철회된 게이트가 그대로 남아 있다.** `H264하드웨어인코더_운영교체계획_20260926.md:215`("실제 업로드 종단 지연을 통과하지 못하면 H264 [중단]")와 `H264하드웨어인코더_구현세션정리_20260927.md:54`는 제목상 "운영교체계획"이라 현행 절차로 오독될 수 있다. 한 줄로 "2026-09-29 조건연구 문서의 범위 정정으로 대체됨" 포인터를 달면 된다. 이력 문서 자체를 고칠 필요는 없다.
2. **중단 조건의 상태값 표기가 실제 필드와 다르다.** README:92는 `rollback_recommended=true`로 적었지만 실제는 `uploader.py:312-316`에서 `status` **문자열**이 `"rollback_recommended"`가 된다. 운영자가 JSON에서 불리언 키를 찾으면 못 찾는다. 또한 1회 실패 시점의 `status == "error"`를 조기 경보로 같이 적어두면 2회 실패(=이벤트 유실 확정) 전에 개입할 수 있다.
3. `manifest.json`의 `runtime`에 `h264_timeout_sec`가 없다. 기본 15초는 관측 최댓값 1.758초의 약 8.5배이고, `upload_clip_sync`(호버링 판정 경로)에서 인코더가 멈추면 15초를 버린 뒤 영상 없이 실패한다. 값 기록과 하향(≈5초)은 1차 SHOULD 그대로 열려 있다.
4. 첫 H264 요청 1.758초 cold 비용이 README:96에 **공개**됐으나 완화는 안 됐다. 시작 시 worker 예열을 넣으면 "재시작 후 첫 트리거"에서 mp4v p50보다 0.268초 느린 구간이 사라진다.
5. 고정 참조 p50/p95의 실제 표본은 20이 아니라 22다(참조 2영상이 `all_videos` 단계에도 2회씩 포함). 판정은 안 바뀌지만 수락 README의 "각 코덱으로 20회"는 집계 표본과 다르다.
6. `jetson/code/*`는 `.gitattributes` 적용 대상이 아니라 작업트리가 여전히 `w/mixed`·`w/crlf`다. 배포 원본이 `candidate/`이므로 절차상 문제는 없지만, `jetson/code/`에서 셸 스크립트를 복사하면 CRLF로 실패한다. 동일 규칙 확장을 권한다.
7. `analyze_results.py`가 여전히 p50/p95를 재산출하지 않아 `analysis.json`으로 README 표를 교차검증할 수 없다(헤드라인 수치는 실행 시점 summary 레코드에만 존재).
8. `codex_quality_5video_results/`, `stage2_full_results_20260927.jsonl`은 여전히 untracked다. 이번 채택 근거로 인용되지 않으므로 차단 사유는 아니다.

## 확인

읽기 전용으로만 검수했다. Jetson SSH 접속·운영 파일 접근·프로세스 조작·서버 전송·git 쓰기를 하지 않았고, 저장소 파일을 수정하지 않았다. 사용 도구는 `Read`/`Grep`과 `sha256sum`·`diff`·`wc`·`git ls-files --eol`·`git cat-file`·`git show`·`git status`뿐이다. 판정 근거는 커밋 `a86f543`의 원문과 원시 JSONL에서 직접 재산출했고, 문서의 요약 주장은 근거로 쓰지 않았다.

**실제 교체(5단계 복사, 6단계 mp4v 리허설, 8단계 H264 활성화)는 수행하지 않고 대기한다.** MUST-1을 반영하면 정적 번들과 실행 절차는 승인 가능하다고 본다.

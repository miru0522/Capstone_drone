# APPROVED

정적 교체 준비 번들과 승인 후 절차에 **배포 차단 MUST가 없다.** 2차 MUST-1은 해결됐고, 새로 생긴 차단 문제도 없다.

## 이번 커밋에서 확인한 것

### 결정적 증거 — 운영 파일이 baseline과 실제로 일치함

2차에서 제기한 핵심 우려는 "`baseline/main.py`가 운영본이라는 가정이 검증되지 않았다"였다. `preflight_result.txt:1-5`가 **실기에서 이 가정을 실증**했다.

| 운영 파일 | Jetson 실측 SHA-256 | manifest `baseline` | 일치 |
|---|---|:-:|:-:|
| `main.py` | `e6ab8de8…` | `e6ab8de8…` | ✅ |
| `uploader.py` | `ac214f96…` | `ac214f96…` | ✅ |
| `start_all.sh` | `b1915fde…` | `b1915fde…` | ✅ |
| `restart_component.sh` | `e124b1b9…` | `e124b1b9…` | ✅ |
| `h264_encoder_worker.py` | 부재 | `null` | ✅ |

즉 운영 `main.py`는 `a1ab160^:jetson/code/main.py`와 바이트 단위로 같다. **팀원 변경 드리프트가 없음이 확인됐으므로**, 1019줄 파일을 덮어써도 되돌릴 팀원 작업이 없다. 이것이 2차 MUST의 실질이었고 해소됐다.

### 검사 로직

`cutover_preflight.sh:27-51`이 `manifest.json`의 `baseline`을 읽어 4개 파일을 `hashlib.sha256(path.read_bytes())`로 비교하고, 불일치나 파일 부재 시 `SystemExit`으로 종료한다. `set -euo pipefail` 하에서 스크립트가 중단되므로 **후보 복사 단계에 도달하지 못한다.** 운영 worker가 존재해도 실패한다(`:47-49`). 검사 위치도 `py_compile`·`gi`·`gst-inspect`보다 앞이라 가장 중요한 조건에서 먼저 멈춘다. 읽기 전용이며(`read_bytes`/`read_text`만) 운영 파일을 수정하지 않는다.

### 절차와 중단 조건

README 4단계가 백업(5)·복사(6)보다 **앞**에 배치됐고 "불일치하면 복사하지 않고 중단해 팀원 변경 여부를 확인한다"로 명시됐다. 중단 조건에 "운영 파일이 manifest `baseline`과 불일치"가 추가됐고, 단계 재번호에 따른 본문 참조(7단계)도 일관되게 갱신됐다.

### preflight_result.txt는 진짜 원본 출력이다

파일의 줄 순서가 스크립트의 출력 순서(`baseline_match`×5 → `preflight=PASS` → `main_pid` → `current_encoder` → `candidate_encoder` → `candidate_bitrate` → `dev_shm_usage:`+`df` → `memory_snapshot:`+`free` → `sha256sum`×5)와 **정확히 일치**한다. 1차에서 지적한 재타이핑 요약 문제가 완전히 해소됐다. 실행 환경도 `/tmp/codex_h264_cutover_review3`, `main_pid=5563`, `current_encoder=mp4v`로 운영이 교체 전 상태 그대로임을 확인했다.

## 전체 검증 사슬 (3회 검수 종합)

1. **후보 코드 = 시험된 코드** — `candidate/uploader.py`(`5ea7aaae…`)와 `h264_encoder_worker.py`(`91700efa…`)는 1차 검토 이후 내용 변경 없음. `candidate/main.py`는 운영본 대비 로그 3줄 순증뿐.
2. **번들 무결성** — 작업트리 = 커밋 blob = manifest = Jetson preflight 원본 출력, 9개 파일 전부 일치. LF 고정.
3. **운영 기준 실증** — 운영 4개 파일 해시 일치, worker 부재 (이번 커밋).
4. **절차 안전성** — preflight → baseline 대조(중단) → 백업 → 복사 → **mp4v 리허설(중단)** → 커밋 → H264 활성화 → 환경 확인 → 첫 트리거(별도 승인). `start_all.sh` 전체 재기동·`pkill python3`·`dae_*` 조작 없음.
5. **근거의 정직성** — 종단 게이트 철회가 연구·채택 문서에 기록됐고 측정되지 않은 개선 주장이 남아 있지 않음. 서버 판정은 28/30, `Burglary017` 미커버 1건, `Abuse028` categoryId 1→2 변경 1건을 원시 traceback과 함께 공개.

## 배포 후 후속 (차단 아님)

1. `H264_TIMEOUT_SEC` 기본 15초 — 관측 최댓값 1.758초의 약 8.5배이고 manifest `runtime`에 미기록. 호버링 판정 경로에서 인코더가 멈추면 15초를 버린 뒤 영상 없이 실패한다. ≈5초 하향과 기록을 권한다.
2. 시작 시 worker 예열 — "재시작 후 첫 트리거"의 1.758초(mp4v p50보다 0.268초 느림) 구간이 사라진다. README에 공개는 됐으나 완화는 안 됨.
3. 인코딩 실패 시 mp4v 대체 경로 없음 — 2회 연속 실패 시 해당 이상 클립이 서버로 전혀 가지 않는다. 최소한 `rollback_recommended`를 관제/텔레메트리로 올리는 것을 권한다.
4. `/tmp/drone_h264_worker.log` 회전 없음.
5. `upload_clip_async`는 호출마다 새 스레드를 만들어 `PR_SET_PDEATHSIG` 조기 발동 위험이 있다. 운영 경로(`main.py`의 단일 `clip-upload-worker` → `upload_clip_sync`)는 안전하지만 `test_live_upload.py`가 이 경로를 쓴다.
6. `analyze_results.py`가 p50/p95를 재산출하지 않아 README 표를 `analysis.json`으로 교차검증할 수 없다.
7. `jetson/code/*` 작업트리는 아직 `w/mixed`·`w/crlf`다. 속성이 설정됐으므로 다음 checkout(또는 `git add --renormalize`) 시 정규화된다. 인덱스는 이미 LF이고 배포 원본은 `candidate/`이므로 교체에는 영향 없다.
8. 첫 실제 트리거 전후로 `MemAvailable`·`SwapFree` 기록 (이벤트당 `/dev/shm` 120 MiB). 현재 여유 2129 MB로 충분하지만 추세는 볼 것.

## 확인

읽기 전용으로만 검수했다. Jetson SSH 접속·운영 파일 접근·프로세스 조작·서버 전송·git 쓰기를 하지 않았고, 저장소 파일을 수정하지 않았다. 판정 근거는 커밋 `270ae82`의 원문(`cutover_preflight.sh`, `preflight_result.txt`, README diff, `.gitattributes`)과 앞선 두 커밋에서 확인한 해시 사슬을 직접 대조한 것이다.

**이 승인은 정적 번들과 문서화된 절차에 대한 것이다.** 7단계 mp4v 리허설, 9단계 H264 활성화, 11단계 첫 실제 트리거는 절차 자체가 별도 승인으로 게이트해 둔 운영 변경이므로, 그 승인은 사용자가 내리면 된다. 나는 실제 교체를 수행하지 않았다.

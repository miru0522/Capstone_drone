## 1. 배경 — 왜 이 테스트를 했는가

`uploader.py`의 `encode_frames_to_mp4()`는 2026-08-31 커밋(`7123cfa8`)에서 소프트웨어 인코더(OpenCV `mp4v`)로 전환됐다. 이유는 당시 GStreamer 하드웨어 인코더(`nvv4l2h264enc`) 경로가 `cv2.VideoWriter` + `CAP_GSTREAMER`를 통해 호출됐을 때 write/release 단계에서 **hang**되는 문제가 있었기 때문이다.

이번 세션에서 "폴백 구조 말고 안정적으로 작동할 방안을 연구하라"는 요청에 따라 재조사했고, **하드웨어 인코더 자체·`qtmux` 자체는 문제가 없으며, 문제는 `cv2.VideoWriter`의 GStreamer 래퍼 특유의 호출 방식(백그라운드 스레드, EOS 처리 미흡 추정)**이었다는 결론에 도달했다. `gst-launch-1.0`으로 동일 파이프라인을 직접 돌리면 정상 동작(3.9초, hang 없음)하는 것으로 확인했다.

## 2. 아키텍처 — 무엇을 어떻게 만들었나

### 2-1. `h264enctest.py` (신규, `drone_2026/code/` 최상위)

`uploader.py`의 `encode_frames_to_mp4()`와 **동일한 시그니처 계약**(프레임 리스트 → mp4 임시파일 경로 반환, 호출자가 삭제 책임)을 갖는 대체 함수 `encode_frames_to_mp4_hw()`를 제공한다.

**핵심 설계 — OpenCV를 거치지 않는다**:
- `gi.repository.Gst`(PyGObject)로 GStreamer 파이프라인을 **직접** 제어한다. 이 Jetson에는 이미 `gi`/`Gst` 1.16.3이 설치돼 있어 신규 패키지 설치가 필요 없다(확인함).
- 파이프라인 문자열은 2026-08-26 커밋에서 쓰던 것과 동일하다:
  ```
  appsrc name=src is-live=true block=true format=time
    caps=video/x-raw,format=BGR,width={w},height={h},framerate={fps}/1 !
  videoconvert ! video/x-raw,format=NV12 !
  nvvidconv ! video/x-raw(memory:NVMM),format=NV12 !
  nvv4l2h264enc bitrate={bitrate} !
  h264parse ! qtmux ! filesink location={path}
  ```
- **EOS/에러를 GStreamer 버스 메시지로 명시적으로 확인**한다: `GLib.MainLoop`을 별도 스레드에서 실행하고, 메인 스레드는 `runner.join(timeout=timeout_sec)`(기본 15초)로 대기한다. `timeout_sec` 안에 EOS를 못 받으면(hang 의심) `HWEncodeError`를 던지고 파이프라인을 강제로 `NULL` 상태로 내린다 — **기존 hang 문제가 재현되더라도 무한정 멈추지 않고 예외로 빠져나온다.**
- 인코딩 완료 시 `logger.info("h264(HW) 인코딩 완료: frames=%d, fps=%d, size=%d bytes, elapsed=%.3fs", ...)`로 소요시간을 남긴다(mp4v의 완료 로그와 같은 패턴).
- `if __name__ == "__main__":` 블록에 독립 자체시험 CLI가 있다: `python3 h264enctest.py <video> --repeats N`으로 실제 영상 파일을 반복 인코딩해 hang 여부만 별도로 검증 가능.

### 2-2. `testermain.py` (신규, `main.py`의 복사본)

`main.py`를 그대로 복사한 뒤 **딱 2곳만** 수정했다(그 외 로직은 100% 동일):

```diff
 from uploader import ANALYZE_URL, DRONE_ID, UPLOAD_MODE, upload_clip_sync
+import uploader as _uploader
+import h264enctest as _h264enctest
+_uploader.encode_frames_to_mp4 = _h264enctest.encode_frames_to_mp4_hw  # 몽키패치
...
-logger = logging.getLogger("main")
+logger = logging.getLogger("testermain")
```

**몽키패치 원리**: `uploader.py`의 `_post_with_retry()`/`upload_clip_sync()` 내부에서 `encode_frames_to_mp4(frames, ...)`를 호출하는 부분은 그대로 두고, `uploader` 모듈 객체의 `encode_frames_to_mp4` 속성 자체를 `testermain.py` 시작 시점에 하드웨어 버전으로 바꿔치기한다. Python은 함수 호출을 모듈 전역 네임스페이스에서 매번 조회하므로, `uploader.py` 소스 자체는 **단 한 줄도 안 건드리고** 동작을 교체할 수 있다. 로거 이름만 바꿔서 로그에서 실제 운영(`main`)과 테스트(`testermain`)를 구분할 수 있게 했다.

**왜 이 방식인가**: 사용자가 "main.py를 건드려야 하면 복사해서 testermain.py로 수정·실행"하라고 명시적으로 요구했기 때문이다. `uploader.py`도 원본 그대로다 — 실제로 바뀐 파일은 신규 파일 2개(`h264enctest.py`, `testermain.py`)뿐이다.

### 2-3. 테스트 드라이버 스크립트 (신규)

- `run_batch_injection.sh` — `video/` 폴더 전체(20개)를 순서대로 2회 반복 투입
- `run_sustained_injection.sh` — 신뢰도 100%로 트리거되는 영상 5개(아래 3-2절)를 각 6회씩(총 30회) 투입

둘 다 기존 `test_trigger_inject.py`(신호파일 기반 주입, 이미 운영에 있던 도구)를 그대로 호출한다 — 새 주입 메커니즘을 만들지 않았다.

### 2-4. 실기 전환 절차 (테스트할 때마다 수행한 것, 코드 아님)

1. 실행 중인 `main.py`를 PID 검증 후 `SIGTERM` → 실제 종료 확인
2. `/proc/meminfo`의 `MemAvailable`이 회복됐는지 확인 (참고: 이것만으로 카메라 초기화 안정성을 보장하진 못함 — 별도 문서 `젯슨_프로세스시작_선행조건_20260926.md` 참고)
3. `testermain.py` 실행, 캡처 루프 시작 로그 확인
4. 테스트 진행
5. `testermain.py` 종료 → 메모리 회복 확인 → `main.py` 재기동(`restart_component.sh main` 또는 동등 절차)

## 4. 아직 안 한 것 / Codex가 판단·진행할 부분

1. **운영 반영 여부 자체가 결정 안 됨** — 이 문서는 "이렇게 하면 된다"는 근거 자료이지, 반영 승인이 아니다.
2. **`uploader.py` 자체 수정** — 실제로 `encode_frames_to_mp4`를 이 하드웨어 버전으로 교체(또는 환경변수로 A/B 선택 가능하게)하려면 `uploader.py`를 직접 고쳐야 한다. 이번 테스트는 몽키패치로 우회했을 뿐 `uploader.py`는 안 건드렸다.
3. **장시간(수 시간) 안정성 미검증** — 이번 테스트는 최대 12분 36초 연속이었다. 메모리 누수 여부는 이 범위 밖.
4. **`nvargus-daemon` 타이밍 문제는 별개 이슈** — 카메라 세션을 새로 여는 시점(프로세스 재시작·재부팅 직후)에 간헐적으로 실패하는 문제를 발견했으나, 이건 하드웨어 인코더와 무관하게 기존부터 있던 문제로 별도 문서(`젯슨_프로세스시작_선행조건_20260926.md`)에 정리해뒀다. 인코더 반영과 별개로 다뤄야 한다.
5. **테스트 파일 정리 시점** — `h264enctest.py`/`testermain.py`/드라이버 스크립트는 사용자 지시에 따라 "테스트 종료 후"까지 유지 중이다. 운영 반영이 결정되면 `h264enctest.py`의 핵심 로직을 `uploader.py`에 통합하고, `testermain.py`와 드라이버 스크립트는 정리(삭제 또는 legacy 이동) 대상이다.
